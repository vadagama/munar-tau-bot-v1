# Спецификация VS-8: `documents`

Дата: 23.10.2026. Статус: согласовано пользователем 23.10.2026 сообщением «Делай», включая
предложения раздела «Решения для согласования».
Модуль [карты](VS8-CAPABILITY-MAP.md); стек, структура, стиль, команды,
проверки и границы — [общая часть](SPEC-vs8-conventions.md).

## Цель и основания

DOC-01–03, WRK-17–18: хранить доступные по аудитории документы и версии,
организовать проверку и исключить приёмку работы с неполным или устаревшим
обязательным комплектом. Источники: требования §7/9, жизненный цикл §7,
LLD-02 §6 и LLD-03 §3.7. Оплата и подтверждение работы остаются независимыми.

## Сценарии и данные

Карточка: название, тип, номер при наличии, дата, стороны, дома, аудитория,
связанные обращение/задание, подготовитель и проверяющий.
У версии — собственный файл, порядковый номер, автор, время, история проверок.
Подписанный вне системы экземпляр хранится отдельно от черновика; проверка
фиксирует способ и основание проверки подписи. Проверка не называется ЭЦП.

Переходы: `draft → on_review → approved` либо `on_review → returned`.
Исправление возвращённого создаёт новую версию. `approved → needs_fix`
фиксирует ошибку с причиной и сохраняет прежнюю проверку в истории.
Файлы и содержимое версии не перезаписываются; меняются состояние и журнал
проверки. Новая версия не наследует подтверждение предыдущей.

Обязательство содержит тип, основание, этап предоставления, ответственного,
проверяющего, срок и конкретную версию регламента. Этапы: до приёмки либо
после приёмки. Закрытие обращения не закрывает последующее обязательство;
оно остаётся в очереди управляющего с напоминаниями по регламенту.

Предлагается определять требования и проверяющих декларативным правилом
по виду работ/документа. Пока для `document_required=true` нет правила,
действие остаётся заблокированным с объяснением; исполнитель не может
сам снять обязательность или подменить акт произвольным файлом.

## Доступ — предлагаемая матрица

| Операция | Правило |
| --- | --- |
| Подготовить документ работы | Управляющий объектом; назначенный сотрудник — только по своему заданию и назначенной обязанности подготовки |
| Проверить технический документ | Действующий `doc_reviewer` или наследующая роль, назначенный правилом, с доступом к объекту; ограничения собственной приёмки сохраняются |
| Финансовый документ | Дополнительно финансовая аудитория PAY-08; проверка документа не является сверкой платежа |
| Прочитать общие инструкции | Подтверждённый житель по DOC-02 |
| Прочитать собственнические | Подтверждённый собственник соответствующего помещения и дома |
| Прочитать служебные | Уполномоченный сотрудник; исполнитель — инструкции и документы назначенного задания |
| Техадминистратор | Только разрешённая поддержка ROL-06, без автоматического доступа ко всем документам |

Доступ к карточке, версии, скачиванию и уведомлению проверяется отдельно
от самого факта связи с обращением. Внутренний акт не раскрывается жителю
автоматически при отправке результата. Каталог хранит историю прежних версий.

## Контракты

API LLD-03: создание `POST /v1/documents`, новая версия
`POST /v1/documents/{id}/versions`; действия `/submit`, `/approve`, `/return`,
`/needs-fix` по `/v1/documents/{id}/versions/{v}`. Чтение списка и карточки,
доступного комплекта и файла проходит через PDP. Предлагаемые дополнения:
чтение обязательств и явное назначение/исполнение обязанности с версией и причиной.

Вход новой версии ссылается на уже сохранённый разрешённый attachment;
сервер проверяет владельца, аудиторию, завершённость загрузки и `is_test`.
Клиент не присылает `approved=true`, проверяющего или состав итогового снимка
как доверенные факты.

Граница провайдера для заданий/обращений: внутри переданной транзакции
`documents` проверяет требования, версии и область и возвращает устойчиво
упорядоченный снимок `{requirement_id, document_id, document_version_id}`.
Потребитель сохраняет его вместе со снимком отчётов. При подтверждении
повторно проверяются соответствие снимка текущему комплекту и действительность
проверок. Документы блокируются в согласованном порядке с работой/обращением.
Гонка проверки и `needs_fix` не допускает подтверждения недействительного комплекта.

Для публикаций и инициатив провайдер проверяет конкретные версии и аудиторию
без раскрытия внутреннего файла. Признанная ошибочной версия перестаёт
подходить для новых действий; ранее состоявшаяся приёмка не переписывается.

## Интерфейс

Кабинет: каталог, карточка с историей версий, подготовка/проверка/возврат,
очередь обязательств; в обращении и задании — состав и причины блокировки.
Бот сотрудника: свои обязанности, просмотр доступной версии, отправка файла
по назначенной обязанности и действия проверки по PDP. Бот жителя: каталог
доступных документов, версия и скачивание; справка о порядке запроса в ОСИ.
Каталог не заменяет юридически надлежащий письменный запрос.

## Приёмка и проверки

- Возврат и исправление сохраняют старый файл, причины и проверку; повтор
  отправки не создаёт дубликат версии/уведомления.
- Непроверенный, чужой, тестовый либо `needs_fix` акт не проходит в реальный
  комплект. Изменившийся снимок запрещает старое подтверждение.
- Проверены одновременные approve/return, needs-fix/подтверждение и
  смена назначения; соблюдён запрет собственной приёмки.
- Обязательство после приёмки видно после закрытия обращения; напоминание
  не означает автоматического выполнения.
- Прямой UUID/URL не открывает внутренний или финансовый файл жителю,
  исполнителю вне задания либо техадминистратору без поддержки.
- API, кабинет, оба бота и эмуляция показывают одинаковые доступ и состояние.

Vitest проверяет FSM/матрицу/снимки; PostgreSQL — блокировки, транзакции,
версии, RLS и rollback; браузер — полный путь и ошибки формы.
Команды и разрешение интеграционного прогона — в общей части.

## Решения для согласования

Предлагаемая матрица подготовки/проверки и декларативная настройка обязательств.
Фактические виды обязательных актов, основания, подготовители и проверяющие
ОСИ задаются перед использованием вида работ; тестовый пример не является
утверждённым юридическим регламентом.
