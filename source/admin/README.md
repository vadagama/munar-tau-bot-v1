# Кабинет ОСИ (admin)

SPA для администраторов и председателя ОСИ: Vite + React + Refine v4 + Ant Design 5.
Статика раздаётся с Cloudflare Pages без серверных функций (ADR-002).

## Команды (из `source/`)

```bash
npm install              # установка всех workspaces
npm run dev -w admin     # dev-сервер Vite
npm run build -w admin   # production-сборка в admin/dist
npm run preview -w admin # локальный просмотр сборки (SPA-fallback включён)
```

## Переменные среды

Только публичные значения, допустимые в браузере и в статической сборке (ADR-002).
Создайте файл `admin/.env.local` (в git не попадает — см. корневой `.gitignore`):

```bash
VITE_SUPABASE_URL=https://YOUR-SUPABASE-HOST
VITE_SUPABASE_PUBLISHABLE_KEY=YOUR-PUBLISHABLE-KEY
# Регион облачной БД; для текущего стенда — eu-central-1. Для self-hosted оставить пустым.
VITE_SUPABASE_FUNCTION_REGION=eu-central-1
```

Локальная интеграция с облачным бэкендом: функция api допускает только origin
кабинета (секрет `CABINET_ORIGIN`), поэтому из браузера под localhost прод
напрямую недоступен — CORS. Обход: задайте `ADMIN_UPSTREAM_URL = адрес
Supabase-проекта` (в `admin/.env.local` или в окружении) и
`VITE_SUPABASE_URL = http://localhost:5173` — dev-сервер Vite проксирует
`/auth/v1` и `/functions/v1` на прод, браузер ходит на свой origin. redirect
`http://localhost:5173` уже есть в allow-list Supabase Auth стенда.

```bash
VITE_SUPABASE_URL=http://localhost:5173 \
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_... \
VITE_SUPABASE_FUNCTION_REGION=eu-central-1 \
ADMIN_UPSTREAM_URL=https://YOUR-SUPABASE-HOST \
npm run dev -w admin
```

Запрещено помещать сюда секреты: service-role key, токен бота, OIDC Client Secret.
Они живут только в секретах среды на сервере (см. `AGENTS.md`, «Границы и безопасность»).
Сборка проверяется автоматикой на отсутствие секретов (Task 7, VS-0).

## Маршруты

- `/login` — вход через Telegram (OIDC custom-провайдер, ADR-001). Без
  `VITE_SUPABASE_URL`/`VITE_SUPABASE_PUBLISHABLE_KEY` — заглушка с пояснением
- `/` — главная: идентичность, роли с областями, пределы сеанса AUTH-06, выход
  (отзыв собственного сеанса + supabase signOut)
- `/audit` — журнал действий (AUD-01/02): фильтры entity/actor/период, курсорная
  пагинация; область записей фильтрует сервер (председатель — всё,
  администратор — свои дома, техадмин — технические события). Меню — для
  chairman/administrator/tech_admin
- `/emulation` — эмуляция ролей (пилот, HLD 10.8): тестовые персоны (is_test),
  старт/завершение сеанса; создание персон — техадмин, роли персонам назначает
  председатель. В режиме эмуляции вверху баннер с именем персоны и пометкой
  журналирования (действия пишутся в журнал с реальным актором и персоной)

Защита маршрутов: `<Authenticated>` Refine проверяет сессию Supabase; профиль,
роли и область при каждом запросе проверяет функция api (PDP на сервере).
401 от API — автоматический выход на `/login`.

Прямые ссылки на маршруты работают: Cloudflare Pages раздаёт `index.html`
на неизвестные пути (SPA-fallback).

## Фильтры и колонки списков

На `/tasks` доступны поиск по номеру, названию и инструкции задания,
исполнитель (включая «Без исполнителя»), состояние и диапазон дат создания.
Фильтры применяются вместе к таблице и доске сразу; границы периода включают
полные выбранные дни по времени Алматы. Некорректный порядок дат показывает
предупреждение. Варианты исполнителей строятся по ID доступных загруженных
заданий, включая сотрудников, чьи полномочия уже прекращены (WRK-11, ROL-02e).
Фильтры сохраняются при переключении вида и фоновом обновлении, сбрасываются
при смене персоны. Фильтрация ограничена текущей загрузкой API (до 100 заданий).

Колонка «Обращение» содержит номер и ссылку на прямое исходное обращение,
если сервер разрешил управление им; назначение на задание не открывает
обращение, жалобы и черновики (ADR-013). Для общего задания без прямого
обращения и при отсутствии доступа отображается «—». Список заданий теперь
содержит `linked_request: {id, number} | null`; функция `api` должна быть
обновлена вместе с кабинетом. Старая версия API оставляет колонку пустой.

В таблицах заданий и обращений кнопка «Колонки» позволяет скрывать поля и
восстанавливать весь набор. Номер остаётся видимым для открытия карточки.
Общий `useTableColumns` сохраняет скрытые колонки в localStorage раздельно:
`columns.tasks` и `columns.requests`. Новые колонки видны по умолчанию;
недоступное или повреждённое хранилище не мешает работе таблиц. Настройка
применяется только к таблице, состав карточек доски не меняет.

## Слои кода

- `src/lib/env.ts` — публичные переменные среды (VITE_*); без env — режим заглушки
- `src/lib/supabase.ts` — клиент Supabase Auth (ADR-001)
- `src/lib/api.ts` — REST-клиент `/v1`: Bearer, разбор ошибок LLD-03 §1.1
- `src/lib/telegram-auth.ts` — изолированный вызов Telegram OIDC (риск R3:
  точная форма custom-провайдера проверяется при настройке среды)
- `src/lib/auth-provider.ts` — authProvider Refine (login/check/logout/getIdentity)
- `src/lib/identity.ts` — хук идентичности и флаги ролей для меню
- `src/pages/` — вход, главная, журнал, эмуляция; `src/layouts/` — каркас с баннером

## Фильтры обращений

В кабинете фильтр здания передаёт `building_id` в `/v1/requests/search`.
Сервер отбирает обращения до пагинации, включая обращения по помещениям и общему
имуществу здания, с сохранением области доступа. При изменении контракта поиска
нужно обновить функцию `api` вместе с интерфейсом: старый API игнорирует новый фильтр.

## VS-2: реестр и регистрация

- `/registry` — здания (дома), четыре типа помещений, предварительные карточки и связи. «Восстановить Telegram» требует анкету с нового аккаунта и основание проверки; прежние сеансы отзываются.
- `/registrations` — очередь анкет/споров, фильтр состояний, подтверждение, уточнение, отказ. Явный выбор проверенной карточки сохраняет её ID; автоматического объединения по телефону нет.
- `/invites` — приглашения в пределах домов, без раскрытия токенов.
- `/registry-import` — XLSX-шаблон, загрузка, полный отчёт с подсвеченным Excel, атомарный commit, экспорт со спецправом IMP-05.
- `/time-rules` — версии сроков регистрации; право TIM-03 проверяет сервер.

Тестовый домен определяется по person.is_test, а не только по наличию эмуляции. В симуляторе выберите сценарий `registration`: это тот же модуль, который обрабатывает webhook. Работа с настоящим Telegram OIDC и доставкой требует настроенных внешних провайдера/бота; воспроизводимые тесты используют вымышленные данные.

Регион передаётся только вызовам прикладного API через `forceFunctionRegion`;
адрес Supabase Auth не меняется. После изменения переменной пересоберите кабинет.
При недоступности выбранного региона автоматического перенаправления нет: смените
регион или очистите переменную и пересоберите. Замеры — ADR-005.


## Навигация кабинета

Структура меню и критерии проверки: [план перестройки навигации](../../tasks/plan-admin-navigation.md).
«Пользователи» разделены на жителей и сотрудников по действующим служебным назначениям; здания, помещения и привязки находятся в «Помещениях». Настройки обращений доступны в «Настройки», уведомления разделены на ошибки доставки и личные предпочтения. Видимость пунктов сохраняет прежние ограничения ролей, сервер проверяет PDP на каждом запросе.

## Обновление данных

Кнопок ручного обновления списков нет. Данные загружаются при переходе на экран,
повторном выборе текущего пункта меню, перезагрузке браузера (включая стандартные
горячие клавиши), а также раз в минуту в видимой вкладке. Возвращение во вкладку
запускает обновление сразу. Общий хук `usePageRefresh` сохраняет состояние страницы,
не запускает параллельные фоновые запросы и снимает подписки при уходе с экрана.
Открытые формы и черновики сохраняются; настройки файлов с несохранённым вводом
не перезаписываются, фоновое чтение расписания обновляет только запуски и исполнителей.

## Структура страниц

Все внутренние страницы используют `PageLayout`: заголовок (и переключатель вида),
строка действий, блок фильтров, рабочая область. Отсутствующие секции не создают
пустых строк. Кнопки создания и общие операции находятся над фильтрами; действия
над записью и сохранение формы остаются в контексте записи или формы. Экран входа
сохраняет самостоятельную композицию. Проверка: `tasks/plan-admin-page-layout.md`.

Карточка обращения группируется компонентом `DetailSection`: информация, свойства,
действия по процессу, переписка, история состояний. Текущая просрочка (FLOW-04)
показывается отдельным предупреждением сверху. При ошибках доставки сотруднику
доступна кнопка журнала внизу, без перечисления одинаковых ошибок.

В информации об обращении инициатор — `author_person_id`, даже если обращение
зарегистрировал сотрудник (REQ-01). API карточки возвращает `author_name` для
инициатора и разрешённых сообщений; переписка показывает имя курсивом перед текстом.
Внутренний канал и ограниченные сообщения продолжают фильтроваться сервером.

Предупреждение и красная дата показывают текущую просрочку: неполученный первый
ответ или незавершённое выполнение. После ответа его прошлая задержка исключается;
на этапе подтверждения срок выполнения уже не считается действующим. Исторический
`overdue_since` сохраняется на сервере, но сам по себе не включает предупреждение.


### Начало работы по обращению

Форма «Начать работу» выбирает любого действующего сотрудника ОСИ независимо от роли и домов, будущий срок и редактируемое описание работы (ROL-02e, ADR-013). Операция `/v1/requests/:id/start-work` идемпотентно создаёт обязательное задание и переводит обращение в работу в одной транзакции (REQ-05, WRK). Ошибка откатывает обе записи и уведомления. Задание ожидает явного принятия исполнителем. Для вопроса/жалобы инструкция по умолчанию предлагает подготовить ответ; переписка не копируется.

Карточка обращения содержит связанные задания со ссылками `/tasks?task=<uuid>`. Карточка задания содержит обратную ссылку `/requests?request=<uuid>`, если сервер подтвердил право управления обращением. В URL передаётся только технический идентификатор.


## Управление сотрудниками

`/users/staff` использует общий PageLayout, карточку CardDrawer и формы ActionPanel по образцу Обращений. Можно выбрать зарегистрированного пользователя, назначить/сменить роли, прекратить полномочия и повторно назначить бывшего сотрудника. Формы содержат перечень ролей и причину; дома, сроки и специальные переключатели отложены.

Наследование и временная область всего ОСИ определены в ADR-014. Сервер разрешает управление только младшими ролями другого человека; системные роли управляются отдельно. Карточка показывает прямые и наследуемые роли, открытые обязанности и историю. Изменения ролей создают личное уведомление в Telegram, включая снятие последней роли. Профиль жителя сохраняется. При конфликте версии и ошибке фонового чтения ввод не теряется.

Контракты и проверки: [ADR-014](../../docs/decisions/014-staff-role-management.md), [приёмка](../../docs/staff-management-acceptance.md).
