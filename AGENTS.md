# AGENTS.md

Правила и контекст для кодинг-агентов (Codex, Zed, Cursor, Claude Code и др.). При значимых изменениях проекта обновляйте этот файл: если правило не записано здесь, для агента его не существует.

## О проекте

Система ОСИ ЖК «Мунар Тау»: Telegram-бот для жителей и исполнителей + веб-кабинет для администраторов и председателя. Одна ОСИ (~45 трёхэтажных домов, ~600 квартир, коммерческие помещения, паркинги, кладовки): обращения жителей с жизненным циклом, задания исполнителям, общие аварии, платные работы с ручной сверкой оплат Kaspi, публикации и документы, опросы, отчётность, декларативные регламенты времени, журнал действий. Заменяет процесс «всё через WhatsApp» на управляемый: номера, состояния, сроки, эскалации.

Фикс маршрутизации (17.10.2026): слэш-команды не отдаются активному сценарию на съедание шагами ввода — из шага выбора помещения `/help`, `/status`, `/cancel` и неизвестные команды работают как обычно (раньше любая отвечала «Выберите номер из списка»); `/notifications` подключён к `notificationStep`; у сотрудника `/help` и `/start` — глобальные выходы. Нажатия inline-кнопок (`callback_query`) должны доходить до вебхука: `setWebhook` без `allowed_updates` сохраняет прежний фильтр Telegram (не сбрасывает его), поэтому `tools/scripts/set-bot-webhooks.ts` задаёт `["message","callback_query"]` явно и проверяет это в `getWebhookInfo`; признак залипшего фильтра — кнопки не работают, а текстовые команды живы.

UX бота — срез C «Уведомления с точкой входа» и ввод дат визитов реализован в `feature/bot-ux-notice-entry` (поверх среза B; закрывает пункты 2–4 UX-предложения 17.10.2026 для обоих ботов): `dispatchNotices` прикрепляет к последней части уведомления кнопку «Открыть обращение/задание» с `callback_data` = точной команде (`/request З-26-00001`, `/task З-26-1`); номер резолвится по `request_id`/`task_id`, разметку отправляет бот из `notification.bot` (ADR-009), сводки и рассылки без карточки остаются текстом. URL-кнопки t.me в уведомлениях не введены (внутри чата callback эквивалентен и не требует username бота в env).

Команды в текстах без `<code>` — Telegram сам делает `/команды` кликабельными (bot_command не распознаётся внутри code-блока). `/status` показывает анкетные данные (имя, помещение, роль, причина). Guard `/register`: при действующей анкете (pending_review/need_clarification/approved/rejected) показывает актуальный статус вместо мастера; отозванная/спорная анкета не мешает новой регистрации; `/add` и `/start invite_*` проходят мимо guard сознательно. `/delete` (PRV-02, LLD-02 §2.9) подаёт запрос администратору, а не удаляет данные: подтверждение кнопкой (`/delete confirm`), домен `domains/privacy/service.ts` (`submitPrivacyRequest`), таблица `privacy_request` (миграция `20261018120000_bot_ux_delete_request.sql`), PDP-действие `privacy.request`, необязательные рассылки (publication, work.report, request.status) отключаются сразу, история остаётся в append-only `audit_log`; уведомление — администраторам зданий жителя (fallback заместитель→председатель) в worker-бот; кабинетного экрана рассмотрения пока нет. Исключение: префикс «Сигнал проверяется / Сигнал тексерілуде» в хранимом `public_text` инцидента (VS-7, поле администратора) — правится отдельно при изменении схемы показа. Выбор языка анкеты — единственная осознанно сдвоенная реплика (язык ещё не выбран).

## Два Telegram-бота (ADR-009)

Каналы доставки разделены (реализовано в `feature/two-bots`; ADR-009): бот жителей `@munar_tau_bot` (`TELEGRAM_BOT_TOKEN`) — анкета регистрации, обращения, уведомления жителям; бот сотрудников `@munar_tau_worker_bot` (`TELEGRAM_WORKER_BOT_TOKEN`) — задания исполнителей (WRK), файлы заданий, служебные уведомления (эскалации анкет REG-14, назначения, дежурство и аварии, недоставки важных сообщений). Бизнес-правила REQ/WRK/REG не менялись, PDP и аудит общие.

- Webhook различает ботов по суффиксу пути: `/bot-webhook/resident` и `/bot-webhook/worker` (базовый путь — жители, совместимость); у каждого бота свой секрет `TELEGRAM_WEBHOOK_SECRET` / `TELEGRAM_WORKER_WEBHOOK_SECRET`. Регистрация — `tools/scripts/set-bot-webhooks.ts`.
- Дедупликация `bot_inbound` — по ключу `(bot, update_id)`; `notification`, `notification_digest_item`, `request_upload_job` хранят колонку `bot` (по умолчанию `resident`). Атрибуция событийная — по целевому получателю: председатель-собственник получает анкетные статусы в бот жителей, а задания — в бот сотрудников. Миграция — `20261017130000_two_bots.sql`.
- Файловый обработчик в `jobs` требует оба токена: без `TELEGRAM_WORKER_BOT_TOKEN` загрузка файлов не выполняется. Дайджест уходит в worker-бот только если все его элементы worker. `bot_dialog` остаётся общим по `telegram_user_id` (cross-bot сценарии самовосстанавливаются через `/cancel`).

## Технологический стек

VS-4 реализован в `feature/vs-4-tasks-common-work` (PR #13; план — `tasks/plan-vs-4.md`, проверки — `docs/vs4-acceptance.md`). Общий домен tasks обслуживает кабинет, бота и эмуляцию: локальные/общие задания, принятие/отказ, запрос остановки, пауза/возобновление, неизменяемые отчёты и проверка доказательств, доработка, визиты, найденные проблемы, версии методичек и ручной запуск шаблонов. Исполнитель видит только свои задания без переписки обращения. Совмещение ролей не разрешает принять собственный отчёт (ROL-02d), в том числе после смены назначения. Файлы заданий имеют owner_type=task, аудиторию internal и после включения в отчёт неизменяемы. Общая работа завершается явно; возврат возобновляет её с сохранением прежней даты в истории. До возврата общего задания надо отозвать ожидающие подтверждения связанных обращений. ADR-006: сервер формирует снимок принятых обязательных отчётов; подтверждение/административное закрытие сверяет его с текущим комплектом. Внутренние файлы автоматически жителю не раскрываются. Отмена родителя прекращает только его незавершённые задания; отменённый обязательный объём не считается выполненным, после апелляции требуется явная замена. Обязательный акт блокирует приёмку до VS-8; платный старт — до VS-6; таймеры и расписание — VS-5. Длинные Telegram-уведомления ставятся в очередь нумерованными частями с отдельными устойчивыми ключами. Миграции проверяются только на Sydney; демонстрационный стенд не обновлён.

## Границы и безопасность (не нарушать)

- Секреты — только в секретах среды на сервере: токен бота, OIDC Client Secret, Supabase service-role key. Никогда в коде, статической сборке, клиентских переменных Vite, логах, коммитах
- В браузере допустим только publishable key — при серверных проверках прав и RLS
- Персональные данные не попадают в URL, статические файлы и журналы сборки
- Проверка полномочий — всегда на сервере (PDP), для чтения и записи, при каждом защищённом запросе; отозванная роль блокирует следующий запрос даже при действующем токене. Редактируемые пользователем метаданные — не источник полномочий
- Облачный прототип — на вымышленных данных; реальные персональные данные и рабочие секреты туда не переносятся, preview не подключается к рабочей среде
- Рабочая среда — self-hosted Supabase в Казахстане; выбор провайдера отложен до развёртывания и не блокирует разработку
- `.env*` не коммитится

## Конвенции

- SQL-параметры сериализованного JSON передавайте с явным `$n::text::jsonb`: postgres.js иначе может повторно сериализовать строку после определения типа параметра. Чтение исторических JSON-строк аудита поддерживается без переписывания append-only журнала.
- Общие модули обязательны: бот и кабинет работают по одним правилам, правам и данным (ADR-003)
- Идемпотентность повторов: повторная доставка webhook и повтор фонового задания не создают повторную бизнес-операцию
- Тесты (по HLD, раздел 19): модульные — переходы состояний, PDP, интервалы TIM, валидация импорта; интеграционные — против dev-БД Supabase (`TEST_DATABASE_URL`): транзакции, идемпотентность миграций, append-only `audit_log`, RLS-заслон, SQL-репозитории; тесты очищают данные (truncate + сид, сохраняя конфигурационные time_rule/time_rule_version) — только dev-проект, не пилот/prod; безопасность — сценарии раздела 7 матрицы прав, отсутствие секретов и персональных данных в статической сборке
- Тестовая инфраструктура: `source/supabase/migrations` → symlink на `source/db/migrations` (единый источник миграций для `db push` и интеграционных тестов), `source/supabase/seed.sql` → `db/seed/identity_dev.sql` (сид после `supabase db reset` локально)
- Проверки ролей — через средство эмуляции (тестовые персоны), без реальных жителей
- Долго живущие процессы создают клиент postgres.js (`createDbClient`) с ограничением пула и таймаутом простоя (`max`, `idleTimeout`): на стенде Supabase `max_connections = 60`, каждый изолят Edge Function держит собственный пул, и соединения без `idle_timeout` исчерпывают слоты (500 при отказе в коннекте, инцидент 2026-10-17). Для клиентов, закрываемых после вызова (`bot-webhook`, `jobs`), достаточно `max: 2`; lock-соединению интеграционных тестов передавайте `maxLifetime: 0, idleTimeout: 0`, чтобы advisory lock не рвался

## VS-5: регламенты, уведомления и расписания

VS-5 реализуется в `feature/vs-5-regulations-notifications` (PR #14) поверх завершённого VS-4. Общий TIM сохраняет версии/график уже запущенных сроков; task_accept/task_escalation поставляются без придуманных нормативов, назначение требует явной настройки. Состояния заданий не меняются автоматически. Регулярные запуски хранят снимок методички и области, отдельную запись на каждую дату и неизгладимый пропуск даже при отмене между тиками. Отозванные полномочия автора блокируют создание; после пяти ошибок — dead, повтор требует действующих прав.

NTF повторно проверяет доступ при материализации и отправке; task_id не раскрывает снятое назначение. Прежний исполнитель получает только личный факт снятия без ссылки на карточку. Ошибка назначения создаёт одну задачу контакта и уведомляет резерв (заместитель/председатель), без автоматической смены исполнителя. История расписания проверяет фактическую область каждого задания. Подробные проверки и зависимости последующих срезов — docs/vs5-acceptance.md. Демонстрационный Frankfurt этим PR не обновляется.

TIM-02: `timing/contracts.ts` — неизменяемый каталог v1 согласованных событий/погашения/действий. Новая версия регламента сохраняет `params.contract`; обычный POST принимает только длительность/график и не разрешает менять обработчик. Старые версии разрешаются в исходный контракт v1 без переписывания истории. Новая семантика требует нового каталога с совместимым исполнением старой версии.
