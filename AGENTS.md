# AGENTS.md

Правила и контекст для кодинг-агентов (Codex, Zed, Cursor, Claude Code и др.). При значимых изменениях проекта обновляйте этот файл: если правило не записано здесь, для агента его не существует.

## О проекте

Система ОСИ ЖК «Мунар Тау»: Telegram-бот для жителей и исполнителей + веб-кабинет для администраторов и председателя. Одна ОСИ (~45 трёхэтажных домов, ~600 квартир, коммерческие помещения, паркинги, кладовки): обращения жителей с жизненным циклом, задания исполнителям, общие аварии, платные работы с ручной сверкой оплат Kaspi, публикации и документы, опросы, отчётность, декларативные регламенты времени, журнал действий. Заменяет процесс «всё через WhatsApp» на управляемый: номера, состояния, сроки, эскалации.

## Статус

VS-0 «Фундамент» выполнен: монорепозиторий `source/` (npm workspaces: `core`, `admin`), ядро env/ошибок, каркас БД, заглушки функций с защитой, SPA-каркас кабинета, CI с условным деплоем.

VS-1 «Доступ и аудит-скелет» выполнен (ветвь `feature/vs-1-access-audit`): PDP (Actor, `can()`, реестр действий с privileged), сеансы AUTH-06 (12 ч / 30 мин бездействия, отзыв), append-only `audit_log` с чтением по областям (AUD-02), каркас эмуляции (тестовые персоны is_test, сеансы эмуляции, симулятор через общий ScenarioRegistry), функция api с полным конвейером (CORS → JWT → профиль → сеанс → Actor → PDP → обработчик → аудит), кабинет: Telegram-вход (OIDC), журнал, эмуляция, баннер режима; сиды identity_dev.sql. TOTP и ROL-06 — за пределами среза.

VS-2 «Реестр и регистрация» реализован в `feature/vs-2-registry-registration` (приёмка/проверки — `tasks/plan-vs-2.md`, инструкция — `docs/vs2-acceptance.md`, уточнения — ADR-004). Общие домены registry/registrations: четыре типа помещений, несколько собственников, предварительные карточки без Telegram, анкета/приглашения/споры/восстановление Telegram, атомарный Excel-импорт с постоянными ID, экспорт со спецправом и аудитом. Минимальный TIM-контур: 72/48 календарных и 12/36 рабочих часов, версии графика, эскалация без автоматической выдачи доступа/закрытия спора. Бот и эмуляция используют общий сценарий `registration`; webhook дедуплицируется транзакционно, jobs доставляет устойчивые уведомления ограниченными порциями. Кабинет: реестр, очередь, приглашения, импорт/экспорт и регламенты.

VS-2: `registration.is_test` обязателен даже до person_id, `premises.is_test` отделяет тестовые помещения; тестовые уведомления имеют канал simulator и не отправляются наружу. Нельзя менять общую структуру зданий из эмуляции. Спор ссылается на конкретный `connection_id`; старая регистрация не отзывает новую связь/собственность. Подтвердивший связь сохраняется при обычном редактировании. OIDC связывает уже подтверждённый profile по `auth.identities(provider='custom:telegram',provider_id)`, без пользовательских metadata. При восстановлении архивируется старый profile и отзываются прикладные сеансы, сохраняются person/история/назначения. TOTP и настройка внешнего OIDC/бота остаются отдельными гейтами пилота; merge — после согласования PR.

VS-3 «Обращения и переписка» реализован в `feature/vs-3-requests-messaging` (план — `tasks/plan-vs-3.md`, приёмка — `docs/vs3-acceptance.md`, ADR-006). Общий домен requests: приватные черновики, идемпотентная отправка и сообщения, version/409, FSM, аудитории resident/internal, совместный доступ с синхронным отзывом при прекращении связи, снимки результата, оценки с историей. Согласовано 17.10.2026: вопросы/жалобы проходят до закрытия; передача результата работы включается только с проверками заданий VS-4. `work_execution_required` не сбрасывается сменой вида после начала работ. Содержимое жалоб/переписки не копируется в общий аудит.

VS-3: upload-url возвращает адрес Edge API с окном 5 минут, загрузка требует Bearer и PDP; complete отдельно проверяет Storage. Бакеты files-resident/files-internal приватны. 20 МиБ (20 971 520 байт), до 10 файлов на сообщение; согласованные форматы — ADR-006, настройки в кабинете могут сужать этот набор. Передача Telegram-файлов — устойчивая очередь request_upload_job; уведомление об успехе только после сохранения. Тестовые уведомления — simulator. Общий лимит API: 100 запросов/мин на реальный профиль в PostgreSQL.

Очищающие интеграционные тесты разрешены только на Sydney `fuwsmewtmxmzttwkbdex` через session pooler (5432). Global setup удерживает session advisory lock `(814733,3)` на весь прогон отдельным соединением; CI дополнительно сериализует integration. Старые CI-запуски без этой блокировки не запускать одновременно с локальными тестами. Миграции и сид передаются в PostgreSQL файлами (simple protocol), каждый файл атомарен. Frankfurt не используется для тестовых миграций и очистки.

Инфраструктура тестирования подключена: модульные (Vitest: `core` + `admin`; Deno: `functions`), интеграционные против dev-БД Supabase (`TEST_DATABASE_URL` в `source/.env.local` из `tools/scripts/env.example.txt`; идемпотентные миграции, truncate + сид между тестами, SQL-репозитории, RLS-заслон, append-only), джоба `integration` в CI временно закомментирована на время разработки. Среда разработки — облачный dev-проект Supabase (вымышленные данные, HLD §20). Далее — срезы VS-2…VS-9 (см. `docs/hld.md`, раздел 27). Команды — в разделе «Команды».

Кабинет развёрнут на Cloudflare Pages (2026-10-16, [ADR-002](docs/decisions/002-admin-cloudflare-pages.md)): Pages-проект `osi-admin`, адрес `https://osi-admin.pages.dev`; развёрнута сборка ветви `feature/vs-1-access-audit`, в статике только публичные переменные (`VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`). Автодеплой из CI заработает после добавления секретов репозитория: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `CF_PAGES_PROJECT`. Вход через Telegram OIDC ещё не настроен (провайдер Supabase + BotFather): пошаговая инструкция — [docs/setup-telegram-oidc.md](docs/setup-telegram-oidc.md); до настройки вход завершается ошибкой на стороне Supabase Auth.

## Технологический стек

VS-4 реализован в `feature/vs-4-tasks-common-work` (PR #13; план — `tasks/plan-vs-4.md`, проверки — `docs/vs4-acceptance.md`). Общий домен tasks обслуживает кабинет, бота и эмуляцию: локальные/общие задания, принятие/отказ, запрос остановки, пауза/возобновление, неизменяемые отчёты и проверка доказательств, доработка, визиты, найденные проблемы, версии методичек и ручной запуск шаблонов. Исполнитель видит только свои задания без переписки обращения. Совмещение ролей не разрешает принять собственный отчёт (ROL-02d), в том числе после смены назначения. Файлы заданий имеют owner_type=task, аудиторию internal и после включения в отчёт неизменяемы. Общая работа завершается явно; возврат возобновляет её с сохранением прежней даты в истории. До возврата общего задания надо отозвать ожидающие подтверждения связанных обращений. ADR-006: сервер формирует снимок принятых обязательных отчётов; подтверждение/административное закрытие сверяет его с текущим комплектом. Внутренние файлы автоматически жителю не раскрываются. Отмена родителя прекращает только его незавершённые задания; отменённый обязательный объём не считается выполненным, после апелляции требуется явная замена. Обязательный акт блокирует приёмку до VS-8; платный старт — до VS-6; таймеры и расписание — VS-5. Длинные Telegram-уведомления ставятся в очередь нумерованными частями с отдельными устойчивыми ключами. Миграции проверяются только на Sydney; демонстрационный стенд не обновлён.

Закреплён ADR; менять только через новый ADR:

| Область | Выбор | ADR |
| --- | --- | --- |
| Серверный код | TypeScript, Supabase Edge Functions: webhook бота, общие бизнес-модули бота и кабинета | [ADR-003](docs/decisions/003-edge-functions-and-environments.md) |
| Состояние и фон | Диалоги, очередь и задания — в PostgreSQL; обработчики по расписанию (отдельный постоянно работающий процесс не принят) | ADR-003 |
| Данные и Auth | Supabase: PostgreSQL, Auth (Telegram OIDC; TOTP для привилегированных ролей после пилота), закрытое Storage | [ADR-001](docs/decisions/001-telegram-auth.md), ADR-003 |

Отклонено: NestJS, самодельный обмен подтверждения от бота на сеанс, email/пароль как основной вход (см. «Альтернативы» в ADR).

## Команды

**Временное правило разработки (решение пользователя 17.10.2026): интеграционные тесты, включая будущие, сохраняются в Git, но не запускаются автоматически и не запускаются агентом без отдельного явного запроса пользователя.** Обычный `npm run test:integration` завершает работу без подключения к БД. Ручное включение: `RUN_INTEGRATION_TESTS=1 npm run test:integration`; интеграционная джоба GitHub CI закомментирована до отдельного согласования. Не считать пропущенные проверки пройденными. Вернуть автоматический запуск только по согласованию. Ограничения Sydney, session pooler и advisory lock сохраняются. Модульные/Deno-тесты, lint, typecheck, build и secret-scan продолжают выполняться.

Все команды для кода выполняются из `source/` (там `package.json` workspaces). Node ≥ 22 (см. `source/.nvmrc`), Deno 2 (для функций).

| Действие | Команда |
| --- | --- |

Интеграционная джоба `integration` временно закомментирована в CI (2026-10-17): долгий прогон и дедлоки при параллельных запусках; запуск только по явному запросу — `RUN_INTEGRATION_TESTS=1 npm run test:integration` из `source/` при настроенном `TEST_DATABASE_URL`. До настройки секретов (R3) деплой фактически не выполняется.

## Границы и безопасность (не нарушать)

- Секреты — только в секретах среды на сервере: токен бота, OIDC Client Secret, Supabase service-role key. Никогда в коде, статической сборке, клиентских переменных Vite, логах, коммитах
- В браузере допустим только publishable key — при серверных проверках прав и RLS
- Персональные данные не попадают в URL, статические файлы и журналы сборки
- Проверка полномочий — всегда на сервере (PDP), для чтения и записи, при каждом защищённом запросе; отозванная роль блокирует следующий запрос даже при действующем токене. Редактируемые пользователем метаданные — не источник полномочий
- Облачный прототип — на вымышленных данных; реальные персональные данные и рабочие секреты туда не переносятся, preview не подключается к рабочей среде
- Рабочая среда — self-hosted Supabase в Казахстане; выбор провайдера отложен до развёртывания и не блокирует разработку
- `.env*` не коммитится

## Конвенции

- SQL-параметры сериализованного JSON передавайте с явным `$n::text::jsonb`: postgres.js иначе может повторно сериализовать строку после определения типа параметра. Чтение исторических JSON-строк аудита поддерживается без переписывания append-only журнала.
- Общие модули обязательны: бот и кабинет работают по одним правилам, правам и данным (ADR-003)
- Идемпотентность повторов: повторная доставка webhook и повтор фонового задания не создают повторную бизнес-операцию
- Тесты (по HLD, раздел 19): модульные — переходы состояний, PDP, интервалы TIM, валидация импорта; интеграционные — против dev-БД Supabase (`TEST_DATABASE_URL`): транзакции, идемпотентность миграций, append-only `audit_log`, RLS-заслон, SQL-репозитории; тесты очищают данные (truncate + сид, сохраняя конфигурационные time_rule/time_rule_version) — только dev-проект, не пилот/prod; безопасность — сценарии раздела 7 матрицы прав, отсутствие секретов и персональных данных в статической сборке
- Тестовая инфраструктура: `source/supabase/migrations` → symlink на `source/db/migrations` (единый источник миграций для `db push` и интеграционных тестов), `source/supabase/seed.sql` → `db/seed/identity_dev.sql` (сид после `supabase db reset` локально)
- Проверки ролей — через средство эмуляции (тестовые персоны), без реальных жителей

## Рабочий процесс

- Для каждой новой задачи — отдельная ветка от актуального `main` (`feature/…`, `docs/…`, `chore/…`); несвязанные изменения не смешивать в одной ветке
- После выполнения задачи — PR в `main` с описанием изменений и результатами проверок; PR остаётся на согласование, мерж — только после одобрения пользователем
- Реализация по срезам VS-0…VS-9 с учётом зависимостей (`docs/hld.md`, раздел 27); не забегайте вперёд без задачи пользователя
- Каждый срез завершается проверкой критериев из раздела 15.2 спецификации и раздела 8 модели процессов

## Регион API (ADR-005)

Демонстрационная БД Supabase размещена в `eu-central-1`. При сборке кабинета задавать
`VITE_SUPABASE_FUNCTION_REGION=eu-central-1`: API передаёт регион через
`forceFunctionRegion`, чтобы последовательные SQL-запросы AUTH-06/PDP/AUD-02
не ходили между континентами. Для self-hosted переменная пустая. Права и сеансы
не кэшировать ради скорости. Замеры и порядок смены региона — ADR-005.

## VS-5 — работа в отдельной ветке

VS-5 разрабатывается в `feature/vs-5-regulations-notifications` поверх завершённого VS-4; план — `tasks/plan-vs-5.md`, фактическая приёмка — `docs/vs5-acceptance.md`.

- `work_schedule` меняется отдельно от длительностей; создаются новые версии операционных рабочих правил. Начатые таймеры остаются на прежних версиях; `time_rule_version` append-only.
- Правовые границы и правовое основание не редактируются обычным API настройки; новая версия сохраняет снимок `legal_basis`.
- `notifyPerson` пишет `notification.requested` в outbox в той же бизнес-транзакции. `dispatchNotices` материализует уведомления, `sendNotifications` повторно проверяет доступ; синхронные ответы webhook через `notifyTelegram` сохраняют существующую очередь. Вызов enqueueNotice не означает доставку.
- Обязательность NTF-03 определяется видом события, не клиентским флагом. На окончательную ошибку важной доставки создаётся одна `notification_followup`; фиксация результата звонка не меняет согласия/состояния обращения.
- Дайджест сохраняет локальный день и отсечку состава, выполняется порциями. Проверка аудитории повторяется перед доставкой; пустое сообщение не создаётся. Тестовые сообщения остаются в simulator.

## VS-5: регламенты, уведомления и расписания

VS-5 реализуется в `feature/vs-5-regulations-notifications` (PR #14) поверх завершённого VS-4. Общий TIM сохраняет версии/график уже запущенных сроков; task_accept/task_escalation поставляются без придуманных нормативов, назначение требует явной настройки. Состояния заданий не меняются автоматически. Регулярные запуски хранят снимок методички и области, отдельную запись на каждую дату и неизгладимый пропуск даже при отмене между тиками. Отозванные полномочия автора блокируют создание; после пяти ошибок — dead, повтор требует действующих прав.

NTF повторно проверяет доступ при материализации и отправке; task_id не раскрывает снятое назначение. Прежний исполнитель получает только личный факт снятия без ссылки на карточку. Ошибка назначения создаёт одну задачу контакта и уведомляет резерв (заместитель/председатель), без автоматической смены исполнителя. История расписания проверяет фактическую область каждого задания. Подробные проверки и зависимости последующих срезов — docs/vs5-acceptance.md. Демонстрационный Frankfurt этим PR не обновляется.

TIM-02: `timing/contracts.ts` — неизменяемый каталог v1 согласованных событий/погашения/действий. Новая версия регламента сохраняет `params.contract`; обычный POST принимает только длительность/график и не разрешает менять обработчик. Старые версии разрешаются в исходный контракт v1 без переписывания истории. Новая семантика требует нового каталога с совместимым исполнением старой версии.
