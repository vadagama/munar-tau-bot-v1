## Навыки (skills)

В `.agents/skills/<имя>/SKILL.md` лежат проектные навыки — рабочие процессы для типовых фаз работы. Их использование обязательно: выбор навыка — первый шаг любой задачи, до чтения кода и любых правок.

- Каждая задача начинается с обращения к мета-навыку `using-agent-skills` — там карта «задача → навык» и базовые правила поведения (surface assumptions, scope discipline, «verify, don't assume»). Навык вызывается на каждую задачу заново: «уже читал в этой сессии» — не основание пропустить выбор
- Выбранные навыки объявляйте в первом ответе по задаче строкой «Навыки: …»; если ни один не подходит — напишите это явно. Объявление делает пропуск выбора видимым и поправимым
- Навык — это порядок действий, а не справка: шаги по порядку, проверки не пропускать. Обычно задействовано несколько навыков; типовая цепочка: `interview-me` / `spec-driven-development` → `planning-and-task-breakdown` → `incremental-implementation` → `test-driven-development` → `code-review-and-quality` → `git-workflow-and-versioning` → `documentation-and-adrs`
- Привязка к правилам этого документа: ветки/коммиты/PR — `git-workflow-and-versioning`, ADR и документация — `documentation-and-adrs`, приёмка изменений — `code-review-and-quality`, отладка — `debugging-and-error-recovery`, UI кабинета — `frontend-ui-engineering`
- Если среда поддерживает skills нативно — используйте её механизм; в остальных случаях достаточно прочитать `SKILL.md` нужного навыка
- Повторяющийся процесс оформляйте новым навыком: каталог `.agents/skills/<имя>/`, `name` в frontmatter совпадает с именем каталога (lowercase, дефисы), `description` — конкретный и отвечает на вопрос «когда применять»

## О проекте

Система ОСИ ЖК «Мунар Тау»: Telegram-бот для жителей и исполнителей + веб-кабинет для администраторов и председателя. Одна ОСИ (~45 трёхэтажных домов, ~600 квартир, коммерческие помещения, паркинги, кладовки): обращения жителей с жизненным циклом, задания исполнителям, общие аварии, платные работы с ручной сверкой оплат Kaspi, публикации и документы, опросы, отчётность, декларативные регламенты времени, журнал действий. Заменяет процесс «всё через WhatsApp» на управляемый: номера, состояния, сроки, эскалации.

## Управление сотрудниками — актуальный режим (18.10.2026, ADR-014)

- `/users/staff` — StaffPage: выбор зарегистрированного пользователя, перечень ролей и причина; общие PageLayout/DetailSection/CardDrawer/ActionPanel по Обращениям. Статус сотрудника вычисляется по действующим ролям; снятие всех ролей сохраняет person/profile, связи и историю.
- Председатель → администратор → заместитель → исполнитель; заместитель и выше наследуют duty/doc_reviewer/finance. Техадминистратор — отдельная системная роль. Обычное управление — только вниз для другого человека; chairman/tech_admin не назначаются и не снимаются этой формой. Привилегированные изменения запрещены в эмуляции.
- Служебная область временно всё ОСИ, формы домов/сроков/спецправ отложены. Новые назначения бессрочные, старые окна действия проверяются. Наследование и область вычисляются сервером в `pdp/roles.ts` + `buildActorForProfile`; raw-назначения сохраняются отдельно. Финансы следуют finance и старшим; экспорт/регламенты — administrator/chairman. Старые флаги не повышают младшие роли.
- Набор ролей сохраняется атомарно с expected_version, Idempotency-Key, причиной, повторной авторизацией и аудитом. Уведомление `staff.roles` через каталог на ru/kk ставится в outbox в той же транзакции, bot=worker, audience=personal; снятие последней роли не отменяет доставку. Test — только simulator. Старые API назначений также уведомляют пользователя.
- Наследование не отменяет ограничения конкретного объекта, жалоб, финансовой аудитории и собственной приёмки. Открытые обязанности после снятия полномочий остаются управляющим для явной передачи. Эти правила заменяют прежние ограничения области/срока/спецфлагов в старых описаниях ROL.

## Доменные правила (кратко)

Полные формулировки — в требованиях, ADR и приёмках срезов. Здесь — правила, которые чаще всего нарушаются при правках.

**Тестовые данные и эмуляция**

- `registration.is_test` обязателен даже до person_id, `premises.is_test` отделяет тестовые помещения; тестовые уведомления уходят в канал `simulator` и не отправляются наружу
- Общую структуру зданий из эмуляции не менять; здание целиком удаляет только председатель вне эмуляции (при активных аварийных сигналах удаление запрещено). Помещение можно удалить в эмуляции. Удаление каскадное: связи, приглашения и анкеты помещения удаляются, обращения сохраняются без привязки (запись в журнале — `registry.buildings.delete`/`registry.premises.delete`)
- В эмуляции «Житель» — тестовая персона без служебных назначений; доступ к помещениям требует подтверждённых связей. Симулятор показывает inline-кнопки конкретных ответов (подписи из каталога ru/kk) и отправляет их точные команды; постоянное главное меню под диалогом не отображается. Новый ответ получает фокус и автоматически прокручивается в видимую область; при наборе текста фокус не перехватывается. Ответы симулятора отображают разрешённую Telegram-разметку через React-элементы (`TelegramText`), без прямой вставки HTML; экранированный пользовательский текст не превращается в разметку, ссылки ограничены http(s)/tg. Отдельные обходы PDP запрещены.
- Только в активной эмуляции в шапке слева от «Выйти» доступно быстрое переключение тестовой персоны по роли. Список строится по действующим назначениям; выбор меняет всю персону через обычный API сеансов и обновляет идентичность на текущем маршруте без перезагрузки браузера. Страница эмуляции сохраняет фильтр и форму; симулятор сбрасывается только при смене сеанса, чтобы не смешивать диалоги персон. Фоновое чтение списка персон не скрывает таблицу и не сбрасывает симулятор. Остальные страницы при смене персоны загружают данные заново. Выдавать роли через этот список нельзя.
- Снимать роль с тестовой персоны техадминистратор может на странице эмуляции (крестик на теге роли, `POST /v1/emulation/assignments/{id}/revoke` с обязательной причиной): назначение отзывается, при сокращении набора ролей сеансы персоны закрываются, персоне ставится уведомление (в симулятор), всё журналируется с реальным актором. Выдача ролей остаётся у председателя.

**Меню ботов (24.10.2026)**

- REG-01/02: в главном меню жителя кнопка «Регистрация» скрывается при действующем профиле, включая жителей без помещений; для остальных остаётся. Проверка одинакова в Telegram и симуляторе, при `/start` и `/cancel`.
- До отдельного решения скрыты кнопки аварий, публикаций, документов, финансовых отчётов, опросов, инициатив, аварийной службы, анкет на подтверждение и работ/планов; соответствующие команды убраны из справки ru/kk обоих ботов. Обработчики и права сохраняются для последующего включения. Финансовые обязанности и личная работа сотрудников остаются.

**Регистрация и связи**

- POL-02/03 (VS-8, ADR-019): история аудитории начинается с внедрения, прошлое не восстанавливается. Изменяющие право корневые транзакции регистрации/реестра/импорта/эмуляции, bot inbound и registrationStep вызывают `lockAudience` первым запросом, до любых row locks. Вложенные операции используют тот же executor. Прямой SQL с предварительным SELECT FOR UPDATE/LOCK сначала вызывает `audience_clock()`; триггер до DML не исправляет уже обратный порядок блокировок. Опросы также соблюдают gate → строки опроса; серверное время проверяется после ожидания gate. История закрыта RLS и append-only, не входит в административный DTO/экспорт. Временные границы в TypeScript — целые микросекунды PostgreSQL, без округления до Date. Тестовая мета-запись начала истории сохраняется при reset Sydney.
- POL-01/02: открытый опрос не редактируется, голос не следует из служебной роли. Ответ принимает только option_key и expected_version; person/time/mode берутся сервером. Guard БД использует одну отметку времени для срока, даты Алматы и answered_at. Replay возвращает исходный снимок, не восстанавливает участие; после успешного write/replay клиент перечитывает getPoll для текущего included. Персональные варианты/история не входят в общий аудит или административные DTO.
- POL-03: финальный период `[opened_at, closes_at)` использует историю слева от closes_at; отзыв ровно на границе/позже не меняет прежний голос, новый ответ на границе запрещён. Итог и состав участников неизменяемы, участник сохраняет сводку после переезда. Отмена до срока не выдаёт распределение. POL-уведомления несут pollId/pollEvent до финальной доставки; их адресаты не раскрываются журналом ошибок и прямым followup, включая председателя и старые записи с dedup_key `poll.*` без ref.
- Кабинет POL: опубликованные параметры доступны только для чтения; действия следуют серверным can_manage/deadline_passed. После write/replay перечитывается карточка. 409 сохраняет ввод и требует сравнить свежую версию. Смена персоны/ролей и начало формы инвалидируют продолжение фонового refresh. Ручной ввод и быстрые сроки опроса используют Алматы независимо от пояса браузера.
- Бот POL: `/polls` и карточка доступны через общий сценарий webhook/симулятора; запись только в боте жителя. Кнопка несёт nonce и индекс, сервер повторяет PDP и обе версии; личность и сеанс берутся из канала диалога. Длинные варианты показываются полностью перед подтверждением, прежнее подтверждение другого варианта недействительно. Неверный UUID отклоняется до SQL. Отменённые опросы не читают сводку.
- Фон POL-03: после порции закрытия проверяет до 10 открытых опросов с ротацией по отдельному poll_reconciliation.checked_at. Сверка не меняет версию карточки и не рассылает управляющим персональные исключения. При окончательном подсчёте источником остаётся история аудитории, не checkpoint или текущий реестр.
- IDEA-01/03 (VS-8): публикация и этапы независимы. При публикации повторяется текущая аудитория автора; расширение на всё ОСИ — только председатель, общая область администратора этого не заменяет. План хранит основание/сотрудника/срок и конкретную версию решения; общий provider проверяет область, файлы и approved, точная видимость версии проверяется отдельно. Перед реализацией/завершением обязательное решение проверяется снова. Снимок не раскрывается публичным DTO. Обязательность решения не понижается флагом. При переходах неизменные даты берутся из to_jsonb исходной строки БД, новые отметки — точным серверным текстом, без потери микросекунд.




- REG-02a/PRV-02a (21.10.2026, ADR-016): одна действующая основная анкета Telegram без помещения; `/add` — отдельные привязки. Исправление approved хранит `confirmed_draft` и предложение в той же записи, `person/profile` меняются только после одобрения ОСИ; отказ сохраняет прежний доступ. `version` повышается триггером; исправления требуют `expected_version`, управление в кабинете — также причину/Idempotency-Key. Удаление архивирует person/profile, закрывает сеансы, отзывает связи/приглашения/роли, сохраняет обращения/задания/аудит. Chairman/tech_admin предварительно передают защищённые полномочия; обычные менеджеры соблюдают иерархию, техадмин может прекратить обычные роли при удалении. Повторная подача использует ту же основную запись с `reactivating`; одобрение восстанавливает прежние person/profile, роли/связи не возвращает. Исторические дубли `superseded_by` не попадают в очереди/диалоги. Тело сообщения бота не дублирует команды и варианты кнопок.
- «Мои помещения» (`/objects`) показывает жителю только подтверждённые связи (`status='active'`): прекращённые и неподтверждённые связи в списке и в выборе помещения для `/invite` не участвуют (24.10.2026); под анкетой добавлена кнопка «Добавить помещение» (`/add`).

- Анкета-минимум (REG-01, ADR-015, 19.10.2026): `/register` спрашивает только язык, имя, телефон и согласие — дом, помещение и роль не входят. Подтверждение анкеты открывает доступ к обращениям без связи; привязка помещения — отдельной анкетой `/add`. Обращение жителя без помещений адресуется одной строкой (location_text, building_id NULL) и попадает в общую очередь administrator/deputy/chairman с сохранением chairmanOnly; авторство адресных обращений — по действующему профилю, не по связи.
- Очередь строительства здания — `building.construction_phase`, необязательное целое 1–5 (REG-11, 19.10.2026). Редактируется с обычными правами на здание; фильтр есть в подразделе «Здания». NULL — «Не указана». В привязке помещения неверный номер дома открывает подсказку по очередям с кликабельными номерами; NULL — отдельная группа. Выбор house_UUID_token действует только в текущем шаге/канале, старые ссылки не переключают диалог. Excel-шаблон пока без очереди; очередь не влияет на PDP.

- Бот, кабинет и эмуляция работают через общие домены и сценарии (ADR-003); webhook дедуплицируется транзакционно, устойчивые уведомления доставляются ограниченными порциями
- Спор ссылается на конкретный `connection_id`; старая регистрация не отзывает новую связь/собственность; подтвердивший связь сохраняется при обычном редактировании
- OIDC связывает уже подтверждённый profile по `auth.identities(provider='custom:telegram', provider_id)`, без пользовательских metadata; при восстановлении архивируется старый profile и отзываются прикладные сеансы, person/история/назначения сохраняются

**Обращения и файлы**

- Обращения: идемпотентная отправка, version/409, аудитории resident/internal; содержимое жалоб и переписки в общий аудит не копируется
- Файлы: приватные бакеты `files-resident`/`files-internal`, до 20 МиБ и до 10 файлов на сообщение (согласованные форматы — ADR-006); передача Telegram-файлов — устойчивая очередь `request_upload_job`, уведомление об успехе — только после сохранения
- Фото инициатив (VS-8, IDEA-01): owner_type=initiative, только images, до 10 по 20 МиБ с дополнительной file_policy; автор добавляет/исключает до публикации. Подготовка/сохранение/исключение повышают версию подачи; незавершённые фото блокируют публикацию, опубликованный состав неизменяем. discarded_at скрывает файл без удаления истории. Любая запись фото соблюдает gate → initiative → attachment, включая retry/jobs. Telegram-перенос повторяет канонического актора/PDP до скачивания и завершения; тестовые Telegram file_id не передаются наружу (тестовые фото — через кабинет). Миграции фото предшествуют функциям FIL.
- История отчётности (VS-8, REP-06/KPI): события/таймеры и версии запуска append-only; старые границы без доказательств не восстанавливаются. Первый ответ — конкретное содержательное служебное message resident; unknown_response отличается от отсутствия ответа. Срезы/длительности сравнивают целые микросекунды (SQL at::text), а не Date. KPI-02 исключает created_at до запуска даже при поздней регистрации. KPI-01 восстанавливает датированное достижение по объединённым историческим интервалам связей, включая календарные границы без DML; фоновый расчёт использует try-gate и бюджет.
- Операционные отчёты (VS-8, REP-01/02/03): область/режим/жалобы фильтруются до агрегации и повторяются object PDP. Выбранный дом исключает безадресную очередь; работник видит свои задания. Историческое назначение/срок берётся из server report-снимка task_log/incident_log либо доказанного старого значения; отсутствие — unknown. Логи closed→closed/accepted_admin→accepted_admin не меняют дату завершения. Без VS-6 платежи недоступны явно, реальный KPI не показывается в тестовом режиме.
- REP-04/05: `/reports` — ролевые панели; `/mywork` worker всегда фильтруется по текущему исполнителю, `/plans` resident читает только опубликованные работы/планы с publication.read до SQL-пагинации. `report_export_job` фиксирует фильтры, as_of, режим, контекст эмуляции и исходные полномочия; один файл за тик, lease 90 секунд, до трёх попыток, private Storage internal. Рост прав не расширяет снимок, потеря исходной области запрещает весь экспорт. Перед ready/status/download повторяются канонический актор и PDP каждой строки, URL только создателю на 5 минут. Дата запуска KPI append-only, задаётся председателем вне эмуляции с причиной/Idempotency-Key.
- Webhook: `bot_inbound.status=error` допускает атомарную повторную обработку; `processed` остаётся дубликатом. Поздняя диагностическая запись не переводит обработанный update обратно в error.



- Общий лимит API: 100 запросов/мин на реальный профиль (PostgreSQL)

**Задания, инциденты и публикации**

- VS-8 FIN: разрешение относится к неизменяемой версии комплекта и повторно проверяется с действующим председателем и PDP документов перед немедленным/плановым выпуском. Плановый выпуск переавторизует `publication.scheduled_by`, для прежних записей — created_by. Финансовый выпуск не выставляет глобальные `document.published_version_id`/`was_published`: раскрытые версии доступны через `financial_package_document` только собственнику домов конкретного опубликованного выпуска (`documents/financial-grants.ts`). Назначение на задание не открывает другие финансовые версии; карточка, архив и файл используют один контракт видимости версий. Рассылка отбирает действующих собственников, доставка повторяет проверку собственности именно в домах уведомления. Самостоятельная публикация документа — отдельное действие. Выпуск, архив, FIN-04, финансовые уведомления и сценарии ботов подключены.

- Исполнителем задания может быть любой действующий сотрудник ОСИ независимо от роли и закреплённых домов (ROL-02e, ADR-013). Назначение открывает только конкретное задание и его материалы; управление, исходное обращение, финансовые данные и приёмка собственного результата проверяются отдельно. Все списки/записи назначений и расписания используют `tasks/assignees.ts`; отзыв всех служебных полномочий прекращает доступ по назначению.

- Исполнитель видит только свои задания, без переписки обращения; совмещение ролей не разрешает принять собственный отчёт (ROL-02d), в том числе после смены назначения
- Файлы заданий — owner_type=task, аудитория internal, после включения в отчёт неизменяемы; сервер формирует снимок принятых обязательных отчётов и сверяет его при подтверждении (ADR-006); внутренние файлы жителю автоматически не раскрываются
- Общая работа завершается явно, возврат возобновляет её с прежней датой в истории; до возврата общего задания отзывают ожидающие подтверждения связанные обращения
- Отмена родителя прекращает только его незавершённые задания; отменённый обязательный объём не считается выполненным до явной замены; обязательный акт требует настроенного обязательства и точной проверенной версии документа (контур VS-8), платный старт — до VS-6
- Производные связи общего объёма (`incident_work_request`) снимаются через инцидент с дальнейшим маршрутом, ручные связи не удаляются; результат передаётся через проверки VS-4 и не подтверждается за жителя. Документозависимые публикации проверяют конкретные версии оснований, финансовые — также снимок разрешения председателя; исправление требует нового разрешения.

- Кабинет инициатив `/initiatives` (VS-8): очередь/карточка/этапы/история, отдельные вкладки модерации и оспариваний. План выбирает действующего сотрудника через WRK-провайдер и конкретную approved-версию документа; сервер повторяет проверку области/файлов. Все ручные сроки форм интерпретируются в Алматы независимо от зоны браузера. 409 сохраняет ввод и требует перечитать версии; смена персоны/служебных назначений сбрасывает формы и игнорирует поздние ответы.
- MOD-01–03 (VS-8): оригиналы комментариев и причины модерации неизменяемы. Скрытые комментарии исключаются до пагинации; автор сохраняет доступ к своему оригиналу и оспариванию после потери связи. Только председатель оставляет/сокращает/снимает действие; одна открытая жалоба на действие, отдельная append-only история решений и версии обоих объектов. Ограничение проверяется по серверному времени только при подаче инициативы/комментария. Персональные уведомления включают вид решения и срок; чужие ошибки их доставки в общий журнал не попадают.

**Регламенты и уведомления (TIM/NTF)**

- Кабинет FIN использует серверные can_manage/can_approve конкретной карточки. Форма комплекта берёт период/дома/обязательные основания из снимка обязанности; дополнительные приложения сохраняются до явного удаления, смена основания очищает только его прежнее раскрытие. Основной отчёт раскрывается обязательно, служебные основания — только если документ допускает раскрытие и сотрудник выбрал его явно. Публичное пояснение исправления отдельно от служебной причины; 409 сохраняет ввод. Формы, архив, очередь, настройки регламентов, передача и подтверждение размещения подключены. Формы сохраняют ввод при 409 и требуют явно загрузить актуальные условия; повтор того же намерения сохраняет Idempotency-Key, изменение тела создаёт новый. Время размещения вводится явно по Алматы. Бот собственника показывает только выпущенные версии своих домов и раскрытые части; бот сотрудника — доступные обязанности. Каталог строится по опубликованным FIN-снимкам до пагинации, независимо от черновика исправления и общего лимита объявлений.

- VS-8 FIN/NTF: broadcast хранит financial_version_id с составным FK к публикации. financialVersionId сохраняется через outbox, дайджест и notification.event_ref; dispatch и send повторяют собственность в области именно этой версии. Служебная роль не подменяет собственность при доставке массового FIN-уведомления. Файлы бота повторяют доступ версии и приложения, кнопки привязаны к nonce карточки. Test остаётся в simulator; уведомление не является фактом размещения.

- VS-8 FIN-04: обязанность хранит версии финансового регламента и TIM с исходным сроком; передача сотрудников не меняет условия. Размещение подтверждается явно по версии и каналу. Только пригодный текущий выпущенный комплект со всеми исходными каналами закрывает обязанность; старые факты остаются историей. Фоновый `needs_fix` активного комплекта открывает ту же обязанность однократно, без переноса срока. Напоминания дедуплицируются по циклу/получателю; `financialObligationId` повторно проверяет полномочия, дома, ответственного и незавершённость при доставке и доступе к followup. API и кабинет FIN-04 подключены. История показывает номер версии комплекта; статус интерфейса следует ответу сервера, а не факту отправки формы.

- `work_schedule` меняется отдельно от длительностей; начатые таймеры остаются на прежних версиях, `time_rule_version` append-only. Каталог TIM-02 (`timing/contracts.ts`) неизменяем: обычный POST принимает только длительность/график, правовое основание — снимком
- `notifyPerson` пишет в outbox в той же бизнес-транзакции; вызов enqueueNotice не означает доставку, `sendNotifications` повторно проверяет доступ
- Обязательность NTF-03 определяется видом события, не клиентским флагом; на окончательную ошибку важной доставки создаётся одна `notification_followup`
- Регламентные запуски хранят снимок методички и области и отдельную запись на каждую дату; после пяти ошибок — dead. Дайджест — порциями, проверка аудитории повторяется перед доставкой, пустое сообщение не создаётся

**Бот: ответы и уведомления**

- Общая навигация не добавляет «Мой профиль / Регистрация / Помощь» к вопросам ввода: если сценарий не вернул контекстные кнопки, остаётся только «Отменить». Главное меню открывается явно через /start или завершение отмены. Подсказка домов и защита старых ссылок — `docs/bot-house-selection-acceptance.md`.

- «Старт» и `/start` открывают главное меню жителя с кратким описанием бота и кнопками разделов; `/start` с payload сохраняет маршрутизацию приглашений и карточек. «Помощь» (`/help`) открывает справку с группами команд и краткими описаниями на языке профиля; из справки предлагается только «Отменить». «Отменить» (`/cancel`) в жительском боте всегда ведёт в главное меню (как `/start`); в боте сотрудников экраны /start и /cancel совпадают. Справки жителей и сотрудников различаются. Только `help.registration_help` и `help.worker_help` допускают команды в основном тексте; в остальных диалогах управление остаётся кнопками. «/register» при действующей основной анкете и «/status» показывают актуальный статус анкетой: имя, дату регистрации и подтверждённые помещения (либо факт их отсутствия — «Помещения пока не прикреплены»); в `/status` ниже идёт история изменений статуса — датой решения (или подачи), статусом и именем; анкеты привязки помещений и факты привязки/отвязки в историю не входят; кнопки исправления и удаления адресованы только актуальной анкете.


- Согласованное направление интерфейса (21.10.2026): во всех функциях обоих ботов управление — кнопками, текст — основной контекст без дублирования команд и вариантов кнопок. Небольшие наборы (в том числе исполнители) — сразу кнопками; большие перечни обращений и заданий — списком с кликабельным номером (глубокая ссылка на UUID: req_/sreq_/wrk_/stsk_) без ряда кнопок на каждую запись, навигация/фильтры — где они есть в сценарии. Сотрудник создаёт обращение только в кабинете. Спецификация `docs/specs/SPEC-staff-bot-requests.md`, технический план и ADR-017 согласованы; реализация подготовлена в PR #66. План — `tasks/plan-staff-bot-requests.md`, реестр — `tasks/todo-staff-bot-requests.md`, доказательства и ограничения выпуска — `docs/staff-bot-requests-acceptance.md`. Диалоги хранятся в `bot_dialog_channel` по bot/telegram/profile/сеансу; переход между сценариями закрывает временные формы, бизнес-черновики сохраняются. Служебные записи идут через общие REQ/WRK/MSG с nonce формы, версией и повторной проверкой PDP; отметка чтения — только явная кнопка для показанных входящих id. Старые формы нельзя восстанавливать навигацией или использовать для другого объекта. Медиа в текстовых формах жителя/визитов отклоняется с кнопкой возврата; файлы из карточки и служебного compose сохраняют отдельные пути. Перед выпуском обязателен read-only аудит переопределений `audit-bot-button-templates.ts`; сбросы — только append-only через обычный редактор с реальным автором. Именованные файлы — реестр именно этой работы; исторические `tasks/plan.md`/`tasks/todo.md` не заменять.
- Ответы и уведомления — `parse_mode: HTML`, весь пользовательский текст через `esc()`; при отказе разбора 400 — повтор без разметки; каскад отправки: HTML+разметка → без parse_mode с разметкой → совсем без разметки

## Границы и безопасность (не нарушать)

- Секреты — только в секретах среды на сервере: токен бота, OIDC Client Secret, Supabase service-role key. Никогда в коде, статической сборке, клиентских переменных Vite, логах, коммитах
- В браузере допустим только publishable key — при серверных проверках прав и RLS
- Персональные данные не попадают в URL, статические файлы и журналы сборки
- Проверка полномочий — всегда на сервере (PDP), для чтения и записи, при каждом защищённом запросе; отозванная роль блокирует следующий запрос даже при действующем токене. Редактируемые пользователем метаданные — не источник полномочий
- Облачный прототип — на вымышленных данных; реальные персональные данные и рабочие секреты туда не переносятся, preview не подключается к рабочей среде
- Рабочая среда — self-hosted Supabase в Казахстане; выбор провайдера отложен до развёртывания и не блокирует разработку
- `.env*` не коммитится

## Конвенции

- SQL-параметры сериализованного JSON передавайте с явным `$n::text::jsonb`: postgres.js иначе может повторно сериализовать строку после определения типа параметра. Чтение исторических JSON-строк аудита поддерживается без переписывания append-only журнала.
- Общие модули обязательны: бот и кабинет работают по одним правилам, правам и данным (ADR-003)
- Идемпотентность повторов: повторная доставка webhook и повтор фонового задания не создают повторную бизнес-операцию
- Тесты (по HLD, раздел 19): модульные — переходы состояний, PDP, интервалы TIM, валидация импорта; интеграционные — против dev-БД Supabase (`TEST_DATABASE_URL`): транзакции, идемпотентность миграций, append-only `audit_log`, RLS-заслон, SQL-репозитории; тесты очищают данные (truncate + сид, сохраняя конфигурационные time_rule/time_rule_version) — только dev-проект, не пилот/prod; безопасность — сценарии раздела 7 матрицы прав, отсутствие секретов и персональных данных в статической сборке
- Очищающие интеграционные тесты — только на Sydney `fuwsmewtmxmzttwkbdex` через session pooler (5432); global setup держит advisory lock `(814733,3)` на весь прогон отдельным соединением, локальные прогоны не запускать параллельно; CI их не выполняет; Frankfurt для тестовых миграций и очистки не используется; миграции и сид передаются в PostgreSQL файлами (simple protocol), каждый файл атомарен
- Тестовая инфраструктура: `source/supabase/migrations` → symlink на `source/db/migrations` (единый источник миграций для `db push` и интеграционных тестов), `source/supabase/seed.sql` → `db/seed/identity_dev.sql` (сид после `supabase db reset` локально)
- Дрейф схемы ↔ SQL проверяется модульным тестом `core/src/db/schema-drift.test.ts` (гоняется в CI в `npm test`): он собирает схему из миграций и проверяет ссылки `алиас.колонка` во всех SQL-строках core и functions. При дропе/переименовании колонки или таблицы в миграции сначала правьте SQL в коде под новую схему, затем вливайте миграцию — тест не даст сделать это в обратном порядке. SQL, собранный интерполяцией идентификаторов, тестом не покрывается
- Проверки ролей — через средство эмуляции (тестовые персоны), без реальных жителей
- Долго живущие процессы создают клиент postgres.js (`createDbClient`) с ограничением пула и таймаутом простоя (`max`, `idleTimeout`): на стенде Supabase `max_connections = 60`, каждый изолят Edge Function держит собственный пул, и соединения без `idle_timeout` исчерпывают слоты (500 при отказе в коннекте, инцидент 2026-10-17). Для клиентов, закрываемых после вызова (`bot-webhook`, `jobs`), достаточно `max: 2`; lock-соединению интеграционных тестов передавайте `maxLifetime: 0, idleTimeout: 0`, чтобы advisory lock не рвался

## Регион API (ADR-005)

Демонстрационная БД Supabase размещена в `eu-central-1`. При сборке кабинета задавать
`VITE_SUPABASE_FUNCTION_REGION=eu-central-1`: API передаёт регион через
`forceFunctionRegion`, чтобы последовательные SQL-запросы AUTH-06/PDP/AUD-02
не ходили между континентами. Для self-hosted переменная пустая. Права и сеансы
не кэшировать ради скорости. Замеры и порядок смены региона — ADR-005.
