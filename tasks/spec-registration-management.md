# Управление единой анкетой Telegram-аккаунта

Статус: согласовано пользователем 21.10.2026. Дополнение: текст ответов бота не дублирует команды и описания действий, доступных кнопками.

## Цель и основания

Устранить противоречие между `/register`, `/status` и `/fix`: существующая подтверждённая анкета должна быть доступна для исправления. Дать жителю управление собственной анкетой, а председателю, администратору, заместителю и техническому администратору — исправление и удаление анкеты через кабинет. Основания: запрос пользователя от 21.10.2026, REG-01/02/08, PRV-02, ADR-015.

Одна основная анкета относится к одному Telegram-аккаунту. Анкеты привязки помещений `/add` — отдельные заявки; они не считаются повторной основной регистрацией. Обращения, связи и служебные назначения не должны терять владельца из-за исправления персональных данных.

## Текущее поведение и причина

- `source/core/src/bot/registration.ts`: `/register` обнаруживает подтверждённую анкету и предлагает `/fix`, но `/fix` выбирает только pending_review/need_clarification/rejected. `/edit` тоже исключает approved.
- `source/core/src/domains/registrations/service.ts`: оба пути исправления запрещают approved. Создание новой анкеты в `submitRegistration` не проверяет наличие основной анкеты аккаунта; проверка только в диалоге не гарантирует уникальность.
- `source/admin/src/pages/registrations.tsx`: есть решения проверки, но нет действий исправления/удаления.
- `/delete` сейчас создаёт запрос администратору по PRV-02. Прямое удаление с прекращением доступа требует согласовать изменение этого правила.

## Требуемое поведение

1. `/register` при существующей основной анкете показывает её актуальное состояние и действительные действия. Отказ или уточнение исправляются в той же записи; подтверждённая анкета также доступна для исправления.
2. `/status` согласован с `/register` и `/fix`. Для анкеты-минимум отсутствие помещения нормально; сообщение объясняет, что помещение добавляется через `/add`.
3. Житель исправляет собственные имя и телефон; язык остаётся согласованным с профилем. Исправление не создаёт новую person/profile и не меняет Telegram-идентичность. Изменения подтверждённой анкеты проходят повторную проверку ОСИ. До положительного решения в person/profile действуют прежние подтверждённые сведения и прежний доступ; отказ в изменениях не отменяет ранее подтверждённый доступ. Предлагаемые изменения хранятся отдельно от действующих сведений, в той же основной анкете. Повторная подача заменяет предложение с проверкой версии, а не создаёт другую основную анкету.
4. В кабинете председатель, администратор, заместитель и технический администратор могут исправлять и удалять анкеты с серверной проверкой прав и области доступа. Исполнитель самостоятельно чужими анкетами не управляет. Операции требуют причины, защиты от повторного выполнения, проверки конкурентного изменения и аудита; тестовые данные остаются изолированными.
5. Защита от повторной основной регистрации находится в общем домене и обеспечивается при конкурентных запросах на уровне БД. Повторная отправка возвращает существующую анкету либо понятный конфликт; новую основную анкету не создаёт. `/add` продолжает работать для разных помещений.
6. Перед введением ограничения существующие дубликаты выявляются отдельно. Выбор основной записи и обработка исторических записей сохраняют связь с person/profile, согласия, решения и аудит; автоматическое уничтожение старых данных исключено. Правило выбора согласуется после обследования структуры данных.
7. Удаление жителем требует явного подтверждения. Удаление сотрудником требует причины и проверки полномочий. При выполнении удаления закрывается доступ к боту и кабинету, отзываются прикладные сеансы, прекращаются действующие связи и служебные полномочия; история обращений и аудит сохраняются. Запоздалые callbacks, открытые сеансы и задания очереди не должны восстанавливать доступ. Физическое уничтожение персональных данных и обязательной истории остаётся отдельным рассмотрением по PRV-02. Системные ограничения chairman/tech_admin не обходятся через удаление анкеты; при необходимости передача защищённых полномочий выполняется существующим отдельным порядком.
8. Новые сообщения и кнопки добавляются через каталог ru/kk, пользовательские значения экранируются. Бот, API и симулятор используют общий домен.

## Стек, расположение и стиль

Существующий TypeScript/Supabase PostgreSQL/Edge Functions, React + Ant Design. Новые зависимости не требуются.

- Общие правила: `source/core/src/domains/registrations/`, проверки прав — `source/core/src/pdp/`.
- Диалог: `source/core/src/bot/registration.ts`, тексты — `source/core/src/templates/catalog/`.
- Кабинет: `source/admin/src/pages/registrations.tsx`, общие PageLayout/CardDrawer/DetailSection по правилам проекта.
- API: существующие обработчики `source/functions/`; миграции — `source/db/migrations/`.
- Тесты — рядом с доменом и ботом, интеграционные проверки — по существующей конфигурации Vitest.

Сохранять стиль проекта: транзакции через `deps.db.transaction`, SQL с параметрами, доменные `ApiError`, аудит в бизнес-транзакции. Пример существующего ограничения:

```ts
if (!row) throw new ApiError("NOT_FOUND");
```

Для интеграционных тестов нужна существующая тестовая БД; рабочая облачная БД для них не используется. Перед реализацией уточнить доступные средства запуска по README и конфигурации.

Приёмка:

- Сценарий из обращения пользователя: approved → `/register` → `/status` → `/fix` позволяет исправить ту же анкету.
- Отказ, уточнение и ожидающая проверки анкета исправляются без создания дубля.
- Две одновременные подачи основной анкеты одного Telegram дают одну основную запись; повтор завершения старого диалога тоже не создаёт дубль.
- Отдельные привязки двух помещений через `/add` не блокируются ограничением основной анкеты.
- Данные person/profile, роли и история после исправления согласованы с выбранной политикой проверки.
- Четыре разрешённые роли управляют анкетами в разрешённой области; житель и исполнитель не изменяют чужие анкеты. Проверить прямые API-вызовы, эмуляцию и тестовую изоляцию.
- Удаление выполняется по согласованной политике, подтверждается явно, сохраняет аудит и историю; повторный запрос безопасен.
- В браузере проверить действия кабинета, отображение ошибок, сохранение формы при фоновом чтении; в симуляторе — ru/kk и команды кнопок.

## Границы

Всегда: серверный PDP, транзакционная целостность, существующие процессы REG/PRV, аудит без копирования персональных сведений в общий журнал, регрессионные тесты.

Согласовано пользователем 21.10.2026; изменение архитектуры данных оформить ADR при необходимости. После согласования обновить требования, жизненный цикл и AGENTS.md в части изменившихся правил.

Не делать: физическое удаление истории обращений/аудита, слияние людей по совпадению телефона, отключение `/add`, обход PDP, работа с реальными анкетами в рамках тестирования.

## Решения пользователя от 21.10.2026

1. Удаление закрывает доступ к боту и кабинету, прекращает связи и служебные полномочия с сохранением истории обращений и аудита.
2. Исправления подтверждённой анкеты проверяет ОСИ; прежний доступ сохраняется до решения.

## Уточнение границ удаления

Прекращение доступа отделено от уничтожения данных: доступ закрывается при выполнении удаления, а решение о физическом удалении/сохранении персональных данных остаётся в PRV-02. Открытые обязанности после снятия полномочий сохраняются управляющим для явной передачи, по действующим правилам ADR-014. Принятые ограничения: запреты обычного снятия chairman/tech_admin сохраняются и для удаления анкеты; интерфейс объясняет необходимость отдельной передачи защищённых полномочий.

Интеграционные тесты против облачной БД запускаются только по отдельному явному запросу (AGENTS.md); в этой задаче не запускались. SQL проверен локально без облачных данных. Итоговые решения и повторная подача после удаления — ADR-016.
