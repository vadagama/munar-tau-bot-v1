# Обращения сотрудников в боте — технический план

Дата: 21.10.2026. Статус: проект плана на согласование.
Основание: [спецификация](../docs/specs/SPEC-staff-bot-requests.md),
согласована сообщением пользователя «Дальше делай» после PR #66.
Код, SQL и настройки сред на этом этапе не изменяются.

## 1. Размещение и границы

План и задачи ведутся в именованных файлах по конвенции AGENTS.md и примеру
`plan-registration-management.md`. Реестр этой работы —
[todo-staff-bot-requests.md](todo-staff-bot-requests.md).
Исторические `plan.md`/`todo.md` VS-0 не заменяются.

Одна возможность: обработка существующего обращения сотрудником через бот.
Базовые изменения транспорта и кнопочных путей нужны также прежним сценариям;
они не добавляют новых бизнес-функций регистрации, аварий или публикаций.
Создание обращения сотрудником остаётся только в кабинете.

План включает предложенный [ADR-017](../docs/decisions/017-staff-bot-request-interaction.md).
Его статус — «предложено»: согласование этого плана должно включать выбор
хранения диалогов и отметок чтения. Реализация начинается после согласования.

## 2. Что подтверждено кодом

| Основа | Следствие для реализации |
| --- | --- |
| `bot/inbound.ts`: worker обрабатывает задания/инциденты; `req_` — только resident | Добавить служебную маршрутизацию, сохранив прежние команды жителя |
| `bot_dialog`: одна строка на Telegram-пользователя; SQL прямо в нескольких сценариях | Изолировать контекст по боту через общий модуль и перевести всех читателей/писателей |
| `domains/requests/service.ts`: `listRequests`, `getRequest`, переходы и редактирование | Переиспользовать общий домен; не вызывать HTTP собственного кабинета из бота |
| Список сейчас ограничен 100 строками и имеет собственную сортировку | Новые фильтры и размер страницы выполнять в SQL; прежние вызовы сохраняют прежнее поведение |
| `request.assigned_admin_person_id` уже существует | «Сопровождаемые мной» не требует нового назначения или роли |
| `tasks/start-request-work.ts` — атомарный старт; `tasks/assignees.ts` — кандидаты | В диалоге подтверждения использовать существующую операцию и повторную проверку исполнителя |
| `bot/request-files.ts` для обращения задаёт `bucket/channel=resident` | Нельзя включать внутренние вложения сотрудника без явного выбора аудитории |
| `getRequest` читает всю переписку/историю; отметок чтения в найденных модулях нет | Нужны ограниченные страницы материалов и персональный учёт прочитанного |
| `telegram-text.tsx` открывает все разрешённые ссылки во внешней вкладке | Для собственных ссылок симулятора нужен внутренний обработчик с обычным серверным PDP |
| Справка и часть функций, например настройки уведомлений, возвращают только текст | Нужна инвентаризация и завершение кнопочных путей, удаления текста команд недостаточно |
| `inbound.ts` передаёт ключ `telegram:<update_id>` | Для новых операций ключ должен включать бота и идентификатор формы; номера update двух ботов независимы |

## 3. Контракты и размещение

Все пути ниже — относительно `source/`; новые имена — целевое размещение,
а не утверждение о наличии файлов.

### Контекст диалога

Предлагается новая таблица `bot_dialog_channel` с ключом `(bot, telegram_user_id)`
и общим модулем `core/src/bot/dialog.ts`. Старый `bot_dialog` остаётся без
изменений как снимок для отката. В новый контекст сохраняются профиль, версия
формата, сценарий, шаг, объект, версия объекта, nonce формы и навигация.
В эмуляции также проверяется идентичность текущего сеанса.

Все функции получают явный `BotKind`; его нельзя выводить из роли человека.
Нет значения worker по умолчанию для общего resident-сценария. Изменение профиля,
сеанса или несовместимой версии формата очищает только временную форму.
Для двух запросов одного бота используются блокировка строки и общий executor
бизнес-транзакции. Другой бот имеет другую строку блокировки.

При переключении версии функции начинают пустой временный диалог с понятным
сообщением при попытке продолжить старый шаг. Данные регистрации, сохранённые
черновики обращений, сообщения, задания и загруженные материалы не удаляются.
Неподтверждённый ввод старой формы не переносится: определять бота по старому
общему состоянию неоднозначно. Это явный компромисс выпуска.

### Команды и глубокие ссылки

Служебное пространство команд — `/staffrequests` и `/staffrequest`;
resident `/requests` и `/request` сохраняются. Короткие операции интерфейса
используют `/sr...` с непрозрачным nonce, объект и параметры хранятся на сервере.
Финальные callback-строки проверяются на лимит 64 байта.

Ссылка номера: `https://t.me/<worker_username>?start=sreq_<uuid>`;
старые `req_<uuid>`/`wrk_<uuid>` сохраняют назначение. Username берётся из
конфигурации/существующего источника, не из входящего пользовательского URL.
Ссылка только читает карточку. В симуляторе собственная ссылка преобразуется
в обычный вызов сценария `staff-requests`; чужие ссылки не становятся командами.

### Очереди и карточка

Общий сервис списков принимает необязательный служебный режим, подборку,
статус/дом/период/поиск, размер страницы и курсор. Служебный режим требует
`request.manage`, а не только авторского доступа. Личные черновики не входят.
Для отсутствующего дома нужен явный фильтр, отличный от «Все дома».
Прежние вызовы resident и кабинета без новых параметров сохраняют контракт.

Новый ответ страницы — записи и признак/курсор продолжения; запрос читает
`pageSize + 1` после ограничения прав, фильтров и сортировки. Бот берёт 10.
Нельзя выбрать первые 100 старым методом и отфильтровать/разбить их в боте.
Сортировка: текущая просрочка, дата регистрации, id; курсор привязан к фильтрам.
Это живая очередь: при изменениях между страницами состав может сдвигаться,
возврат перечитывает выдачу, не обещая снимок всей очереди.

`staff-requests.ts` координирует диалог; рендеринг — отдельный модуль, бизнес-правила
остаются в доменах. Доступные действия учитывают PDP, FSM, авторство отчёта,
незавершённые обязательства и зависимости VS-6/VS-8. Наличие кнопки не заменяет
повторную серверную проверку при записи. Открытие карточки не отмечает переписку
прочитанной и не изменяет сроки.

Страницы переписки/истории/файлов и связанные задания читаются через общие
сервисы с ограничением аудитории до пагинации. API получает тонкие обработчики
для этих операций и новых фильтров; переработка интерфейса очередей кабинета
в эту задачу не входит.

### Чтение и причины внимания

Предлагается `request_message_read` с ключом `(person_id, message_id)`.
Подтверждаются только показанные пользователю сообщения жителя из resident-канала,
разрешённые текущим PDP и не ограниченные к дальнейшему раскрытию.
Имена, текст, телефон и прочие персональные данные в отметку не копируются.
Новая таблица закрыта для прямого доступа anon/authenticated.

Чтобы не считать прочитанной ещё не доставленную Telegram-страницу, предлагается
кнопка «Отметить прочитанным» на странице переписки. Она подтверждает только
идентификаторы показанной страницы, сохранённые сервером в контексте формы.
Это уточнение UX для согласования плана: само открытие раздела не снимает
непрочитанное. Новое параллельно пришедшее сообщение остаётся непрочитанным.
Повтор кнопки безопасен; состояние общее для человека, а не для отдельного бота.
Исторические входящие сообщения без отметок считаются непрочитанными;
молчаливой массовой отметки при выпуске нет.

Очередь «Требуют внимания» использует общие вычисляемые причины:
текущая просрочка неисполненного обязательства, непрочитанное входящее,
ожидающий проверки отчёт, запрос отмены, неразрешённый отказ исполнителя.
Отказ определяется журналом назначения и текущим состоянием задания:
назначение/отмена устраняет этот признак, простой просмотр — нет.
Точный предикат проверяется на историях decline → assign и reassign → assign;
неоднозначную запись нельзя молча считать отказом.

### Запись, файлы и уведомления

Форма имеет стабильный ключ операции, сохраняемый до подтверждения. Ключи
включают bot и nonce, не только update_id. Повтор того же callback возвращает
результат без новой операции; отдельное осознанное действие получает новый ключ.
Актуальные Actor, версия обращения/задания и кандидат проверяются перед записью.

Файл сотрудника принимается только внутри явной формы сообщения с выбранным
каналом. Загрузка создаёт подготовленное вложение и устойчивое задание передачи;
автоматическая отправка сообщения из `queueRequestFile` для этой формы запрещена.
Предпросмотр включает аудиторию и состояния файлов; финальная отправка разрешена
после сохранения выбранных файлов, лимиты — ADR-006. Отмена не публикует материалы;
подготовленные неотправленные файлы обслуживаются существующей политикой очистки.

Уведомления используют каталог, outbox и существующую повторную проверку доступа.
В worker-уведомления добавляется переход к служебной карточке, в resident —
к карточке жителя. Операции и постановка уведомлений атомарны. Тестовые доставки
не выходят из simulator. Привилегированные операции AUTH-03 остаются в кабинете.

## 4. Порядок реализации

| Этап | Задачи | Проверяемый результат |
| --- | --- | --- |
| A. Безопасный контекст | T01–T05 | Resident и worker не смешивают ввод; прежние сценарии продолжают работать |
| B. Найти и прочитать | T06–T10 | Очереди, кликабельные номера, карточка, поиск и возврат, включая симулятор |
| C. Переписка и внимание | T11–T14 | Чтение по страницам, персональные отметки, две аудитории, безопасные файлы |
| D. Организовать работу | T15–T18 | Взятие на рассмотрение, задания, переназначение и проверка отчётов |
| E. Завершить процесс | T19–T22 | Остальные переходы, свойства обращения, результат и уведомления |
| F. Все прежние кнопочные пути | T23–T26 | Регистрация, обращения жителя, задания, инциденты и настройки доступны кнопками |
| G. Приёмка | T27–T29 | Сквозной сценарий, права, ошибки и документация, PR без слияния |

Зависимости и точные проверки — в реестре задач. Изменения общих контрактов,
миграции, маршрутизация и финальная сборка выполняются последовательно.
Параллельные агенты этим планом не требуются. После каждых 2–3 задач — контроль
регрессий, пользовательского пути и соответствия спецификации.

Ранние срезы допустимы как небольшие PR, но промежуточная поставка не считается
реализацией всей спецификации. Новые пункты меню не публикуются до готовности
их обработчиков, каталогов и симулятора. Общая изоляция диалогов выпускается
только после перевода всех обращений к состоянию, включая очистку при удалении
профиля. Частичное переключение читателей и писателей не допускается.

## 5. Проверки и выпуск

Focused-команды и проверки указаны у задач, все запускаются из `source/`.
Итог: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`,
`deno task check`, `deno task lint`, `deno task test`, проверка сборки на секреты.
Ревью — по `code-review-and-quality`, до слияния; слияние только по одобрению.

SQL/PDP, пагинация и конкурентные операции требуют интеграционной приёмки
на Sydney. Очищающий запуск — только по отдельному явному запросу:
`RUN_INTEGRATION_TESTS=1 npm run test:integration`. Его отсутствие фиксируется
как непроверенная часть приёмки, не заменяется зелёными фейками.
Браузерная приёмка — симулятор с тестовыми персонами; Telegram-ссылки и
кнопки — реальные клиенты на вымышленных данных. Эти проверки ещё не выполнены.

Порядок выпуска: совместимые добавляющие миграции/RLS → миграции шаблонов и
кнопок → согласованное переключение функций/симулятора → smoke → меню Telegram.
Старые таблицы и версии шаблонов не удаляются. Откат возвращает предыдущие
функции/меню; SQL-структуры сохраняются. Миграции/деплой не выполняются в рамках
подготовки плана. Для реального выпуска применяются правила сред AGENTS.md.

## 6. Риски и решения

| Риск | Мера |
| --- | --- |
| Незаметная публикация внутреннего файла жителю | Явный канал формы; отдельные проверки bucket/owner; никаких автоматических сообщений при приёме медиа |
| Смешение ввода между ботами или сеансами эмуляции | Ключ bot + Telegram, профиль/сеанс в контексте; тесты пересечения и отмены |
| Утечка через список или поиск | Единый серверный предикат доступа до LIMIT, одинаковая ошибка для неизвестного и недоступного номера |
| Повтор задания из callback либо коллизия update_id | Стабильный ключ bot + nonce, повторная авторизация, транзакционный старт |
| Прочитанным становится новое или не показанное сообщение | Отметки по точным id страницы и явное подтверждение, конкурентный тест |
| Большое число старых непрочитанных после выпуска | Явно описано в ADR; чтение страниц снимает признак постепенно, остальные причины не затрагиваются |
| Существующее переопределение шаблона продолжает показывать команды | Инвентаризация default и активных override; только новые append-only версии с причиной и аудитом, без удаления истории |
| SQL-фейки пропускают ошибку прав или курсора | Проверка реальным PostgreSQL по правилам среды; незапущенные проверки остаются открытыми |

Открытых вопросов по бизнес-границам нет. На согласование вынесены технический
план, ADR-017 и уточнение кнопки отметки прочитанного; полные задачи подготовлены,
реализация не начата.
