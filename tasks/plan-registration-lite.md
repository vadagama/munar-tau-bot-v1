## Сценарий (финальный, согласован с пользователем)

**Этап 1 — анкета (проверка администратором; дом, помещение и роль не спрашиваются):**

```
/register
Выберите язык анкеты: ru
Ваше имя и фамилия: Олег Краснов
Телефон (например: +7 777 777 16 76): +7 777 777 16 76
Согласие на обработку данных: да
→ анкета pending_review без premises_id и роли
```

После подтверждения — person+profile **без связей**; доступ к обращениям открыт, квартирные данные закрыты.

**Обращения жителя без привязанных помещений** (шаг «Мои помещения / Общее имущество» пропускается, адрес — одной строкой, без распознавания):

```
/newrequest → вид (Заявка на работу / Вопрос / Жалоба)
Напишите адрес одной строкой (например: дом 107/2, кв 11): Дом 107/2, кв 40
Опишите проблему: …
Добавите файл/фото для подтверждения проблемы? [да] [нет]
да → (медиа) → «Хотите добавить ещё?» [да] [нет] → …
нет → проверка (вид · адрес · описание · файлы) → [Отправить]
```

**Обращения жителя с привязкой** — путь Фазы A без изменений (Мои помещения → список; Общее имущество → в доме/на территории), но выбор дома переведён с списка всех домов на текстовый ввод с автопроверкой (T8). Файловый цикл добавляется в оба пути (T7).

**Этап 2 — привязка в любой момент** существующим `/add`: номер дома текстом с автопроверкой → тип → номер (автопроверка, как сейчас) → роль → согласие → проверка связи администратором. Приглашения REG-03/04 не меняются.

**Принятые решения:** обращение без дома видят администратор (и заместитель, как в текущей связке ролей) и председатель; привязки сотрудников к домам пока нет, служебная область — вся ОСИ. Авторство обращения без помещения требует подтверждённого профиля, а не связи.

## Architecture Decisions

- Анкета хранится без `premises_id` и `role` (nullable); дом в анкете не хранится — маршрутизация анкет и так не зависит от дома (`registrations/routing.ts`, `reviewers` дом игнорирует).
- Одобрение анкеты = доступ без связи; привязка — только через `/add` (существующий механизм, отдельная анкета на помещение). Кабинетную привязку (старые B3/B4) не делаем.
- PDP: для обращений с `premises_id IS NULL` — `active_author` = действующий профиль автора; видимость для сотрудников при `building_id IS NULL` — chairman/administrator/deputy с сохранением правила `chairmanOnly`.
- Адрес обращения сохраняется как написан (`location_text`), без распознавания дома; `building_id` остаётся NULL — обращения идут в общую очередь (уточняет администратор).
- Реплики — только через каталог шаблонов (ADR-010/011), append-only, ru+kk; миграция кнопок предшествует деплою функций.
- Права и аудит — только сервером (PDP, `recordAudit`, Idempotency-Key через общий конвейер API).

## Risks and Mitigations

| Риск | Влияние | Митигация |
| --- | --- | --- |
| Эскалации/джобы падают на анкетах и обращениях без дома | High | Явные ветки null в R1.1/R2.2 + unit-тесты на null |
| Расширение видимости PDP раскроет chairmanOnly-жалобы администраторам | High | Отдельный тест на chairmanOnly + null в R2.2 |
| Адресные обращения скапливаются в общей очереди без маршрутизации | Med | Осознанное решение пользователя; уточнение администратором; точка пересмотра в ADR-015 |
| Регресс старых черновиков обращений и анкет | Med | Тесты совместимости в R1.2/R2.3; старые черновики открываются без ошибок |
| Новые шаги ломают симулятор/эмуляцию (кнопки, фокус) | Med | Кнопки только из каталога; simulator-тесты в каждой фазе |
| Деплой шаблонов/кнопок перед функциями | Med | Порядок деплоя — в описании PR (правило ADR-010/011) |
| Файловый цикл конфликтует с фоновой загрузкой файлов | Med | Синхронная реплика «Хотите добавить ещё?» отделена от асинхронного «Файл сохранён»; тесты request-files |
