# Аудит UI/UX экранов Telegram-ботов ОСИ «Мунар Тау»

Дата: 2026-10-18. Охват: оба бота (житель `@munar_tau_bot`, сотрудник `@munar_tau_worker_bot`) — интерактивные сценарии, тексты ошибок, доменные уведомления, дайджест, меню команд, кнопки-точки входа. Источник — код `source/core/src/bot/*`, `source/core/src/locales/*`, `source/core/src/domains/*` (уведомления), `source/tools/scripts/set-bot-commands.ts`.

Критерии: понятность для жителя/исполнителя, отсутствие технической информации, умеренность эмодзи, полнота ключевых данных (дата, состояние, адрес), единый язык подачи, паритет «кнопка ↔ подсказка».

Приоритеты: **P1** — мешает пользоваться/читать; **P2** — заметное неудобство; **P3** — шлифовка.

## 2. Сквозные правила (корень большинства находок)

1. **Любая дата в реплике/уведомлении — только через `fmtDate`/`fmtInterval`** (`bot/text.ts`). Сейчас в пяти доменах даты подставляются как сырой `Date`/ISO-строка. Это источник примеров владельца «Sat Oct 17 2026 19:37:00 GMT+0000» и `2026-10-17T19:37:00.000Z`.
2. **Любой статус — через словарь подписей** (`locales/*`). Сырые `proposed/confirmed/no_show`, `Услуга: 1` (если это код) выглядят как отладка.
3. **Ссылки на объекты — по номеру или кнопкой; UUID не показывать.** UUID допустим в `callback_data`, но не в видимой строке.
4. **Кнопка вместо подсказки; подсказка не дублирует кнопку.** Если реплика несёт `buttons`, текстовая строка «/command — действие» избыточна. Для эмуляции (кнопок не видно) — дописывать эквиваленты в `replyText()`, а не в Telegram-текст.
5. **Эмодзи: только заголовки разделов справки и экстренная строка.** В пунктах-командах эмодзи не нужны (команды Telegram кликабельны), в reply-меню — по одному на кнопку (норма).
6. **Уведомления — только `LocalizedNotice`** (`{ru, kk}`). Остатки строковых литералов в `tasks/*` нарушают срез B.

## 3. Поместные находки

### 3.1. Бот жителей

**/start (первый экран) — P1.** Любой новый пользователь получает полную справку из ~25 строк (18 эмодзи) + reply-меню. Предложение: короткое приветствие (что умеет бот, 2–3 строки), кнопка «📝 Зарегистрироваться» (если профиля нет), полная справка остаётся на `/help`. Место: `bot/registration.ts` (финальный `return help()` для `/start`), `bot/inbound.ts`.

**/help — P1 (пример владельца №1).** 7 эмодзи в заголовках + 11 в пунктах. Предложение — сохранить заголовки разделов, убрать эмодзи из пунктов:

```
🏛 ОСИ ЖК «Мунар Тау»

Анкета
• /register — регистрация
• /status — статус анкеты
• /fix — исправить после уточнения
• /delete — запрос на удаление анкеты

Объекты
• /objects — мои помещения
• /add — добавить помещение

Обращения
• /newrequest — новое обращение
• /requests — мои обращения

Доступы собственника
• /invite — пригласить жильца
• /accesses — выданные доступы

Настройки
• /notifications — уведомления и язык

🚨 В экстренной ситуации и при непосредственной угрозе жизни звоните 112!
```

То же для `workerHelp` (17 эмодзи → только заголовки). Место: `bot/help.ts`.

**Шаги анкеты: «Тип помещения», «Ваша роль» — P1 (пример №2).** `numbered()` добавляет «1. », а элемент уже содержит `${i+1}. ` → «1. 1. Собственник». Убрать внутренний префикс: `numbered(ROLE_OPTIONS.map((r) => label(roleLabels, r, lang)))`. Место: `bot/registration.ts` L57–64.

**/status — P3.** Строки анкет читаемы (жирное состояние, данные, причина), но: нет даты подачи; подсказка «/fix — исправить…; /edit НОМЕР — заполнить заново» дублирует кнопки «Исправить». Оставить одну строку-подсказку только для случаев без кнопок.

**/objects — P2.** Подсказка `/invite НОМЕР tenant|resident|other` требует английских слагов от жителя. Предложение: при `/invite НОМЕР` спрашивать роль кнопками («Арендатор / Проживающий / Другое») или принимать русские слова. Место: `bot/registration.ts` L227.

**/pending, /accesses — P3.** Кнопки «Подтвердить N» есть; строка из трёх команд (`/approve…/reject…/dispute…`) — шум; оставить короткую: «Для отказа или спора: /reject НОМЕР причина».

**/newrequest — выбор помещения — P3.** Одна реплика несёт четыре инструкции (выбор, общее имущество с синтаксисом «дом КОД описание», «черновик сохраняется», «/requestcancel — назад»). Разгрузить: главную инструкцию оставить, синтаксис общего имущества — по подкоманде/помощи.

**/requests — P1 (пример №4).** Сейчас: `1. З-26-00003 — Нужно уточнение\nНе закрывается крышка` + хвост «/request НОМЕР — открыть обращение; /newrequest — новое». Нет даты, текст сливается со статусом, подсказка — шум (владелец: «это всё не нужно»). В `rows` уже есть `created_at` (`select r.*`). Предложение:

```
1. З-26-00003 · Нужно уточнение · 15.10
   Не закрывается крышка
2. З-26-00004 · Новая · 17.10
   Жалоба на освещение
```

+ построчные inline-кнопки «Открыть» (паритет с `/tasks`, где они уже есть), подсказку убрать; пагинация — кнопкой «Далее». Место: `bot/request-text.ts` (`requestListText`).

**/request — карточка — P1.** Сейчас: номер — статус, текст, последние 3 сообщения (без дат и подписей), сводка результата, «Версия результата: N», строка «Действия: …». Предложение:

```
З-26-00003 · Нужно уточнение
Квартира 1/12 · создано 15.10 18:40

Текст: Не закрывается крышка

Сообщения:
17.10 10:05 — Администратор: Уточните, какой подъезд.

Результат работ: … (когда есть)
[Действия — кнопками по состоянию]
```

Убрать «Версия результата» (версия нужна только команде `/confirm` — она уже зашита в кнопку), сообщения подписать датой и автором-ролью. Место: `bot/request-text.ts` (`requestCardText`).

**/result — P2.** «версия результата 2. Отчёт 1/2: З-26-1, версия 1» — технические версии. Достаточно: «Отчёт 1 из 2 · задание З-26-1», текст работ, результат, ограничения. «Следующий отчёт: /result НОМЕР 2» оставить (листание без кнопок).

**/visits — P1.** Статусы сырым enum: «17.10 14:00 – 17.10 16:00 — proposed». Ввести подписи: предложен/согласован/не состоялся/нет доступа/перенесён (двуязычный словарь рядом с `locales/requests.ts`). Там же в `/task` (карточка задания). Места: `bot/requests.ts` L129–131, `bot/tasks.ts` L155–157.

**/sendrequest — P2.** «Первый ответ до … (Алматы). Начало обработки: … (Алматы). Вне графика немедленной обработки нет…». «Начало обработки» — внутренний термин TIM; суффикс «(Алматы)» — технический шум (все даты бота и так алматинские). Предложение: «Первый ответ до 18.10 19:30. Экстренных круглосуточных вызовов бот не заменяет: в опасной ситуации звоните 112» (формулировку согласовать с TIM-правилами). Место: `bot/requests.ts` L337–347.

**/notifications — P3.** Экран настроек читаем; пример изменения содержит служебный параметр `ru`. Пояснить человеческим языком: «…и язык: ru/kk».

**/incidents, /incident, /emergency — P2.** «Сигнал не подтверждает выезд» — жаргон; «Авария: /emergency КОД_ДОМА — …» — синтаксис в первой же строке. Разделить: человекочитаемое назначение + пример отдельной строкой. Карточка `/incident` не показывает «следующее обновление» (а рассылка показывает) — выровнять состав.

**/publications, /publication — P1.** Список публикаций отдаёт сырые UUID: `/publication 3f2c…` — житель не может ни набрать, ни понять. Решение: построчные inline-кнопки с `callback_data = /publication <id>` (49 байт — помещается в лимит 64), в тексте — только заголовки и даты. То же для `/signals` (`/acceptsignal <uuid> <version>` — служебный бот, но то же правило) и `/publication`-карточки для `work_report` (хвост «/workproblem <uuid> КОД_ДОМА | описание» → кнопка + подсказка коротко). Место: `bot/incidents.ts`.

**Уведомления-точки входа (срез C) — ок.** Кнопки «Открыть обращение/задание» работают; предложить распространить на публикации (кнопка вместо UUID-команды).

### 3.3. Бот сотрудников

**/help — P1.** Аналогично жителю: убрать эмодзи из пунктов, оставить в заголовках.

**/tasks — ок.** Построчные кнопки есть; состояние подписано. P3: в строке три поля через «—» — можно «·».

**/task — P2.** Строка «Методичка: версия 2, Автор, 17.10.2026 18:00» — версия нужна (WRK-08), автор и время — служебное; достаточно «Методичка v2 (действует с 15.10)». Статусы визитов — сырые enum (см. 3.1). Суффикс «(Алматы)» убрать.

**Мастер отчёта — P2.** Время выполнения строго `ГГГГ-ММ-ДД ЧЧ:ММ`. Исполнитель у объекта; предложить «сейчас» (по умолчанию), а также принять `17.10 15:30`; строгий формат оставить совместимостью. Сообщения шагов — короткие и понятные, ок.

**/problem — P2.** Синтаксис «место|описание|номера файлов» с пайпами в подсказке `/help` — технично; в диалоге (без аргументов) спрашивать по шагам, как сделано для визитов.

**/noaccess — P3.** Семантика номера визита неочевидна («/noaccess НОМЕР причина» — номер визита из карточки); уточнить подсказку: «номер визита из карточки задания».

**Служебные уведомления** — см. таблицу 3.2 (UUID, только ru). Эскалации `sweepTaskTimers` («Задание N не принято…») — ок по форме.

### 3.4. Ошибки и мелочи

- `NOT_FOUND`: «Проверьте номер: /requests, /tasks» — жителю показывается `/tasks`, которого в его боте нет. Развести тексты по ботам. Место: `bot/bot-errors.ts`.
- `CONCURRENT_MODIFICATION`: «Объект уже изменён…» — в контексте обращения лучше «Обращение уже изменено…» (уточнить по типу объекта). P3.
- «Укажите номер из списка или ID», «или ID анкеты» — упоминания ID убрать: номер из списка. P3.
- `notificationParts` (`[1/2]`) — ок для длинных сообщений.
- Кнопка «★ 1…5», reply-меню, описания команд (`set-bot-commands.ts`) — эмодзи в норме.

### 3.5. Пример владельца №3 («здесь вылез казахский»)

Текст «Состояние регистрации / Тіркелу күйі: … / …» — формат прежних сдвоенных строк; в коде это уведомление давно переведено на `LocalizedNotice` и выбирает язык получателя (`domains/registrations/service.ts` L542–549, диспетчер `dispatchNotices` L283–285). По AGENTS.md демонстрационный стенд Frankfurt не обновлялся — скорее всего, это старая доставка со стенда. Действия: развернуть текущий `main`/ветвь на стенд и повторить; если воспроизведётся — искать остатки `labelCombined` в данных (`notification.text` старых строк очереди). Известное исключение, зафиксированное в AGENTS.md: префикс «Сигнал проверяется / Сигнал тексерілуде» в хранимом `public_text` инцидента (VS-7) — правится отдельно.

## 4. Связь со срезом «Шаблоны сообщений»

Утверждённый план `tasks/plan-bot-message-templates.md` переносит ~136 реплик и ~28 уведомлений в каталог шаблонов, где дефолт ключа = точная копия текущего текста (golden-тесты). Это закрепит сегодняшние формулировки как дефолты. Варианты:

1. **Согласовать P1/P2-правки текстов до переноса** (правим литералы → golden-тесты фиксируют уже исправленные дефолты). Дешевле всего сделать правки, не зависящие от механизма: `fmtDate`, словари статусов, удаление дублей нумерации и подсказок, emoji-чистка, `LocalizedNotice`.
2. Либо принять текущие тексты как дефолты и править их переопределениями в кабинете — но тогда дефолты для новых установок останутся неудобными (не рекомендуется).

Рекомендация — вариант 1: механические P1-правки (даты/статусы/UUID/нумерация/эмодзи) выполняются до среза 2 плана шаблонов или объединяются с ним (правка текста в момент переноса файла, с новым golden-эталоном, согласованным владельцем).

## 5. Предлагаемый порядок работ (черновик среза `bot-ux-fixes`)

1. **P1-механика без изменения правил:** `KIND_TEXT`/`ROLE_TEXT` (дубль нумерации); `fmtDate` во всех уведомлениях (requests/service, tasks/common, visits, incidents/service, publications/service); словарь статусов визитов; `LocalizedNotice` для оставшихся строк `tasks/*`; UUID → номера/кнопки в `/publications`, `/signals`, служебных уведомлениях анкет; построчные кнопки в `/requests` + дата в списке/карточке; emoji-чистка справки; короткий `/start`.
2. **P2:** подсказки-дубли → кнопки/короткие строки; «Начало обработки», «Версия результата», методичка; слаги ролей в `/invite`; тексты ошибок по ботам; «privacy_request» → «раздел кабинета».
3. **P3:** суффиксы «(Алматы)», дайджест с датой, «ID»-упоминания, прочая шлифовка.

Каждый шаг — с обновлением модульных тестов (golden-строки) и `AGENTS.md`. Интеграционные тесты — по отдельному запросу владельца.
