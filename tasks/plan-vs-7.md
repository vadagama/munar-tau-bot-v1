# VS-7 — Аварии и публикации

Статус: подготовка завершена; план готов к проверке, реализация не начата.
Запрос пользователя: «Запусти выполнение VS-7», 17.10.2026.
Ветка: `feature/vs-7-incidents-publications`; база: `origin/main` (`59d8e41`, VS-5, PR #14).

## Основания

Требования EMG-01–07, PUB-01–03, JOB-04, TIM-05, NTF-01–03, FIN-01–04;
модель процессов §6 и §8; матрица доступа §3 и §5; HLD §5.2/27;

Чужие незакоммиченные изменения входа и интерфейса остаются в исходной рабочей папке.

## Контракты и границы

- Общие домены incidents/publications обслуживают API, кабинет, бот и эмуляцию.
- Использовать существующие outbox, notification, preference, digest, lease и обработчик jobs из VS-5. Не создавать второго диспетчера доставки.
- Аудитория: подтверждённые действующие связи с затронутыми объектами, один получатель на человека; повторная проверка при доставке. Зоны и услуги нельзя свести к рассылке по всему дому без проверки охвата.
- Все чтения и изменения проходят PDP, область домов, `is_test`; тестовые сообщения идут только в simulator. Отзыв назначения/связи действует со следующего запроса.
- Изменения состояния, журнал, outbox и таймеры атомарны; expected_version и 409 защищают от устаревших действий, ключи операций защищают от повторов.
- Публичный текст и выбранные материалы отделены от переписки, персональных данных и внутренних файлов. Вложения отчётов не становятся публичными автоматически.
- Общая авария не закрывает индивидуальные обращения и не подтверждает результат за жителей. Использовать существующие проверки комплекта VS-4/ADR-006.
- Публикации, требующие утверждённых документов, не обходят VS-8: до появления проверяемой утверждённой версии действие блокируется. Финансовая публикация требует разрешения председателя и внешних оснований FIN; полная документальная приёмка остаётся зависимой от VS-8.
- Не менять демонстрационный стенд в рамках реализации. SQL-проверки допустимы только на Sydney с установленной общей блокировкой. Автоматический integration остаётся отключённым согласно текущему main.

## Последовательность

Каждый пункт выполняется небольшими коммитами: контракт/тест → реализация → проверка.
Перед кодом сверять фактические имена таблиц и существующие миграции.

### 1. Контракты инцидента и охвата

- [ ] Типы состояний и команд, FSM всех переходов §6, включая повторную проверку неподтверждённого сигнала и возобновление завершённого инцидента.
- [ ] Аддитивная миграция incident/scope/log и связей с обращениями/общими работами; непустой охват, версии, история, изоляция тестовых данных, RLS-заслон.
- [ ] Проверки обязательных оснований, фактического начала, времени/способа проверки и полного восстановления. Частичное восстановление не завершает инцидент.

Проверка: модульные таблицы переходов и негативные сценарии; SQL-ограничения/откат транзакции на Sydney. Зависимости: нет. Файлы: новый домен incidents, миграция, интеграционный тест.

### 2. Права и операции инцидента

- [ ] PDP для администратора и назначенного дежурного; исполнитель сообщает результат только в допустимом контексте.
- [ ] Создание, чтение, изменение охвата/прогноза, переходы, история через общий сервис и API; version/409 и повтор операции.
- [ ] Привязка после проверки места/причины; отсоединение с причиной и дальнейшим маршрутом, сохранением ответственного и сроков обращения.

Проверка: чужой дом, отзыв роли, просроченное назначение, устаревшая версия, rollback аудита/outbox, отсутствие чужой переписки. Зависимость: 1. Файлы: PDP, incidents service/access, API handlers/tests.

### 3. Дежурство и срочный маршрут

- [ ] Настройка основного/резервного дежурного и графика, аварийного телефона; сообщение о возможной аварии и опасности из задания (EMG-01/02, JOB-04).
- [ ] Круглосуточный маршрут TIM-05: через 10 календарных минут без принятия основным — резервный и уведомление администратора; ещё через 10 минут — ответственность администратору и уведомление председателя.
- [ ] Только текущий ответственный может принять сигнал; устаревшая кнопка показывает нового ответственного. Отправка уведомления не считается принятием или выездом.

Проверка: ночь, отсутствие дежурного, повторный тик, гонка принятия/эскалации, simulator. Зависимость: 2. Раздельные коммиты: конфигурация, TIM, бот/эмуляция.

### Контрольная точка A

- [ ] FSM, PDP, API и срочный маршрут проходят проверки; база и типы совместимы с VS-5.

### 4. Адресные обновления и массовая доставка

- [ ] Устойчивый broadcast.fanout ограниченными порциями с курсором, дедупом и конкурентной защитой; выход по бюджету Edge Function.
- [ ] Первое подтверждение, предупреждение о проверке, корректировка неподтверждённого сигнала, изменения охвата/прогноза/ограничений, частичное и полное восстановление.
- [ ] При неизвестном прогнозе обязательны «Уточняется» и следующее обновление; TIM напоминает/эскалирует пропуск. NTF-02 передаёт окончательную ошибку резервному ответственному.
- [ ] Аварии обязательны независимо от предпочтений; проверять действующий доступ перед отправкой, включая потерю связи после fanout; сохранять историю аудитории для исправлений.

Проверка: несколько помещений одного человека, разные зоны, отзыв доступа, 429/retry_after, падение между порциями, конкурентные jobs, отсутствие реальных отправок из эмуляции. Зависимости: 2–3. Раздельные коммиты: fanout, TIM, delivery/followup.

### 5. Восстановление и связанные обращения

- [ ] Сохранять восстановленные зоны/услуги и остаточные ограничения; завершение только после фактической проверки всего охвата.
- [ ] Передавать обезличенный общий отчёт связанным обращениям через проверки готовности заданий/документов VS-4. Неготовые обращения остаются в работе с причиной.
- [ ] Сохранение локальной проблемы требует решения администратора: локальное задание либо возобновление инцидента. Старые отчёты/история сохраняются.

Проверка: два дома, восстановлен один; общий объём готов, локальное задание не готово; один житель подтвердил, другой вернул; устаревший комплект. Зависимости: 2, 4. Файлы: incidents recovery, адаптер requests/tasks, тесты.

## Решения, требующие уточнения

- Цели производительности пока не утверждены: API p95 ≤ 500 мс, ответ бота ≤ 2 с, пик до 100 сессий, начало аварийной рассылки ≤ 1 мин; прохождение ≤ 15 мин — предложение Ф-1. Пользователю направлен вопрос; без ответа не считать эти цифры согласованными и не объявлять нагрузочную приёмку пройденной.
- Точные нормативы напоминаний об обновлении инцидента должны быть декларативными; не придумывать значения вместо настройки уполномоченным сотрудником.
- Выбранные публичные медиа требуют отдельного безопасного механизма раскрытия; перед реализацией зафиксировать контракт, сохраняющий приватность исходных внутренних вложений.
