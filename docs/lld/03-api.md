# LLD-03: API и контракты

Основание: [HLD раздел 12](../hld.md), [модель процессов](../request-lifecycle.md), [матрица прав](../access-matrix.md). Реализация — функция `api` (Edge Function, ADR-003); все эндпоинты ниже указаны в документном виде `/v1/…`, при развёртывании им соответствует `/functions/v1/api/v1/…` `[согласовано 16.10.2026]`.

## 1. Общие соглашения

- **Формат:** HTTPS, JSON (UTF-8). Даты — ISO 8601 UTC. Язык сообщений об ошибках — по `Accept-Language` (ru/kk, UI-02).
- **Аутентификация:** `Authorization: Bearer <JWT Supabase>`. Сервер проверяет JWT, находит `profile` по `supabase_user_id`/`telegram_user_id` (ADR-001), собирает `Actor` (профиль, человек, действующие `staff_assignment`, связи, участие). Отсутствие профиля — 401 `NO_PROFILE` (вход не выдаёт роль). Webhook бота — отдельная аутентификация (раздел 6).
- **Проверка полномочий:** PDP на каждом вызове для чтения и записи (AUTH-01); deny-by-default; отказ — 403 с `reason` без раскрытия существования запрещённого объекта (404 для чужих ресурсов).
- **Привилегированные действия** (AUTH-03): действуют только через кабинет (JWT-сеанс), недоступны webhook-каналу бота; после пилота дополнительно подтверждение TOTP (механизм — открытая точка AQ-02). Перечень ведётся в реестре PDP.
- **Сеанс (AUTH-06):** ≤ 12 ч от старта, 30 мин бездействия; контроль в middleware по `access_session` (LLD-02, раздел 13); превышение — 401 `SESSION_EXPIRED`. Отзыв полномочий блокирует следующий запрос из открытого сеанса (ROL-04): PDP проверяет назначения при каждом вызове; отзыв роли доменом `admin` дополнительно отзывает сеансы.
- **Идемпотентность (REQ-05, OPS-01):** мутации принимают заголовок `Idempotency-Key` (uuid, клиент генерирует при первом действии). Повтор с тем же ключом возвращает сохранённый результат без повторного эффекта. Коллизия ключа с другим телом — 409 `IDEMPOTENCY_CONFLICT`.
- **Конкурентность (FLOW-01):** агрегаты несут `version`; мутации передают `expected_version`; конфликт — 409 `CONCURRENT_MODIFICATION` с актуальным состоянием и новой `version` (второй участник обновляет карточку).
- **Пагинация:** `?limit=50&cursor=…` (курсор — base64 создано_в+id); максимум `limit=100`. Сортировка фиксирована на эндпоинте и указана в описании.
- **Трассировка:** каждый запрос получает `trace_id` (сервер) и `request_id`; в логи — без персональных данных (ADR-002).
- **Ограничение темпа:** 100 запросов/мин на профиль `[согласовано 16.10.2026]`; превышение — 429 `RATE_LIMITED` с `Retry-After`.

### 1.1. Формат ошибки

```json
{
  "error": {
    "code": "INVALID_TRANSITION",
    "message": "Недопустимый переход для текущего состояния",
    "details": { "current_state": "in_work", "allowed": ["on_review", "on_hold", "need_clarification"] },
    "trace_id": "01J…"
  }
}
```

Коды: `UNAUTHENTICATED`, `NO_PROFILE`, `SESSION_EXPIRED`, `FORBIDDEN`, `PRIVILEGED_REQUIRED` (нужен кабинет/TOTP), `NOT_FOUND`, `VALIDATION_FAILED` (details: список полей), `INVALID_TRANSITION`, `CONCURRENT_MODIFICATION`, `IDEMPOTENCY_CONFLICT`, `FILE_LIMIT` (FIL-01), `RULE_LEGAL_BOUNDARY` (TIM-07), `RATE_LIMITED`, `INTERNAL`.

### 1.2. Заголовки ответов приватности

Все ответы с персональными данными: `Cache-Control: no-store`; вложения отдаются подписанными URL с коротким сроком (≤ 5 мин `[согласовано 16.10.2026]`).

## 2. Файлы

1. `POST /v1/files/upload-url` — {owner_type, owner_id, bucket(аудитория), size, mime} → PDP на запись в владельца + FIL-01 (≤ 20 МБ) → создаёт `attachment` (status=incomplete) и возвращает {attachment_id, upload_url, expires_in}.
2. Клиент кладёт файл в Storage по `upload_url`.
3. `POST /v1/files/{attachment_id}/complete` — сервер проверяет размер/доступность, ставит `status=complete` (FIL-02: ошибка загрузки не блокирует бизнес-операцию — вложение остаётся неполным и помечено).
4. `GET /v1/files/{attachment_id}/url` — выдача ссылки на скачивание после PDP по аудитории вложения (MSG-03, PAY-08, DOC-02–03); ответ {url, expires_in}.

Прямые ссылки Storage из клиента не используются; ссылка из уведомления ведёт на `/v1/files/…/url` (переход после проверки).

FIN-04 использует `/v1/financial-rules` (GET/POST), `/v1/financial-rules/{id}`
(PATCH), `/v1/financial-obligations` (GET/POST), `/v1/financial-obligations/{id}`
(GET), а также POST `/{id}/reassign` и `/{id}/placements` внутри
`financial-obligations`. Все команды требуют Idempotency-Key и причину;
правки/передача/размещение — expected_version, создание обязанности — версию
выбранного финансового регламента. Режим берётся из эффективной персоны.
Чтение требует финансового PDP области, управление — управляющего PDP;
техническая роль и личная собственность сами по себе доступа к настройкам
и очереди не дают. Очередь возвращает до 200 доступных строк, offset/has_more.
Карточка содержит исходный снимок, историю размещений и missing_channels;
старые подтверждения не покрывают исправляемую версию. Размещение принимает
financial_version_id, channel, placed_at, evidence и необязательный proof_version_id
проверенного документа. Запись факта не завершает непригодный комплект.

Финансовые POST/PATCH `/v1/publications` принимают `obligation_id`, `period_from/to`,
`report_version_id`, `basis_versions: [{code, document_version_id}]`,
`disclosed_version_ids`, `correction_note`. Сервер создаёт неизменяемую версию
комплекта; клиентские признаки проверки/разрешения не принимаются за доказательство.
Изменение финансовой или документозависимой публикации требует `reason`,
`expected_version`, `Idempotency-Key`; создание — ключа намерения. Пояснение
исправления для собственника отделено от служебной причины действия.
Обычная документозависимая публикация указывает `document_version_ids`.

Немедленный и плановый выпуск используют тот же провайдер версий документов;
финансовый выпуск также повторно проверяет снимок разрешения и действующего
председателя. GET возвращает `financial_versions`; собственник получает
опубликованные снимки, включая заменённые, и только раскрытые доступные версии
приложений. Пока готовится исправление, его текст и файлы собственнику не видны.
URL финансового приложения через `/v1/publications/{id}/files/{fileId}/url`
повторяет PDP публикации, документа, источника и конкретной версии.

IDEA/MOD VS-8: конвейер использует `initiative.use` эффективной персоны, домен
повторяет объектный PDP. GET `/v1/initiative-comments/{id}` сохраняет доступ
автора к скрытому оригиналу. GET `/v1/moderation/actions` и `/{id}` показывают
свои/доступные по области действия; GET `/v1/moderation/appeals` и `/{id}` —
частную аргументацию только автору и председателю. Списки `{items,has_more}`,
limit 1–50 (20 по умолчанию), offset 0–100000, фильтрация до пагинации.
Комментарии — по 20, offset до 10000. Личная поддержка имеет свою version;
DELETE `/{id}/support?expected_version=N` использует query, поскольку тело
DELETE общий конвейер не читает. Все записи требуют Idempotency-Key;
разрешение оспаривания — expected_version жалобы и action_expected_version.
Карточка содержит support_count, own_support и серверные can_*; состав
поддержавших, снимок решения, телефоны и помещения не выдаются.

POL VS-8: `poll.use` — только вход конвейера с эффективной персоной; домен
повторно проверяет конкретный `poll.read/manage/answer/results`. Список принимает
`offset` (0–100000), `limit` (1–50, по умолчанию 20), необязательное `state`:
`draft/open/closed/canceled`; ответ `{items, has_more}`. Фильтрация PDP предшествует
пагинации. Карточка содержит `id/question/options[{key,label}]/building_ids`,
`closes_at/state/version/cancel_reason/informational`, названия существующих
зданий `buildings[{id,label}]`, серверный `deadline_passed`, собственный `own_answer`
либо null и флаги `can_manage/can_answer/can_results`. Чужие ответы и состав
участников не выбираются для DTO списка/карточки.

Создание принимает вопрос, 2–20 вариантов со стабильными ключами, дома,
ISO-срок с часовым поясом и причину. PATCH частичный, только для draft, требует
`expected_version`; переход — `{action: open|cancel, expected_version, reason}`.
Бот жителя использует `/polls`, `/poll UUID` и глубокую ссылку `poll_UUID`.
Личные кнопки привязаны к nonce карточки, версии опроса и собственного ответа,
профилю/каналу/сеансу. Варианты длиннее 64 символов открывают полный текст
перед отдельным подтверждением; короткие отправляются непосредственно.

Личный ответ POST/PATCH принимает ровно `{option_key, expected_version}`,
для первого ответа версия 0; чужие person/time/eligibility отвергаются.
Все изменения требуют `Idempotency-Key`; replay — исходный снимок успеха,
после записи клиент перечитывает карточку для текущего `included`.

Сводка: `{participants_count, distribution:[{option_key,count}], as_of, final}`,
без имён и персональных ответов. Управляющему доступен текущий агрегат,
участнику окончательного снимка — final после закрытия, в том числе после
переезда. Отмена отклоняет чтение до запроса распределения. Истёкший срок не
продлевает приём ответов даже до jobs. UUID и страницы валидируются транспортом
и доменом; неизвестные/недоступные объекты — NOT_FOUND, версии — 409.

## 4. Детальные контракты ключевых операций

### 4.1. Создание обращения (REQ-01–05)

`POST /v1/requests` с `Idempotency-Key`:

```json
{
  "kind": "request", "category_id": null, "urgency": "normal",
  "premises_id": "uuid|null", "building_id": "uuid|null",
  "text": "…", "attachments": ["attachment_id"],
  "as_draft": false, "expected_draft_version": null
}
```

- Эффект (одна транзакция): черновик → new (или создание сразу new), номер, `first_response_due_at` по TIM (2 рабочих часа), события `request.created`, `timer` напоминаний; участник author.
- Повтор с тем же `Idempotency-Key` → тот же номер, новых событий нет (REQ-05, OPS-01).
- Ответ: `{id, number, state, first_response_due_at, version}` + вне графика — предупреждение отсутствия немедленной обработки и аварийный телефон (TIM-05, EMG-02).

### 4.2. Переходы обращения — `POST /v1/requests/{id}/transitions`

```json
{ "action": "submit_result", "expected_version": 7, "reason": null,
  "payload": { "confirmation_payload": { "summary": "…", "document_version_ids": [], "task_report_ids": [] } } }
```

Соответствие действий модели процессов (раздел 4; каждое — валидируется FSM и PDP, пишет `request_log`, события — outbox):

| Action | Переход | Кто |
| --- | --- | --- |
| `submit` | draft → new | автор/админ |
| `start_review` | new → reviewing | админ |
| `ask_clarification` | new/reviewing/in_work/rework → need_clarification | админ |
| `answer_clarification` | need_clarification → reviewing (ответ сохранён с источником) | автор/участник |
| `resolve_clarification` | need_clarification → reviewing (снятие) | админ |
| `start_work` | reviewing → in_work (план/задания; платная — условия старта) | админ |
| `hold` · `resume` | → on_hold → reviewing (причина, дата следующего действия) | админ |
| `submit_result` | reviewing/in_work → awaiting_confirmation (комплект и снимок) | админ |
| `confirm_result` | awaiting_confirmation → closed (метод author) | автор |
| `return_result` | awaiting_confirmation → rework | автор |
| `admin_close` | awaiting_confirmation → closed (метод administrative, WRK-07/15) | админ |
| `withdraw_report` | awaiting_confirmation → in_work (отзыв ошибочного отчёта) | админ |
| `reopen` | closed → rework (в окне, по умолчанию 7 дней) | автор |
| `plan_rework` | rework → in_work | админ |
| `cancel_request` · `approve_cancel` · `reject_cancel` | запрос/согласование отмены (до начала работ — сразу canceled) | автор / админ |
| `reject` | открытое → rejected (основание) | админ |
| `appeal_reject` · `uphold_appeal` | оспаривание; rejected → reviewing | автор / председатель |

Ошибки: 409 `INVALID_TRANSITION` (details: текущее состояние и допустимые действия), 409 `CONCURRENT_MODIFICATION` (version), 403 `FORBIDDEN`. Устаревшее подтверждение не принимается: `confirm_result` проверяет `confirmation_version` снимка (модель процессов, сценарий 3).

### 4.3. Переходы задания (`tasks/{id}/transitions`) — модель процессов раздел 5

`assign` → awaiting_acceptance (админ) · `accept`/`decline` (исполнитель) · `start` (условия старта, платная — work_permission=granted) · `suspend`/`resume` (админ или запрос исполнителя; отдельное событие «Нет доступа») · `submit_report` (версия отчёта + доказательства) · `accept_report` / `return_for_rework` (админ; замечания) · `reassign` (→ created, история сохраняется) · `cancel` (обязательное — требуется замена или явное изменение объёма).

### 4.4. Инцидент (`incidents/{id}/transitions`) — модель процессов раздел 6

`register_signal` (создание) · `confirm` · `mark_unconfirmed` · `start_mitigation` (фактическое начало) · `report_recovery` (что восстановлено, зоны) · `fail_check` (→ mitigation) · `complete` (весь заявленный охват; частичное восстановление не проходит) · `reopen` (ошибочное завершение). Каждый переход сохраняет основание и уведомляет соответствующую аудиторию по `incident_scope` (EMG-06).

### 4.5. Финансовая карточка плательщика (PAY-03/06)

`GET /v1/payments/orders/{id}` для плательщика возвращает только: услугу, объём, согласованную цену/смету, платежи, возвраты, статус; переписка обращения не раскрывается. Отправка квитанции — `POST …/payments` (attachment в `files-finance`); уведомления — только плательщику (FLOW-03).

## 6. Webhook бота: `POST /functions/v1/bot-webhook`

Два бота (ADR-009): `/bot-webhook/resident` — бот жителей,
`/bot-webhook/worker` — бот сотрудников; базовый путь без суффикса —
бот жителей (совместимость), иной суффикс — 404. У каждого бота свой секрет
(`TELEGRAM_WEBHOOK_SECRET` / `TELEGRAM_WORKER_WEBHOOK_SECRET`).

- Проверка заголовка `X-Telegram-Bot-Api-Secret-Token` (не совпал — 401, тело не читается).
- Запись `bot_inbound(bot, update_id)` — составной ключ: нумерации update_id
  у ботов независимы; повтор доставки игнорируется (возврат 200 без эффекта, REQ-05).
- Лёгкие шаги (ответ меню, валидация) — синхронно; тяжёлые (создание обращения с файлами, отправка отчётов, рассылки) — задачи в `job_queue`; ответ Telegram — 200 как можно быстрее (≤ 10 с `[согласовано 16.10.2026]`).
- Ошибка обработки — `status=error` и повтор по очереди; Telegram не получает 5xx повторно (защита от пинг-понга) `[согласовано 16.10.2026]`.
- Диалог: `bot_dialog` читается/пишется в транзакции шага; прерванный вызов функции продолжается следующим обновлением/тиком (ADR-003).
- Привилегированных API-операций у бота нет (AUTH-03): сценарии бота вызывают те же домены с Actor = житель/исполнитель.

## Уточнения VS-2 (17.10.2026)

Контракты минимального контура — [ADR-004](../decisions/004-vs2-registration-bootstrap.md).

- Реестр также предоставляет GET/POST `/v1/registry/buildings`, PATCH `/v1/registry/buildings/{id}`. Структуру зданий изменяет председатель; эмуляция её не меняет. Лица, связи, помещения и анкеты разделены по тестовому домену и области домов.
- Списки возвращают `{items:[…]}`. Мутации — созданную/изменённую запись. Поля snake_case соответствуют таблицам. Для предварительной карточки обязательны `full_name`, `phone_e164`, `premises_id`, `source`, `processing_basis`; доступ остаётся неподтверждённым.
- POST `/v1/registrations`: `full_name`, `phone_e164`, `language:ru|kk`, `consent:true`, `premises_id`, `role`; сотрудник указывает `person_id` для подачи за существующего человека. Решения approve/reject/clarify/dispute требуют `reason`; approve допускает явно проверенный `person_id` из реестра. Собственник использует tenant-approval с `registration_id`, `approve:boolean`, `reason`.
- При принятии приглашения создаётся конкретная `connection` и подтверждённая `registration`; повторное принятие при существующей активной связи отклоняется. Спор адресуется именно этой связи и не отзывает собственность/новую позднейшую связь.
- GET `/v1/registrations/invites` — список приглашений области без bearer-токенов приглашений.
- GET `/v1/registry/template`, POST `/v1/registry/export` и GET `/v1/registry/imports/{id}/template-errors` возвращают `{filename,content_type,data_base64}`. POST imports принимает `{data_base64}` и отвечает 202 `{id,state}`. - POST `/v1/registry/persons/{id}/telegram-recovery` — кабинет, привилегированное действие. Вход `{registration_id,verified_basis}`: ID анкеты с нового проверенного Telegram и основание внешней проверки. Прежние сеансы/привязка прекращаются, person и полномочия сохраняются. Совпадение metadata/телефона не переносит доступ.

### Уточнение реализации VS-4: общий объём и методички (17.10.2026)

- `POST /v1/tasks`: ровно один `request_id` или `common_work_id`; шаблон задаётся
  `template_id`/`template_version`, инструкция и чек-лист копируются сервером.
  `document_required=true` допустим только для обязательного задания и блокирует
  приёмку без актуального одобренного обязательного акта (VS-8). Платные условия старта закрыты до VS-6.
- `request_pause` в transitions: назначенный исполнитель, причина, состояния
  accepted/in_progress. Сохраняет состояние, уведомляет ответственного; остановку
  оформляет администратор отдельным `suspend`.
- `cancel`: причина, `stop_checked=true`, для обязательного задания —
  `replacement_task_id` того же родителя, без зависимости от отменяемого задания.
  Неначатые зависимости переносятся на замену; начатые требуют `dependency_review`.
  `replace_canceled` позволяет явно заменить обязательное задание, отменённое
  вместе с обращением, после его возобновления по апелляции. История сохраняется.
- `GET/POST /v1/common-works`, `GET /:id`, `POST/DELETE /:id/requests`,
  `POST /:id/transitions` (complete/cancel), `GET /:id/task-assignees`:
  полномочия на все дома работы, version/409 и Idempotency-Key для изменений.
  Создание требует title/plan/due_at/building_ids; отсоединение — reason/resolution_plan.
  Завершение проверяет весь обязательный объём. Отмена требует stop_checked и
  request_decisions с основанием по каждому связанному обращению; обращения
  автоматически не отменяются. Локальные незавершённые задания отмечаются в истории
  завершения и уведомлении конкретному автору.
- `GET/POST /v1/job-templates`, `PATCH /:id`, `GET /:id/versions`, `POST /:id/run`:
  версия, область, инструкция и чек-лист. Новая версия не меняет действующие задания.
  Ручной запуск создаёт общую работу с заданием без обязательного обращения жителя.
  `revise_template` явно применяет текущую версию к открытому заданию с причиной,
  историей старой инструкции и снятием назначения; отчёт сначала возвращается.
- `POST /v1/tasks/:id/problems`: location/description/attachment_ids — сохранённые
  фотографии этого задания; сообщение фиксируется в task_log. Менеджер получает
  доступ к указанным фото. `POST /v1/task-problems/:id/link`: task_id/reason,
  связывает сообщение с отдельным заданием по решению администратора.
- submit_result формирует task_report_ids/task_results из БД; переданный клиентом
  состав проверяется. Публикуется текстовый снимок объёма/результата/ограничений,
  внутренние доказательства не раскрываются. confirm_result/admin_close сверяют
  текущий комплект с активным снимком; несовпадение — 409, требуется отзыв и новая
  передача. Возврат общего задания запрещён до отзыва ожидающих подтверждений.
- Длинный текст уведомления сохраняется полностью: нумерованные части до 4096
  символов с отдельными dedup_key. Повтор постановки не создаёт дубли частей.

### VS-5: расписание шаблонов

- `GET /v1/job-templates/:id/schedule` — настройки, доступные исполнители, последние доступные запуски (до 100); текущая область шаблона и область каждого запуска проверяются сервером.
- `POST /v1/job-templates/:id/schedule` — `version`, `enabled`, `next_run_at` (ISO с часовым поясом), `interval_hours`, `due_hours` (целые 1–8784), `assignee_person_id?`. Конфликт версии — 409; отсутствующие регламенты назначения — ошибка валидации.

Карточка задания возвращает `acceptance_due_at`, `overdue_at`; обработчик дополнительно получает безопасные коды окончательных ошибок доставки и состояние контакта.

### Уточнение исполнителей заданий (18.10.2026, ROL-02e, ADR-013)

- `GET /v1/requests/:id/task-assignees`, `GET /v1/common-works/:id/task-assignees` и поле `assignees` в расписании возвращают всех действующих сотрудников той же тестовой области: `{id, full_name, roles: string[]}`. Одно лицо возвращается один раз; роли — действующие. Сначала сотрудники области задания, затем остальные, внутри групп — по ФИО.
- Создание, `assign`, начало работы из обращения и включение расписания используют одну проверку сотрудника: активная персона, хотя бы одно действующее служебное назначение, совпадение `is_test`. Роль `executor` и область сотрудника не требуются. При запуске расписания сотрудник проверяется повторно.
- `task.use` доступен всем служебным ролям; `task.read`/`task.execute` по личному назначению не зависят от домов. `task.manage` сохраняет прежние ограничения. Снятие назначения или отзыв всех служебных полномочий прекращает доступ по личному назначению и доставку уведомлений задания.
- Назначение не расширяет доступ к исходному обращению, финансовым данным или приёмке собственного результата.

## Уточнение управления сотрудниками (18.10.2026)

Актуальная модель — ROL-02f и [ADR-014](../decisions/014-staff-role-management.md): служебная область временно всё ОСИ, назначение — перечень ролей, управление только вниз, наследование председатель → администратор → заместитель → исполнитель плюс duty/doc_reviewer/finance у заместителя и выше. Системные полномочия техадминистратора отдельны. Новая редакция заменяет прежние домовые ограничения и специальные переключатели в форме сотрудника; существующие окна действия назначений сохраняют силу. Аудит и ограничения конкретных объектов/жалоб/финансовой аудитории/собственной приёмки сохраняются.

- `GET /v1/staff` — каталог действующих, будущих и бывших сотрудников той же тестовой области, доступные роли и возможность редактирования.
- `POST /v1/staff/candidates/search` с `{query}` — зарегистрированные активные пользователи с действующим профилем без текущих/будущих служебных назначений; поиск по имени/телефону передаётся в теле запроса, без персональных данных в URL.
- `GET /v1/staff/:id` — прямые и наследуемые роли, версия перечня, открытые обязанности, история и серверный can_edit.
- `POST /v1/staff/:id/roles` — `{roles, reason, expected_version}` + Idempotency-Key. Пустой roles прекращает служебные полномочия. 409 сохраняет ввод клиента и требует явного повторного подтверждения.
- `/v1/meta/me` дополнительно возвращает assigned_roles/effective_roles; assignments содержит только прямые назначения.
- Каждое изменение ставит обязательное персональное событие staff.roles в outbox для worker-бота, включая отзыв последней роли. Текст — каталог notices.staff.roles_changed, оба языка, время Алматы и причина.
