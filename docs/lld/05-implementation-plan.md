# LLD-05: План реализации

Основание: [HLD раздел 27](../hld.md); критерии проверки — [раздел 15.2 спецификации](../requirements-v1.md) и [раздел 8 модели процессов](../request-lifecycle.md). Порядок срезов соответствует зависимостям; состав каждого среза — конкретные модули [LLD-01](01-modules.md), таблицы [LLD-02](02-data-model.md) и эндпоинты [LLD-03](03-api.md).

Оценки — относительный размер (S/M/L/XL), не срок: календарный план — после VS-0, когда появится CI и измеримая скорость команды.

## 1. Состав срезов

### VS-0 — Фундамент (M)

- Структура репозитория по [LLD-01](01-modules.md); workspace TypeScript, lint, typecheck, тесты; запись в `/source/` снимается с `.gitignore`.
- Миграции: `db/migrations` (нумерованные SQL, expand/contract), `db/rls.sql` ([LLD-02](02-data-model.md), раздел 16).
- Функции-заглушки `api`, `bot-webhook`, `jobs` (health-ответы); регистрация pg_cron; секреты только в средах; среда `dev` — Supabase Cloud, вымышленные данные.
- CI: lint → typecheck → тесты → сборка → деплой функций; кабинет — сборка Vite; автопроверка отсутствия секретов в сборке.
- Кабинет: каркас SPA (React + Refine + AntD, Vite), вход «Войти через Telegram» (ADR-001), SPA-маршрутизация.

Критерий: поставка пустого ядра и статики по HLD раздел 20; деплой из CI повторяем; в сборке нет секретов.

### VS-1 — Доступ и аудит-скелет (L)

- `pdp`: Actor, `can()`, реестр действий с флагом privileged (AUTH-03); сценарные тесты по разделу 7 [матрицы](../access-matrix.md).
- Сеансы: `access_session`, middleware 12 ч / 30 мин бездействия, отзыв сеансов; отозванная роль блокирует следующий запрос (ROL-04, AUTH-01/06).
- `audit_log` + чтение по областям (AUD-02); append-only (LLD-02, раздел 17).
- Эмуляция: тестовые персоны, `emulation_session`, транспорт симулятора (тот же сценарный модуль бота), баннер режима.
- Кабинет: `/v1/meta/me`, журнал, управление тестовыми персонами и сеансами эмуляции.

Критерий: сценарии входа/отзыва/эмуляции (AUTH-01, ACC-01; на пилоте — вход только Telegram OIDC, privileged — кабинет-only); эмулированные действия в журнале с реальным актором и эмулируемой персоной.

### VS-2 — Реестр и регистрация (L)

- Таблицы: person, profile, building, building_parking, premises, connection, staff_assignment, staff_scope, invite, registration, import_batch/import_mapping ([LLD-02](02-data-model.md), разделы 2, 11).
- Домены `registry`, `registrations`; эндпоинты [LLD-03](03-api.md) 3.2–3.3; бот: анкета, добавление помещения, приглашение, статус проверки.
- Кабинет: реестры, очередь анкет и споров, приглашения, импорт Excel (загрузка → отчёт ошибок → commit), экспорт персонального реестра (priv, журналируется, IMP-05).
- Минимальный TIM-контур (правило + таймер + напоминание) для эскалации споров REG-14.

Критерий: сценарии REG/IMP — четыре типа помещений, уникальность (building, kind, number), ошибка Excel блокирует весь импорт (IMP-02), идентификаторы при импорте сохраняются в выгрузке (IMP-04), доступ не выдаётся автоматически (IMP-03).

### VS-3 — Обращения и переписка (L)

- Таблицы: request, request_log, request_participant, request_confirmation, message, attachment, request_category, rating ([LLD-02](02-data-model.md), раздел 3).
- Переходы обращения — полная таблица модели процессов (раздел 4) через `/transitions`; идемпотентность отправки (Idempotency-Key, REQ-05); конкурентность 409 по `version` (FLOW-01).
- Файлы: upload-url/complete/url по аудиториям (FIL-01–02, MSG-03); каналы «Жителю»/«Внутреннее»; совместный доступ SHR; оценка RAT.
- Бот: создание заявки с вложениями, статус, переписка, подтверждение результата; кабинет: очередь, карточка, классификация, каналы, вложения.

Критерий: основной маршрут REQ/SHR/MSG и приватность (раздел 15.2): внутренний канал и чужие заявки недоступны; прямой URL внутреннего вложения — отказ; повтор отправки не создаёт дубль; молчание автора не закрывает заявку.

### VS-4 — Задания и общая работа (L)

- Таблицы: task, task_log, task_report, visit, common_work(+request), job_template ([LLD-02](02-data-model.md), раздел 4).
- Переходы задания (модель процессов, раздел 5): принятие/отказ, старт, приостановка (отдельное событие «Нет доступа»), отчёт с доказательствами (WRK-16), приёмка/доработка, переназначение, отмена обязательного с заменой; общая работа: агрегированные состояния и персональная приёмка; визиты WRK-03–05.
- Бот исполнителя: задания, принять/отказаться, отчёт (текст + файлы), визиты; кабинет: назначение, приёмка, замечания, шаблоны JOB-01–06.

Критерий: сценарии WRK/JOB: приёмка задания ≠ подтверждение обращения; возврат задания возобновляет общую работу; «общая работа завершена, локальное задание не выполнено» — обращение не уходит на подтверждение.

### VS-5 — Регламенты и уведомления (M)

- Таблицы: time_rule/time_rule_version, timer, notification, notification_pref ([LLD-02](02-data-model.md), разделы 9–10); движок TIM и свип ([LLD-04](04-background-tasks.md), разделы 2–5).
- Полный пайплайн уведомлений: outbox → notification (дедуп) → send → результат/ошибка (NTF-02); шаблоны ru/kk; предпочтения.
- Эскалации REG-14 (12 рабочих часов на этапе), напоминания 48 ч (REG-04, WRK-07), дайджест NTF-01 (следует за концом смены, пустые не отправляются), первый ответ 2 рабочих часа с приостановкой вне графика (TIM-05).
- Кабинет: реестр правил с версиями, границы TIM-07 (`RULE_LEGAL_BOUNDARY`), ошибки доставки; бот: настройки уведомлений.

Критерий: сценарии TIM/NTF: задержки не обнуляются, запущенные сроки живут по прежней версии (TIM-04), пустая сводка не отправляется, ошибки доставки видны администратору.

### VS-6 — Платные работы (M)

- Таблицы: service_catalog_item, payment_order, estimate, payment ([LLD-02](02-data-model.md), раздел 7).
- Потоки PAY-01–12: каталог (утверждает только председатель), согласование цены/сметы и явное согласие плательщика, счёт в финкарточку бота (PAY-03/06), квитанция → «Ожидает проверки», ручная сверка с проверкой повторного использования квитанции (PAY-07), исправление с сохранением прежней записи (PAY-10), отмена с фиксацией объёма/расходов/возврата (PAY-09), `work_permission` отдельно от денег (PAY-08).
- Кабинет: каталог, сметы, заказы, сверка; бот: финансовая карточка плательщика без остальной переписки.

Критерий: сценарии PAY: ручная сверка, независимость статусов работы и расчётов, повторная квитанция отклоняется, финансовый файл недоступен исполнителю по прямой ссылке.

### VS-7 — Аварии и публикации (M)

- Таблицы: incident, incident_scope, incident_log, publication, publication_scope ([LLD-02](02-data-model.md), разделы 5–6).
- Переходы инцидента (модель процессов, раздел 6); адресные обновления по `incident_scope` (EMG-06); частичное восстановление не завершает инцидент; ошибочное завершение — возобновление.
- Массовая рассылка: `broadcast.fanout` с лимитом скорости и дедупом; проверка целевого времени прохождения (≤ 15 мин `[допущение]`) после утверждения целей 5.2.
- Публикации: объявления, отключения, отчёты работ, финансовый отчёт с разрешением председателя (FIN-01–04); аудитории и области.

Критерий: сценарии EMG/PUB: частичное восстановление, аудитория по объектам без дублирования, время прохождения рассылки (тест), инцидент не завершается таймером.

### VS-8 — Документы, опросы, инициативы, отчётность (M)

- Таблицы: document, document_scope, document_version, poll, poll_answer, initiative, initiative_support, initiative_comment, moderation_action ([LLD-02](02-data-model.md), раздел 8).
- Документы: версии без перезаписи, проверяющий по типу (WRK-17–18), отметка `needs_fix` с сохранением истории; интеграция с снимком комплекта в VS-3 (устаревший комплект не принимается).
- Опросы: один ответ на человека, исключение при потере права; инициативы: аудитория по подтверждённым связям, комментарии без телефона/помещения (IDEA-02); модерация без правки чужого текста, оспаривание — председатель (MOD-03).
- Отчёты REP-01–04 (роли и области), экспорт Excel очередью с журналированием (REP-05), без телефонов/переписки/вложений; KPI с исключением тестовых персон.

Критерий: сценарии WRK-17–18, POL/IDEA/MOD, REP (раздел 15.2).

### VS-9 — Приватность, журнал, эксплуатация, запуск (M)

- `consent`, `privacy_request`, каркас retention (не включается до OQ-12); согласия до обработки (PRV-01).
- Доведение журнала: области AUD-02 для всех доменов, защита append-only (AQ-07 — граница фиксируется).
- OPS: реестр копий (`ops_backup_registry`), контроль возраста (backup.overdue только основному техадминистратору), пробное восстановление в отдельной среде с фиксацией возраста/длительности/результата (OPS-03).
- Мониторинг: выбор инструмента (AQ-04), метрики и алерты [LLD-04](04-background-tasks.md) раздел 7, дашборд.

Критерий: сценарии PRV/AUD/OPS; обязательные проверки допуска (раздел 15.1): пробное восстановление выполнено, секретов и персональных данных в статической сборке нет, копии зашифрованы и вне сервера.

## 3. Сквозные проверки безопасности по срезам

| Сценарий (матрица, раздел 7) | Срез |
| --- | --- |
| Отзыв полномочий запрещает следующий запрос из открытого сеанса | VS-1 |
| Администратор другого дома не экспортирует реестр; жалоба недоступна вне обычной роли | VS-2 / VS-3 |

## 4. Готовность среза (DoD)

1. Миграции в основной ветке; `rls.sql` обновлён при новых таблицах.
2. Модульные тесты: FSM-переходы среза, PDP-сценарии, TIM-интервалы (где применимо); интеграционные: идемпотентность, транзакции, «все или ничего» (где применимо).
3. Критерий среза (раздел 1) выполнен через средство эмуляции на тестовых персонах; эмулированные действия в журнале.
4. Обновлены документы, затронутые изменением (AGENTS.md — команды после VS-0; реестр событий/правил при расширении).
5. Новые privileged-операции внесены в реестр PDP и доступны только в кабинете.

## 6. Первый сквозной сценарий (после VS-3)

Регистрация в боте → подтверждение администратором → создание обращения → разбор → задание → отчёт → приёмка → подтверждение автором. Маркер «каркас и PDP работают насквозь» до расширения доменов (HLD раздел 27, шаг 6).
