# LLD-01: Модули

Основание: [HLD раздел 9–10](../hld.md), [ADR-003](../decisions/003-edge-functions-and-environments.md).

## 1. Структура репозитория

Монорепозиторий в `source/` (сейчас пуст):

```
source/
  db/                        # PostgreSQL: схема, RLS, сиды
    migrations/              # нумерованные SQL-миграции (расширяемые, expand/contract)
    rls.sql                  # включение RLS и запрет прямого клиентского доступа (второй рубеж, AQ-06)
    seed/                    # справочники: категории обращений (OQ-02), стартовый реестр правил TIM
  core/                      # общий серверный код ядра (используется всеми функциями)
    src/
      config/                # env, секреты, константы сред
      db/                    # клиент SQL, транзакции, миграционный хелпер
      errors/                # типы ошибок API (см. LLD-03), маппинг в ответы
      locales/               # тексты уведомлений и меню ru/kk (UI-02)
      pdp/                   # сервис авторизации (PDP)
      fsm/                   # машины состояний: request, task, common_work, incident, document_version
      tim/                   # регламенты времени: правила, версии, рабочий календарь, таймеры
      outbox/                # публикация и чтение событий (outbox)
      jobs/                  # клиент очереди job_queue + реестр обработчиков
      notify/                # диспетчер уведомлений, шаблоны, дедупликация
      telegram/              # клиент Bot API, rate limiter, адаптер webhook
      bot/                   # сценарии бота: анкета, заявка, приёмка, оценка, финансовая карточка, диалоги
      storage/               # закрытые бакеты, подписанные URL, лимиты FIL-01
      audit/                 # append-only журнал AUD-01
      idempotency/           # ключи идемпотентности (REQ-05)
      domains/               # домены (см. раздел 4)
  functions/                 # функции-входы Supabase Edge Functions (тонкие)
    bot-webhook/
    api/
    jobs/
  admin/                     # веб-кабинет: React + Refine Core + Ant Design, Vite (ADR-002)
    src/
      api/                   # клиент REST /v1, auth-провайдер Supabase
      pages/                 # экраны по доменам
      components/
  tools/                     # эксплуатация: бэкап/восстановление, шаблон Excel, сиды
  tests/                     # модульные, интеграционные, сквозные (стратегия — HLD раздел 19)
```

Правила: `functions/*` не содержит бизнес-правил — только транспорт, вызов `core` и ответы; `core/*` не знает о HTTP-фреймворке функций; `admin/*` не обращается к PostgreSQL напрямую (только REST `/v1`, допущение HLD раздел 7).

## 2. Функции-входы (Edge Functions)

| Функция | Триггер | Ответственность | Защита |
| --- | --- | --- | --- |
| `bot-webhook` | POST от Telegram Bot API | проверка секрета, дедуп `update_id`, быстрые ответы, постановка тяжёлых шагов в `job_queue` | `X-Telegram-Bot-Api-Secret-Token` |
| `api` | POST/GET/PATCH/DELETE `/functions/v1/api/v1/*` | единый роутер REST `/v1`: аутентификация, PDP, идемпотентность, аудит, outbox | Bearer JWT (Supabase Auth); anon-доступа нет |
| `jobs` | вызов по расписанию (pg_cron → pg_net) | слив очереди `job_queue`, свип таймеров TIM, порции длинных задач | JWT service-role + заголовок `x-jobs-secret` |

Пределы вызова (Cloud: ~150 с CPU / 400 с wall `[согласовано 16.10.2026]`; self-hosted настраиваются) учитываются: `jobs` работает бюджетами по ~50 с и возвращает управление; продолжение — на следующем тике (детали в LLD-04). Один ответ на webhook Telegram — до 10 с `[согласовано 16.10.2026]`: лёгкие действия выполняются сразу, остальное — через очередь.

## 3. Ядро: общие модули

### 3.1. `pdp` — сервис авторизации

Контракт (единиственный способ проверки доступа в системе):

```ts
can(actor: Actor, action: string, resource: ResourceRef): Decision
// Decision = { allow: true } | { allow: false; reason: string; code: 'FORBIDDEN' }
```

- `Actor` = профиль + человек + действующие `staff_assignment` (роль, область, спецправа, срок) + связи `connection` + участие в обращении + эмуляция (если активна).
- Оценка по шести измерениям (ROL-01, матрица раздел 1): роль/полномочие → область домов → связь с помещением → участие → аудитория данных → состояние процесса; плюс срок полномочий и проверка отзыва при каждом вызове.
- Правила совмещения: ROL-02d (председатель не принимает собственную работу и не утверждает собственные сметы), CMP-01 (жалобы), CMP-02 (передача при конфликте интересов), ROL-06 (доступ поддержки по отдельному разрешению с причиной/сроком).
- Deny-by-default. Привилегированные действия (AUTH-03) требуют: канал «кабинет» + действующее спецправо; на пилоте — вход Telegram OIDC, после пилота дополнительно подтверждение TOTP (механизм — открытая точка AQ-02).
- Решения кэшируются в пределах одного запроса; журнал решений пишется при privileged-действиях, экспортах и отказах.

Реализация — данные + чистые функции (без БД-запросов внутри оценки): сборка Actor выполняется репозиторием, оценка — детерминированная, тестируется таблицей сценариев (матрица раздел 7).

### 3.2. `fsm` — переходы состояний

- Таблицы переходов объявлены кодом из модели процессов (разделы 4–6): `{from, to, who, guards[], effects[]}`; таблица — единственный источник, схема БД и UI её отображают.
- Применение перехода — одна транзакция: `SELECT ... FOR UPDATE` агрегата → проверка текущего состояния и полномочий (PDP) → запись перехода в `*_log` → изменение состояния → события в outbox (FLOW-01).
- Конкурентность: колонка `version` у агрегатов; несовместимое параллельное действие возвращает 409 с актуальным состоянием (FLOW-01).
- Повтор того же действия (идемпотентность) не создаёт повторных событий — через `idempotency_key` (LLD-03, раздел 2.4).

### 3.3. `tim` — регламенты времени

- Реестр правил `time_rule`/`time_rule_version` (ключи и стартовые значения — LLD-02, раздел 11); таймер (`timer`) хранит `rule_version_id` — запущенный срок живёт по прежней версии (TIM-04).
- Рабочий календарь: параметры графика (08:00–20:00 Asia/Almaty `[согласовано]`) внутри версии правила; расчёт «N рабочих часов» и «N календарных часов» — чистые функции с тестами (REG-14, 48-часовые интервалы REG-04/WRK-07, 72 ч REG-03).
- Правовые правила (`kind='legal'`) имеют `source` и границы; обычная настройка не может их нарушить — проверка при сохранении версии (TIM-07).
- Действия по истечении — только напоминание/эскалация/передача; автоматической смены человеческих состояний нет (HLD 10.5).

### 3.4. `outbox` + `jobs`

- `outbox.publish(event, payload)` внутри той же транзакции, что и бизнес-изменение (HLD 12.2); состав событий фиксирован (LLD-03, раздел 5).
- Обработчик outbox → перевод события в уведомления/задачи; `job_queue` — единица исполнения с повторами (LLD-04). Ничего, что должно произойти «само», не вызывается напрямую из API — только через очередь.

### 3.5. `notify`, `telegram`, `bot`

- `notify`: резолвинг получателей, дедупликация по ключу события, выбор канала (`telegram` / `simulator` для эмуляции), запись результата и ошибки доставки (NTF-02); шаблоны ru/kk в `locales` (UI-02); пустой дайджест не отправляется (NTF-01).
- `telegram`: клиент Bot API с токеном-бакетом (лимиты, обработка 429 + `retry_after`); идемпотентность входящих по `update_id`; вложения — не через Telegram-файлы как источник истины, а через Storage.
- `bot`: сценарный конечный автомат диалогов, состояние в `bot_dialog` (ADR-003); команды: анкета/добавление помещения (REG-01–02, REG-08), создание заявки (REQ-01–05), принятие задания/отчёт/визит (WRK-02–06, JOB-04), подтверждение результата (WRK-07–08), оценка (RAT), финансовая карточка плательщика (PAY-03/06). Привилегированных действий у бота нет (AUTH-03).
- Один и тот же сценарный модуль используется webhook-адаптером и симулятором эмуляции (HLD 10.8) — транспорт подменяется, логика общая.

### 3.6. Прочие модули ядра

- `storage`: приватные бакеты по аудиториям (жительские/внутренние/финансовые/служебные); выдача короткоживущих подписанных URL только после PDP (модель процессов раздел 8); проверки размера/количества/типа (FIL-01); отметка неполных вложений (FIL-02).
- `audit`: append-only записи; для эмуляции — реальный актор + эмулируемая персона (AUD-01); тег области чтения (`scope_buildings`) для AUD-02.
- `idempotency`: хранение результата по ключу операции (REQ-05, OPS-01).
- `config`: секреты (токен бота, OIDC Client Secret, service-role key, `x-jobs-secret`) только из env сервера; в `admin` — publishable key (ADR-001/002).

## 4. Домены `core/domains`

Каждый домен — модуль с публичным сервисом (функции-операции) и собственными таблицами; домены не импортируют таблицы друг друга напрямую — только через публичные сервисы и события outbox.

| Домен | Публичный сервис (пример операций) | Основные требования |
| --- | --- | --- |
| `registry` | лица, объекты, связи, приглашения, импорт/экспорт | REG, IMP, ROL-02 |
| `registrations` | анкеты, подтверждение, споры, эскалации | REG-01–14 |
| `requests` | жизненный цикл, переписка, участники, оценки | REQ, SHR, MSG, FLOW |
| `tasks` | задания, отчёты, визиты, приёмка, общая работа, шаблоны | WRK, JOB |
| `incidents` | инциденты, охват, обновления | EMG |
| `documents` | документы и версии, проверки, аудитории | DOC, WRK-17–18 |
| `payments` | каталог, сметы, заказы, платежи, сверка, возвраты | PAY |
| `publications` | объявления, отключения, отчёты работ, финотчёты | PUB, FIN |
| `polls` | опросы, ответы | POL |
| `initiatives` | инициативы, поддержка, комментарии, модерация | IDEA, MOD |
| `reports` | отчёты REP-01–05, экспорт Excel | REP |
| `regulations` | правила TIM, версии, границы | TIM |
| `notifications` | настройки уведомлений, журнал доставки | NTF |
| `files` | подписанные URL, лимиты | FIL, MSG-03 |
| `audit` | чтение журнала по областям | AUD |
| `admin` | роли, полномочия, области, сеансы, перенос привязки | ROL, AUTH |
| `emulation` | тестовые персоны, эмулированные сеансы, симулятор | пилот, HLD 10.8 |
| `ops` | реестр копий, напоминания о возрасте копий | OPS-03 |
| `privacy` | согласия, запросы удаления | PRV |

Направление зависимостей: `domains → {pdp, fsm, tim, outbox, storage, audit, idempotency}`; `requests ↔ tasks` — через сервисы (запросы создают задания, задания читают минимальный снимок обращения) без циклов; события вместо прямых вызовов там, где достаточно асинхронности (уведомления, рассылки).

## 5. Веб-кабинет (`admin`)

- Экраны по доменам: реестр и импорт; очередь обращений и карточка (переписка, задания, документы, статусы); задания и общая работа; аварии; документы и публикации; финансы (каталог, сметы, заказы, сверка); опросы/инициативы/модерация; отчёты; регламенты; журнал; права и сеансы; резервные копии; эмуляция.
- Mobile-first для приёма/назначения/ответа/смены статуса; таблицы и массовые действия — для большого экрана (UI-01).
- Вход «Войти через Telegram» (ADR-001); сеанс ≤ 12 ч, бездействие 30 мин (AUTH-06) — контроль на сервере, UI лишь показывает остаток и предупреждает.
- Прямые ссылки на вложения в UI — только через `/v1/files/*` (короткоживущие URL после PDP); в сборке нет секретов и персональных данных (ADR-002).
- Эмуляция: баннер режима, вход под эмулируемой ролью, «входящие» симулятора (HLD 10.8).

## 6. Правила изменения

- Новое состояние/переход → сначала модель процессов, затем `fsm` и миграция; таблица переходов — источник для модульных тестов.
- Новая privileged-операция → список AUTH-03 в коде PDP (единый реестр действий с флагом privileged и требуемым спецправом) + кабинет-only.
- Схема БД меняется только миграциями (expand/contract, HLD раздел 20); RLS-файл пересматривается при каждой новой таблице.
