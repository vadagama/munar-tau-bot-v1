# LLD-01: Модули

Основание: [HLD раздел 9–10](../hld.md), [ADR-003](../decisions/003-edge-functions-and-environments.md).

## 1. Структура репозитория

Монорепозиторий в `source/` (фактическая структура, 25.10.2026):

```
source/
  db/                        # PostgreSQL: схема, RLS, сиды
    migrations/              # SQL-миграции (расширяемые, expand/contract); фактический состав — каталог
    rls.sql                  # включение RLS и запрет прямого клиентского доступа (второй рубеж, AQ-06)
    seed/                    # identity_dev.sql и справочники: категории обращений (OQ-02), правила TIM
  core/                      # общий серверный код ядра (используется всеми функциями)
    src/
      auth/                  # проверка JWT Supabase (ES256 по JWKS), политика сеансов AUTH-06
      bot/                   # сценарии бота: два бота (ADR-009), нативное меню chat-menu.ts, перенос Telegram-файлов
      config/                # env, секреты, константы сред
      db/                    # клиент postgres.js (createDbClient), транзакции
      domains/               # домены (см. раздел 4)
      errors/                # типы ошибок API (коды — LLD-03 §1.1), маппинг в ответы
      locales/               # тексты уведомлений и меню ru/kk (UI-02)
      pdp/                   # сервис авторизации (PDP): Actor, can(), реестр действий, roles.ts
      templates/             # каталог шаблонов сообщений ru/kk (ADR-010/011) с golden-фикстурами
      testing/               # in-memory фейки доменов для модульных тестов
  functions/                 # функции-входы Supabase Edge Functions (тонкие)
    api/                     # маршруты группами: handlers.ts + <домен>-handlers.ts
    bot-webhook/             # вебхук двух ботов (ADR-009): /bot-webhook/resident и /bot-webhook/worker
    jobs/                    # конвейер фоновых задач (состав и порядок — LLD-04)
  admin/                     # веб-кабинет: React + Refine v4 + Ant Design 5, Vite (ADR-002)
    src/
      api/                   # клиент REST /v1, auth-провайдер Supabase
      pages/                 # экраны по доменам (см. раздел 5)
      components/
  landing/                   # публичный лендинг жителей: статический HTML/CSS (ADR-007, отдельный Pages-проект)
  tools/scripts/             # эксплуатация: set-bot-commands/webhooks, check-bot-health, импорт/экспорт, деплой, проверка секретов
  supabase/                  # config.toml (verify_jwt по функциям); миграции и сид — symlink на db/
```

Тесты лежат рядом с кодом (`*.test.ts` в `core`, `admin`, `functions`), отдельного каталога `tests/` нет. Правила: `functions/*` не содержит бизнес-правил — только транспорт, вызов `core` и ответы; `core/*` не знает о HTTP-фреймворке функций; `admin/*` не обращается к PostgreSQL напрямую (только REST `/v1`, допущение HLD раздел 7).

## 2. Функции-входы (Edge Functions)

| Функция | Триггер | Ответственность | Защита |
| --- | --- | --- | --- |
| `bot-webhook` | POST от Telegram Bot API: `/bot-webhook/resident` и `/bot-webhook/worker` (базовый путь — жители; ADR-009) | проверка секрета (свой у каждого бота), дедуп `(bot, update_id)`, быстрые ответы, постановка тяжёлых шагов в устойчивые очереди | `X-Telegram-Bot-Api-Secret-Token` |
| `api` | POST/GET/PATCH/DELETE `/functions/v1/api/v1/*` | единый роутер REST `/v1`: аутентификация, PDP, идемпотентность, аудит, outbox; маршруты сгруппированы в файлах `<домен>-handlers.ts` | Bearer JWT (Supabase Auth); anon-доступа нет |
| `jobs` | вызов по расписанию (pg_cron → pg_net); на демостенде дополнительно быстрый тик каждые 5 с (LLD-04 §2) | конвейер фоновых задач (порядок — LLD-04 §9) | JWT service-role + заголовок `x-jobs-secret` |

Пределы вызова (Cloud: ~150 с CPU / 400 с wall `[согласовано 16.10.2026]`; self-hosted настраиваются) учитываются: `jobs` работает бюджетами по ~50 с и возвращает управление; продолжение — на следующем тике (детали в LLD-04). Один ответ на webhook Telegram — до 10 с `[согласовано 16.10.2026]`: лёгкие действия выполняются сразу, остальное — через очередь.

## 3. Ядро: общие модули

### 3.1. `pdp` — сервис авторизации

Контракт (единиственный способ проверки доступа в системе):

```ts
can(actor: Actor, action: string, resource: ResourceRef): Decision
// Decision = { allow: true } | { allow: false; reason: string; code: 'FORBIDDEN' }
```

- `Actor` = профиль + человек + действующие `staff_assignment` (роль, область, спецправа, срок) + связи `connection` + участие в обращении + эмуляция (если активна).
- Оценка по шести измерениям (ROL-01, матрица раздел 1): роль/полномочие → область домов → связь с помещением → участие → аудитория данных → состояние процесса; плюс срок полномочий и проверка отзыва при каждом вызове.
- Правила совмещения: ROL-02d (председатель не принимает собственную работу и не утверждает собственные сметы), CMP-01 (жалобы), CMP-02 (передача при конфликте интересов), ROL-06 (доступ поддержки по отдельному разрешению с причиной/сроком).
- Deny-by-default. Привилегированные действия (AUTH-03) требуют: канал «кабинет» + действующее спецправо; на пилоте — вход Telegram OIDC, после пилота дополнительно подтверждение TOTP (механизм — открытая точка AQ-02).
- Решения кэшируются в пределах одного запроса; журнал решений пишется при privileged-действиях, экспортах и отказах.

Реализация — данные + чистые функции (без БД-запросов внутри оценки): сборка Actor выполняется репозиторием, оценка — детерминированная, тестируется таблицей сценариев (матрица раздел 7).

### 3.2. `fsm` — переходы состояний

Выделенного каталога `fsm/` нет: таблицы переходов объявлены кодом внутри доменов (например, `domains/tasks/fsm.ts`, `domains/requests`), контракт прежний:

- Таблицы переходов объявлены кодом из модели процессов (разделы 4–6): `{from, to, who, guards[], effects[]}`; таблица — единственный источник, схема БД и UI её отображают.
- Применение перехода — одна транзакция: `SELECT ... FOR UPDATE` агрегата → проверка текущего состояния и полномочий (PDP) → запись перехода в `*_log` → изменение состояния → события в outbox (FLOW-01).
- Конкурентность: колонка `version` у агрегатов; несовместимое параллельное действие возвращает 409 с актуальным состоянием (FLOW-01).
- Повтор того же действия (идемпотентность) не создаёт повторных событий — через `idempotency_key` (LLD-03, раздел 2.4).

### 3.3. `tim` — регламенты времени

Реализация — домен `core/src/domains/timing`: `timing/contracts.ts` (закрытый каталог контрактов TIM-02), `timing/rules.ts` (правила и версии), `timing/request-timers.ts` (таймеры обращений). Контракт прежний:

- Реестр правил `time_rule`/`time_rule_version` (ключи и стартовые значения — LLD-02, раздел 11); таймер (`timer`) хранит `rule_version_id` — запущенный срок живёт по прежней версии (TIM-04).
- Рабочий календарь: параметры графика (08:00–20:00 Asia/Almaty `[согласовано]`) внутри версии правила; расчёт «N рабочих часов» и «N календарных часов» — чистые функции с тестами (REG-14, 48-часовые интервалы REG-04/WRK-07, 72 ч REG-03).
- Правовые правила (`kind='legal'`) имеют `source` и границы; обычная настройка не может их нарушить — проверка при сохранении версии (TIM-07).
- Действия по истечении — только напоминание/эскалация/передача; автоматической смены человеческих состояний нет (HLD 10.5).

### 3.4. `outbox` + `jobs`

- `outbox.publish(event, payload)` внутри той же транзакции, что и бизнес-изменение (HLD 12.2); состав событий фиксирован (LLD-03, раздел 5). Реализация: таблица `outbox` с `dedup_key/attempts/next_attempt_at`, публикация — в доменах (основной случай — `notification.requested` в `domains/notifications/service.ts`).
- Обработчик outbox → перевод события в уведомления/задачи; конвейер исполнения — `functions/jobs` (LLD-04). Ничего, что должно произойти «само», не вызывается напрямую из API — только через очередь.

### 3.5. `notify`, `telegram`, `bot`

- `notify` — домен `core/src/domains/notifications`: доставка (`delivery.ts`), дайджест (`digest.ts`), контакты по ошибкам (`followup.ts`), предпочтения (`policy.ts`); каналы `telegram`/`simulator`, дедупликация по `dedup_key`, запись ошибки доставки (NTF-02); пустой дайджест не отправляется (NTF-01). Реплики и уведомления — только через каталог `core/src/templates/catalog` (ADR-010/011), не строками в сценариях.
- `telegram` — клиент Bot API: отправка в `functions/jobs` (каскад: HTML с разметкой → без `parse_mode` → без клавиатуры), вызовы сценариев — в `core/src/bot`; `setWebhook` (`allowed_updates`) — `tools/scripts/set-bot-webhooks.ts`; вложения — не через Telegram-файлы как источник истины, а через Storage (`request_upload_job`).
- `bot` — сценарии в `core/src/bot`: житель/сотрудник (ADR-009), нативное меню команд (`chat-menu.ts`, 25.10.2026), перенос файлов (`request-files.ts`), диалоги в `bot_dialog_channel`. Один и тот же сценарный модуль используется webhook-адаптером и симулятором эмуляции (`POST /v1/emulation/simulate`) — транспорт подменяется, логика общая.

### 3.6. Прочие модули ядра

- `storage`: приватные бакеты по аудиториям; реализация — `domains/requests/files.ts` (`SupabaseFileStorage`) и API файлов `/v1/files/*` (LLD-03 §2): подписанные URL только после PDP, проверки размера/количества/типа (FIL-01), отметка неполных вложений (FIL-02).
- `audit` — домен `core/src/domains/audit` (`SqlAuditRepo`): append-only записи; для эмуляции — реальный актор + эмулируемая персона (AUD-01); тег области чтения (`scope_buildings`) для AUD-02.
- `idempotency`: middleware `functions/api/http.ts` + таблица `idempotency_key` (endpoint включает person_id, тело хешируется канонически) — REQ-05, OPS-01.
- `auth`: проверка JWT (ES256 по `SUPABASE_JWKS`), сборка профиля и Actor, контроль сеансов AUTH-06 (12 ч / 30 мин бездействия по `access_session`).
- `config` (`core/src/config/env.ts`): секреты (токены ботов, секреты вебхуков, `x-jobs-secret`) только из env сервера; в `admin` — publishable key (ADR-001/002).

## 4. Домены `core/domains`

Каждый домен — модуль с публичным сервисом (функции-операции) и собственными таблицами; домены не импортируют таблицы друг друга напрямую — только через публичные сервисы и события outbox.

> Актуализация (25.10.2026): фактический состав — 16 реализованных доменов, включая `timing` (вместо модуля `tim`, §3.3) и `privacy` (сервис без API-маршрутов). Домены `files`, `payments`, `regulations`, `ops` как отдельные модули не выделены — см. примечания под таблицей.

| Домен | Публичный сервис (пример операций) | Основные требования | Состояние |
| --- | --- | --- | --- |
| `registry` | лица, объекты, связи, приглашения, импорт/экспорт | REG, IMP, ROL-02 | реализован |
| `registrations` | анкеты, подтверждение, споры, эскалации, управление (ADR-016), приглашения-привязки (ADR-020) | REG-01–14 | реализован |
| `requests` | жизненный цикл, переписка, участники, оценки; файлы — внутри домена (`files.ts`) | REQ, SHR, MSG, FLOW, FIL | реализован |
| `tasks` | задания, отчёты, визиты, приёмка, общая работа, шаблоны; FSM переходов — `tasks/fsm.ts` | WRK, JOB | реализован |
| `timing` | правила TIM (`contracts.ts`, `rules.ts`, `request-timers.ts`) | TIM | реализован (вместо домена `regulations`) |
| `incidents` | инциденты, охват, обновления, экстренные сигналы, дежурства | EMG | реализован |
| `documents` | документы и версии, проверки, обязанности | DOC, WRK-17–18 | реализован |
| `publications` | объявления, отключения, отчёты работ, финотчёты, финансовые правила | PUB, FIN | реализован |
| `polls` | опросы, ответы | POL | реализован |
| `initiatives` | инициативы, поддержка, комментарии, модерация | IDEA, MOD | реализован |
| `reports` | отчёты REP-01–05, экспорт Excel | REP | реализован |
| `notifications` | настройки уведомлений, журнал доставки, outbox/dispatch, дайджесты, follow-up | NTF | реализован |
| `audit` | append-only журнал, чтение по областям | AUD | реализован |
| `admin` | роли, полномочия, области, сеансы, перенос привязки | ROL, AUTH | реализован |
| `emulation` | тестовые персоны, эмулированные сеансы, симулятор | пилот, HLD 10.8 | реализован |
| `privacy` | согласия, запросы удаления | PRV | сервис без API (VS-9) |
| `payments` | каталог, сметы, заказы, платежи, сверка, возвраты | PAY | не начат (VS-6) |
| `ops` | реестр копий, напоминания о возрасте копий | OPS-03 | не начат (VS-9) |

Примечания: `files` — не выделен в отдельный домен: подписанные URL и лимиты реализованы внутри `requests` (`files.ts`, `/v1/files/*` — LLD-03 §2); `regulations` — не выделен: правила TIM реализованы доменом `timing` (API `registry/time-rules`, изменения значений версионируются в `time_rule_version`), отдельный API `/v1/regulations/*` (активация версий, правовые границы, диагностика таймеров) не реализован — LLD-03.

Направление зависимостей: `domains → {pdp, auth, config, db, errors, templates, bot}` и события outbox (уведомления, рассылки); `requests ↔ tasks` — через сервисы (запросы создают задания, задания читают минимальный снимок обращения) без циклов.

## 5. Веб-кабинет (`admin`)

- Экраны по доменам: реестр и импорт; очередь обращений и карточка (переписка, задания, документы, статусы); задания и общая работа; аварии; документы и публикации; финансы (каталог, сметы, заказы, сверка); опросы/инициативы/модерация; отчёты; регламенты; журнал; права и сеансы; резервные копии; эмуляция.

> Актуализация (25.10.2026) — фактические маршруты (`admin/src/App.tsx`, React + Refine): сводка `/`; реестр — `/registry/buildings|premises|connections` (разделы с фильтрами), `/registry/phases` (этапы строительства), `/registry-import`, `/invites`, `/registrations` (анкеты и журнал), `/users/residents`, `/users/staff` (ADR-014); обращения — `/requests`, `/settings/requests` (категории); задания — `/tasks`, `/common-works`, `/job-templates`; `/incidents`, `/documents` (+обязанности), `/publications` (включая финансовые правила, пакеты, размещения, архив), `/polls`, `/initiatives` (+модерация), `/reports`; сервисные — `/time-rules`, `/templates` (каталог шаблонов сообщений, ADR-010/011), `/notifications/preferences` и `/notifications/failures`, `/audit`, `/emulation`, `/login`. Не реализованы экраны: финансы-каталог/сметы/заказы (VS-6), резервные копии (VS-9).
- Mobile-first для приёма/назначения/ответа/смены статуса; таблицы и массовые действия — для большого экрана (UI-01).
- Вход «Войти через Telegram» (ADR-001); сеанс ≤ 12 ч, бездействие 30 мин (AUTH-06) — контроль на сервере, UI лишь показывает остаток и предупреждает.
- Прямые ссылки на вложения в UI — только через `/v1/files/*` (короткоживущие URL после PDP); в сборке нет секретов и персональных данных (ADR-002).
- Эмуляция: баннер режима, вход под эмулируемой ролью, «входящие» симулятора (HLD 10.8).

## 6. Правила изменения

- Новое состояние/переход → сначала модель процессов, затем `fsm` и миграция; таблица переходов — источник для модульных тестов.
- Новая privileged-операция → список AUTH-03 в коде PDP (единый реестр действий с флагом privileged и требуемым спецправом) + кабинет-only.
- Схема БД меняется только миграциями (expand/contract, HLD раздел 20); RLS-файл пересматривается при каждой новой таблице.

> Актуализация (25.10.2026): новые реплики бота/кабинета — через каталог шаблонов `core/src/templates` (страница `/templates`, права `settings.templates.read/edit`, ADR-010/011) и локали `core/src/locales`; новые команды и меню бота — `core/src/bot/chat-menu.ts` (области default/ru/kk) + скрипт деплоя `tools/scripts/set-bot-commands.ts`, флаг регистрации в `bot_dialog_channel.menu_registered` (LLD-04).
