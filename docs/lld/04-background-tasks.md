# LLD-04: Фоновые задачи

Основание: [HLD раздел 10.5, 16, 18](../hld.md), [ADR-003](../decisions/003-edge-functions-and-environments.md). Отдельный постоянно работающий процесс отсутствует: всё «само происходящее» — записи в PostgreSQL, обрабатываемые по расписанию.

## 1. Принципы

1. **Три источника фоновой работы:** `outbox` (события бизнес-транзакций), `job_queue` (единицы исполнения с повторами), `timer` (сроки по регламентам TIM). API никогда не выполняет фоновую работу синхронно, кроме выдачи ответа пользователю.
2. **Бюджет вызова:** функция `jobs` работает порциями до ~50 с `[согласовано 16.10.2026]` и завершается; продолжение — на следующем тике. Ни одна задача не рассчитана на «дождаться окончания» внутри одного вызова.
3. **Повтор — не дубль:** каждая задача имеет `dedup_key` или опирается на состояние предметной записи; повтор не создаёт повторной бизнес-операции (ADR-003, REQ-05, OPS-01).
4. **Планировщик не человек:** таймеры напоминают и эскалируют; автоматической смены состояний, требующих человека, нет (HLD 10.5): ни закрытия обращений, ни завершения инцидентов, ни авто-возобновления.

## 2. Расписание (pg_cron → pg_net)

VS-8 FIN-04: `reopenFinancialObligations` проверяет needs_fix только активной
выпущенной версии под блокировками публикации, версии, документов и обязанности.
Проблема дедуплицируется по версии/документу; повторно открытая обязанность
сохраняет срок. `sweepFinancialObligations` обрабатывает до 20 просроченных
обязанностей в бюджете jobs, уведомляет ответственных и эскалирует председателю.
Повторы дедуплицируются по обязанности/циклу/получателю, test идёт в simulator,
доступ через financialObligationId повторяется перед доставкой.

FIN-01–03: рассылка использует неизменяемую версию выпуска и ключ `financial:<version_id>`.
Ссылка `financialVersionId` проходит через outbox, дайджест и конечную очередь.
Собственность в домах этой версии проверяется при dispatch и send; после утраты
связи текст исключается из дайджеста и уведомление отменяется. Test идёт только
в simulator. Кнопки открывают конкретную версию или обязанность; чтение файла
вновь проверяет PDP версии, приложения и контекст карточки.

| Расписание | Вызов | Назначение |
| --- | --- | --- |
| каждую минуту | `POST /functions/v1/jobs` (JWT service-role + `x-jobs-secret`) | свип таймеров TIM + слив очереди `job_queue` |

## 3. Обработчик `jobs`

Алгоритм одного вызова:

1. Аварийный возврат: задачи в `state='running'` с `locked_at` старше 10 мин → `queued` (счётчик попыток растёт).
2. Свип TIM: `timer` с `state='scheduled' AND due_at ≤ now()` → выстрел (раздел 5), батчами по 100.
3. Слив очереди: `job_queue` `state='queued' AND run_after ≤ now()` — заявка батча `FOR UPDATE SKIP LOCKED` (до 20 задач), исполнение до бюджета ~50 с; незавершённое — освобождение и продолжение на следующем тике.
4. Проведение `outbox`: необработанные события → порождение задач (раздел 4.1), пометка `processed_at`.

Параллельность: один активный вызов `[согласовано 16.10.2026]` (advisory-lock в PostgreSQL; второй вызов завершается сразу). Рост нагрузки — второй экземпляр с другим ключом блокировки (HLD раздел 17).

## 4. Типы задач (`job_queue.kind`) и повторы

Общая политика: `max_attempts=5`, пауза 1 мин → 5 мин → 15 мин → 1 ч → 6 ч; далее `dead` и событие для алерта (NTF-02, HLD 18).

| Kind | Что делает | Особенности / повторы |
| --- | --- | --- |
| `outbox.dispatch` | событие → уведомления/задачи (резолвинг получателей, аудитории) | дедуп по `notification.dedup_key`; ошибки получения — повтор |
| `notify.send` | одно уведомление получателю (Telegram или симулятор) | 429 → пауза по `retry_after`; блокировка бота пользователем → `failed` с кодом `BLOCKED_BY_USER`, видна админу (NTF-02); результат пишется в `notification` |
| `broadcast.fanout` | массовая рассылка (инцидент) → `notify.send` на получателя | приоритет ниже личных; лимит ~20 сообщ./с `[согласовано 16.10.2026]` с джиттером; полный разлёт по ~45 домам — цель ≤ 15 мин (предложение, точка Ф-1; раздел 5.2 HLD); дедуп по (событие, получатель) |
| `tim.sweep` | выстрелы таймеров (см. раздел 5) | идемпотентно по состоянию таймера |
| `import.process` | валидация Excel чанками по 500 строк; отметки ошибок; затем единый commit (IMP-02) | состояние в `import_batch`; повтор продолжает с последнего чанка; commit — одна транзакция; объём пилота (реестр ~600 квартир) укладывается в один вызов `[согласовано 16.10.2026]` |
| `report.export` | формирование Excel-выгрузки (REP-05) | файл → Storage (service), ссылка создателю; журналирование |
| `digest.daily` | сводка публикаций за день для выбравших режим | пустой получатель — пропуск (NTF-01); время — из версии правила `digest_time` |
| `backup.check` | возраст последней полной копии (БД+файлы) | > 24 ч `[согласовано 16.10.2026]` → `backup.overdue` только основному техадминистратору (OPS-03) |
| `privacy.retention` | применение правил хранения (OQ-12) | не включается до заполнения правил; каркас — задачи по `privacy_request` |

Задачи, порождённые действиями пользователя (импорт, экспорт), приоритетнее фоновых свипов.

## 5. Движок TIM

- **Правила и версии:** `time_rule`/`time_rule_version` (LLD-02, раздел 9). Сохранение версии проверяет границы: правовые правила (`kind='legal'`) не изменяются обычной настройкой за допустимой границей (TIM-07, `RULE_LEGAL_BOUNDARY`).
- **Таймер:** создаётся при бизнес-событии (получен номер, задан вопрос, отправлен отчёт, приглашение создано, копия устарела…) и хранит `rule_version_id` — уже запущенные сроки живут по прежней версии (TIM-04). Отмена таймера — при погашении события (ответ получен, задание принято).
- **Рабочий календарь:** расчёт `due_at`: для «рабочих часов» — приращение только внутри графика из версии правила (08:00–20:00 Asia/Almaty `[согласовано]`); для «календарных часов» — прямое приращение (48 ч REG-04/WRK-07, 72 ч REG-03). Вне графика отсчёт приостанавливается (TIM-05, REG-14).
- **Действия при выстреле** (из `params.contract.action`): напоминание ответственному; эскалация следующему уровню (REG-14: администратор → заместитель → председатель, 12 рабочих часов без реакции на каждом этапе, только в пределах полномочий); передача спора (REG-05); напоминание автору (WRK-07); напоминание о копии (OPS-03). Уведомление дежурным/админам — через `notify.send`, дедуп по (таймер, этап).
- **Свип:** каждые 60 с; выстрел пишет `fired_at`, состояние `fired`, событие `timer.fired` → задачи. Погашенный до выстрела таймер — `canceled` (без действий).

Сценарии: «исполнитель не принял назначение» — задание ждёт, эскалация админу, ложного начала нет; «автор молчит» — напоминание и проверка админом, без автозакрытия; «просрочка не обнуляется» — `overdue_since` хранится отдельно от состояний (FLOW-04).

## 6. Уведомления (NTF)

Пайплайн: `outbox` → `outbox.dispatch` → `notification` (queued, дедуп) → `notify.send` → Telegram/симулятор → `sent|failed` (+`last_error`).

- Шаблоны ru/kk в `core/locales`; получатель — по событию и предпочтениям (`notification_pref`); обязательные согласования видимы в карточке независимо от настроек (FLOW-03).
- Финансовые уведомления — только плательщику; внутренние причины — переводом в объяснение для жителя без служебной переписки (FLOW-03).
- Ошибки важной доставки видны администратору (NTF-02); полная недоступность Telegram — принятый риск (NTF-01, OPS-01).
- Rate limit: глобальный токен-бакет на токен бота (лимиты Bot API), приоритет: аварийные → личные → дайджест; повтор по 429 с `retry_after`.

## 9. Независимый этап VS-5: исполняемый контракт

Текущий `jobs` удерживает транзакционную advisory-блокировку `(814733,6)` на отдельном соединении до окончания вызова. Второй вызов возвращает `busy`; бизнес-операции выполняются собственными короткими транзакциями и сохраняют выполненные порции при последующей ошибке. Ключ интеграционных тестов `(814733,3)` и ключ изменения регламентов `(814733,5)` отдельные. Пул должен иметь более одного соединения (сейчас max=5).

Бюджет — 45 секунд: последние 15 секунд резервируются для outbox/дайджеста/доставки. Порядок: перенос файлов, регистрационные таймеры, импорт, таймеры обращений, заданий и результата, регулярные шаблоны, outbox, дайджест, отправка. Проверка бюджета происходит между единицами работы; один уже начатый SQL-запрос или HTTP-вызов может закончиться позже границы. Telegram HTTP ограничен 10 секундами.

Предметные очереди `request_upload_job`, `import_batch` и `notification` сохраняются. VS-5 дополнительно использует `job_schedule` → `job_queue` → `job_run` для регулярных шаблонов JOB-05; другие будущие виды очереди не включены. Диспетчер берёт до 100 событий, sender — до 20 сообщений, дайджест — до 20 получателей и 20 элементов на порцию. При отправке есть пауза 50 мс. Отсечка и прогресс сводки сохраняются между тиками.

Отправка — at-least-once: Telegram не принимает ключ идемпотентности, поэтому потеря ответа после успешной сетевой отправки может привести к повтору. Бизнес-событие и задача контакта дедуплицируются. Повторы отправки проверяют доступ и предпочтения заново; утрата права переводит notification в canceled. Исчерпание подготовки текста фиксируется кодом DISPATCH_FAILED, доставки — DELIVERY_FAILED, блокировка бота — BLOCKED_BY_USER. В журнал не попадает текст транспортного исключения.

См. [фактическую приёмку VS-5](../vs5-acceptance.md) для доступных сценариев и оставшихся зависимостей.

### Регулярные задания VS-5 (JOB-05/06)

Расписание задаётся явно в карточке шаблона: дата с часовым поясом, период и срок в календарных часах, необязательный исполнитель. Изменение расписания версионируется и аудируется. Без нормативов принятия/эскалации назначение недоступно; значения не зашиты в код.

Тик блокирует до пяти расписаний (`FOR UPDATE SKIP LOCKED`), материализует до пяти дат каждого. Ключ `(template_id, scheduled_at)` сохраняет каждую пропущенную дату без дублей. Payload содержит версию методички, область домов, тестовый признак и дату срока. Создание общей работы, задания, привязка версии и завершение очереди атомарны; сетевых вызовов внутри нет. После пяти ошибок очередь получает `dead`; явный повтор проверяет текущую и сохранённую область и записывает нового ответственного автора в аудит.

Непринятие задания проходит администратору → заместителю → председателю по сохранённым версиям регламентов. Погашенный таймер отменяется. Просрочка сохраняется как `task.overdue_at` и `job_run.missed_at`, включая отмену/приёмку между тиками. Состояние задания автоматически не меняется. История расписания дополнительно проверяет область каждого запуска; смена области шаблона не раскрывает старые задания.

### Контракт TIM-02

Закрытый каталог `timing/contracts.ts` версии 1 задаёт событие начала, календарную и бизнес-паузу, погашение и идентификатор согласованного обработчика. Новые версии сохраняют снимок в `params.contract`; API возвращает его, кабинет показывает условия только для чтения. Клиент может менять только длительность/график и причину, подмена действия или версии контракта отклоняется. Отсутствующий снимок исторической версии разрешается в исходный контракт v1 по известному ключу без переписывания append-only истории. Неизвестные версии/действия не исполняются. Изменение семантики требует новой версии каталога с сохранением старого обработчика; произвольного FSM/SQL/автозакрытия настройка не разрешает.


## Опросы POL-03 (VS-8)

`closeDuePolls` включён в общий jobs: не более 10 просроченных открытых опросов
с переданным бюджетом. Gate аудитории берётся до строк опроса; повторный запуск
и конкурирующее закрытие не дублируют итог. История всех отвечавших читается
порцией, расчёт использует closes_at слева, не время запуска jobs.
Итог/участники/исключения/аудит и batch outbox фиксируются одной транзакцией.
Закрытие до срока и несогласованный снимок блокируются БД.
`pollId/pollEvent` проходят dispatch и финальную delivery-проверку; старое
приглашение после закрытия/отмены не отправляется. POL-адресаты скрыты из
административных ошибок доставки и ручного followup.
