# ADR-017: контекст ботов и служебная работа с обращениями

Дата: 21.10.2026. Статус: предложено, ожидает согласования технического плана.

## Контекст

[Спецификация](../specs/SPEC-staff-bot-requests.md) расширяет worker-бот
сценариями обработки обращений. Один человек может одновременно вести
регистрацию/обращение в resident и служебный диалог в worker.
ADR-009 оставил `bot_dialog` общим по Telegram ID как временное упрощение.
Теперь оно нарушает необходимую независимость двух рабочих контекстов.

В существующих сценариях обращения и медиа жителя имеют аудиторию resident;
служебный сценарий должен также поддерживать внутреннюю заметку и её файлы.
Очередь «Требуют внимания» требует персонального учёта непрочитанного,
которого пока нет. Роль и отдельный интерфейс не меняют PDP и правила WRK/MSG.

## Предлагаемое решение

1. Добавить закрытую серверную таблицу `bot_dialog_channel` с ключом
   `(bot, telegram_user_id)`, профилем, JSON-состоянием и временем обновления.
   JSON имеет версию формата; контекст эмуляции дополнительно привязан к сеансу.
   Сценарии читают/блокируют/сохраняют его через общий `bot/dialog.ts`
   с явным BotKind и тем же executor, что бизнес-операция.
2. Сохранить прежний `bot_dialog` как снимок для отката, не копировать его
   неоднозначное временное состояние автоматически. При переключении функции
   создают чистую временную форму. Сохранённые бизнес-черновики и объекты
   не удаляются; неподтверждённый ввод предыдущего диалога требуется повторить.
   Пользователь получает понятное сообщение при продолжении старого шага.
   Удаление/архивирование профиля очищает оба хранилища диалогов.
3. Служебные сценарии вызывают общие домены requests/tasks без собственного
   обхода PDP. Служебная ссылка `sreq_<uuid>` только открывает карточку worker,
   прежние resident `req_` и worker `wrk_` сохраняют поведение.
   Ключ операции содержит bot и nonce формы, чтобы update_id разных ботов
   не пересекались в доменной идемпотентности.
4. Добавить закрытые персональные отметки `request_message_read` с ключом
   `(person_id, message_id)`, ссылками на person/message и временем чтения.
   Тексты сообщений и данные заявителя в отметках не копируются.
   Подтверждение отмечает только доступные показанные входящие сообщения
   resident-аудитории. Кнопка «Отметить прочитанным» предотвращает ложную отметку
   страницы, которая только поставлена в очередь доставки.
   Исторические сообщения без отметок считаются непрочитанными.
5. SQL-фильтры очередей, признаки внимания и ограниченные страницы материалов
   принадлежат общему домену и доступны через тонкий API. Прежние вызовы списка
   без новых параметров сохраняют контракт; бот запрашивает по 10 строк.
6. Вложения сотрудника живут в явной форме выбранной аудитории; получение файла
   ставит загрузку в очередь, но не публикует сообщение. Подтверждение после
   успешного сохранения файлов передаёт их в общий `addMessage` нужного канала.
   Автоматического раскрытия внутренних файлов нет.

Новые таблицы получают составные ключи/внешние связи и индексы под фактические
запросы, RLS и запрет прямого доступа anon/authenticated по принятой серверной
модели. Выбор индексов и планы запросов проверяются при реализации.
SQL и миграции этот ADR пока не добавляет.

## Альтернативы

- Сохранить один диалог: меньше изменений, но текст и файлы могут попасть
  в другой рабочий контекст. Не удовлетворяет SBR-12.
- Заменить ключ старой таблицы сразу: компактнее, но старые функции при
  частичном обновлении могут прочитать несколько строк или изменить чужой бот.
  Добавляющая таблица упрощает контроль переключения и откат.
- Хранить оба диалога внутри одного JSON: сохраняет общую блокировку и повышает
  риск потери соседнего состояния при неполном обновлении сценариев.
- Считать прочитанным при создании ответа бота: ответ ещё может не доставиться.
  Отметки доставки требуют нового протокола подтверждения прочтения, поэтому
  для первой версии выбран явный пользовательский шаг.
- Один временной watermark на человека/обращение: компактнее, но требует
  решения порядка конкурентных сообщений и пропусков при постраничном чтении.
  Отметки точных id не помечают непросмотренные страницы.

## Проверки при реализации

- Два одновременных диалога одной персоны; смена сеанса эмуляции; старые формы;
  архивирование; отказ от неподтверждённого ввода без удаления бизнес-черновика.
- Чужой объект/жалоба, отозванная роль, коллизия update_id, повтор callback,
  конфликт версии и атомарный откат создания задания.
- Внутренние медиа не попадают в resident-канал ни при приёме, ни при доставке;
  неготовые/отменённые вложения не публикуются.
- Подтверждение одной страницы не отмечает другие страницы или новое сообщение;
  второй сотрудник сохраняет свой признак непрочитанного.
- RLS-заслон, фильтрация до пагинации, повторяемость миграций и безопасный откат.
