# ADR-019: история аудитории и порядок блокировок опросов

Дата: 23.10.2026. Статус: принято в рамках согласованного плана VS-8 P01.

## Контекст

POL-02/03 требуют исключать ответ при потере последней подходящей связи,
не восстанавливать его автоматически и считать итог на closes_at даже при
задержке jobs. Текущий реестр и журнал действий не восстанавливают это прошлое.
Каскадное удаление помещения также не должно уничтожать доказательство права.

## Решение

Закрытая append-only таблица audience_connection_event хранит снимки связи,
человека, помещения и действующего профиля. Внешних ключей к удаляемым объектам
нет. Триггеры охватывают изменение статуса, режима, человека, здания, дат,
архивирование профиля и удаление. Имена, телефоны и выбор опроса не копируются.
Действующая связь считается подтверждённой по status=active: старые записи
могут не иметь confirmed_at, и отсутствие этой даты не отменяет их права.

Начало истории фиксируется отдельно; миграция снимает исходное состояние
существующих связей, не утверждая ничего о времени до внедрения. Опросы
открываются после этой границы. start_date включительна, end_date включительна
как дата Алматы: в расчёте это полуоткрытый интервал до следующей полуночи.
Истечение даты учитывается без jobs. При чтении в TypeScript время передаётся
целыми микросекундами Unix, без округления timestamptz до миллисекунд Date. Интервалы нескольких связей объединяются;
перерыв в их объединении требует нового ответа после восстановления.

Корневая транзакция, способная изменить аудиторию, первым запросом вызывает
`audience_clock()`: транзакционная advisory-блокировка `(814733,8)`, затем одна
серверная временная отметка на всю транзакцию. Порядок: gate → строки домена.
Это относится к реестру, импорту, регистрации, созданию тестовой персоны,
существующим внешним транзакциям inbound бота и simulate, а также будущим
операциям ответа/закрытия опроса. Вложенные операции используют тот же executor.
API не получает новую внешнюю транзакцию: auth/session остаются autocommit.

BEFORE STATEMENT триггер берёт тот же gate перед обычным прямым DML.
Скрипт, который предварительно делает SELECT FOR UPDATE/LOCK, обязан вызвать
`audience_clock()` раньше этих блокировок. Одного row-trigger недостаточно:
каскадный писатель мог бы держать gate и ждать строку другого писателя,
уже ожидающего gate. Общее направление блокировок устраняет этот цикл.
Не связанные с аудиторией транзакции документов/финансов этот gate не берут.

Все снимки атомарного переноса имеют одну отметку; промежуточное состояние
внутри транзакции не создаёт разрыв. Откат убирает снимки вместе с изменением.
Закрытие ждёт предшествующих писателей и вычисляет историю на closes_at;
более поздние изменения не меняют сохранённый итог. Приём ответа дополнительно
сверяет реальное серверное время со сроком, после ожидания блокировки.

## Альтернативы и ограничения

Чтение только текущих связей меняет поздний итог. Логирование только в сервисе
пропускает SQL и каскады. Gate в row-trigger даёт обратный порядок блокировок.
Глобальная блокировка всех бизнес-транзакций неоправданно задерживает документы
и финансы. Отслеживание commit timestamp потребовало бы изменения платформы.

Один gate сериализует изменения аудитории и операции опросов всей ОСИ. Для
масштаба одной ОСИ это принимается вместо нескольких независимых блокировок,
которые сложно упорядочить при массовом переносе и удалении здания.
Перед расширением на несколько ОСИ границу блокировки нужно пересмотреть.
История не является административным API персонального выбора или экспортом.

## Проверки при реализации

- Все корневые и вложенные пути соблюдают gate → row locks.
- Отзыв, восстановление, смена режима/здания/человека, архив и каскады пишут снимки.
- Две конкурентные транзакции и закрытие не создают deadlock/потерянную историю.
- Границы дат, последняя/вторая связь, восстановление и задержанный итог проверены.
- RLS закрывает историю для anon/authenticated; изменения истории запрещены.
