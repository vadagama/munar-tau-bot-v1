# ADR-014: управление сотрудниками перечнем ролей и наследование полномочий

Дата: 18.10.2026. Пользователь согласовал реализацию после уточнения интерфейса и иерархии. Уточняет ADR-013, ROL-01–04, AUD-02 и DOC-03.

## Контекст

Служебные назначения и их API существуют, но страница сотрудников не позволяла управлять ими. Пользователю нужен выбор зарегистрированного человека и перечень ролей; дома, сроки и специальные переключатели отложены. Старшая роль должна включать возможности младших. Изменение полномочий должно приходить самому пользователю в Telegram.

## Решение

1. Статус сотрудника вычисляется по действующим назначениям. Первая роль делает пользователя сотрудником; снятие последней прекращает служебный доступ. Person/profile, связи с помещениями, обращения, история и авторство сохраняются.
2. UI `/users/staff` использует PageLayout, DetailSection, CardDrawer и ActionPanel по образцу Обращений. Действия: добавление из зарегистрированных пользователей, изменение набора ролей, прекращение полномочий, повторное назначение. Поля — роли и причина. Фильтры — имя/телефон, роль и состояние. Карточка показывает роли, наследуемые возможности, количество открытых обязанностей и историю.
3. Иерархия: председатель → администратор → заместитель → исполнитель. Заместитель и выше также наследуют дежурного, проверяющего документов и finance. Технический администратор — отдельная системная роль. Наследование вычисляется при сборке Actor на каждый запрос; дополнительных строк staff_assignment нет. API разделяет assigned_roles и effective_roles.
4. Обычное управление разрешено только вниз по иерархии, для другого человека. Председатель и техадминистратор не назначаются/не снимаются обычной формой: остаются отдельные системные процедуры. Самоповышение, изменение равного/старшего и управление из эмуляции запрещены.
5. Служебные полномочия временно действуют по всему ОСИ. Сохранённые staff_scope не удаляются, но в этом режиме не ограничивают служебную область. Каталог домов берётся сервером при сборке Actor. У новых назначений нет сроков; прежние valid_from/valid_until продолжают проверяться до их отдельного пересмотра. UI показывает будущие назначения отдельно.
6. Финансовые возможности следуют роли finance и старшим деловым ролям. Экспорт персонального реестра и управление регламентами доступны администратору и председателю. Старые специальные флаги не повышают младшие деловые роли. Отдельные настройки прав в UI отсутствуют; технические полномочия не наследуются деловой иерархией.
7. Наследование не отменяет назначение конкретного исполнителя, доступ по связи с объектом, ограничения жалоб, финансовые аудитории и запрет собственной приёмки. Дежурства и ответственные объекты по-прежнему требуют отдельного назначения.
8. Запись целого набора атомарна: серверная авторизация, блокировка персон инициатора/получателя по id, повторная сборка Actor, проверка expected_version, Idempotency-Key, отзыв/создание назначений, аудит и outbox. Конфликт — 409 без потери ввода; повтор не создаёт второй аудит/уведомление. Снятие роли отзывает прикладные сеансы пользователя. Старые API дополнительно проверяют иерархию целевой персоны и также создают уведомление.
9. Обязательное персональное событие `staff.roles` идёт в worker-бот. Шаблон каталога на ru/kk содержит прежние и новые роли, инициатора, время Алматы и причину. Проверка доставки не требует сохранения служебной роли получателя. Test остаётся в simulator; окончательная ошибка видна в штатном журнале недоставок.
10. Открытые задания/обращения/настроенные расписания показываются перед прекращением полномочий. Они не закрываются и не передаются произвольному человеку автоматически; остаются доступными управляющим для явного переназначения. Задания отозванного сотрудника недоступны ему по старому назначению.

## Альтернативы

- Отдельный флаг «Сотрудник»: создаёт противоречия с назначенными ролями, поэтому статус вычисляется.
- Полная форма домов, сроков и специальных прав: отложена пользователем.
- Хранить все унаследованные роли отдельными назначениями: усложняет отзыв и историю; наследование вычисляется.
- Скрыть поля без изменения серверных проверок: новые сотрудники не получали бы ожидаемый доступ; отклонено.

## Проверки при реализации

Модульные тесты и API: наследование, системные исключения, управление вниз, подмена тестовой области, отсутствие профиля, отзыв инициатора, версия/409, повтор, аудит и outbox после снятия последней роли. UI: добавление, изменение, прекращение, сохранение ввода при конфликте, единственная шторка. Браузер — тестовые ответы API без БД. Интеграционные сценарии сохраняются без запуска по временному правилу проекта.

Схема БД, зависимости и способ развёртывания не меняются. Деплой — отдельное действие.
