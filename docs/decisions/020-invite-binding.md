# ADR-020: приглашение = регистрация, привязка жильца — отдельное действие

Дата: 24.10.2026
Статус: принято (решение пользователя от 24.10.2026 в обсуждении сценария приглашения; approved «Да, нормальный сценарий. Можно делать»)

## Контекст

Механика REG-03 объединяла три решения в один шаг: собственник до отправки
ссылки выбирал помещение и роль, а принятие приглашения (`/start invite_*`)
одновременно создавало анкету, профиль (если нужно) и активную связь с
помещением. Обсуждение с владельцем 24.10.2026 выявило проблемы:

- сценарий тупиковый для пользователя: `/invite` из главного меню требовал
  «указать номер из списка», которого на экране не было (номер надо было
  взять из `/objects`); ввод числа текстом падал в справку;
- помещение и роль фиксируются до того, как собственник знает, кто именно
  примет ссылку; смена решения означала выпуск новой ссылки;
- приглашение по сути было «прямой выдачей доступа», а не приглашением;
- часть веток сценария стала недостижимой после перехода на кнопки.

## Решение

**Приглашение — только регистрация.** `/invite` без параметров создаёт
приглашение (токен, срок 72 ч по регламенту `invite_expiry`) и присылает
Deep Link. `invite.premises_id` и `invite.role` стали nullable; активные
приглашения старого типа (с помещением) миграция гасит — обратной
совместимости ссылок нет. Принятие ссылки:

- новый пользователь проходит мастер язык → имя → телефон → согласие и
  получает **одобренную анкету без помещения** (модель REG-01/ADR-015);
- уже зарегистрированный пользователь проходит без мастера — ссылка
  помечается использованной (подтверждение личности ссылкой).

**Привязка — отдельное действие собственника.** `/bind`: собственник
выбирает человека из списка «зарегистрировались по моим приглашениям и ещё
не привязаны к моим помещениям», затем помещение (только где он действующий
собственник) и роль — арендатор/проживающий/другое. Связь создаётся сразу
активной (основание: `rent` для арендатора, `family` для остальных),
`confirmed_by` — собственник. Границы доверия: привязать можно только
человека, зарегистрировавшегося по приглашению этого собственника; себя —
нельзя; собственность не выдаётся. Жилец получает уведомление об открытом
доступе. Инициатор получает уведомление о регистрации жильца с кнопкой
«Привязать» (ссылка на человека); в эмуляции — в симулятор.

**Управление — на одном экране `/accesses`.** Две секции: «Выданные
доступы» (привязки: отзыв с обязательной причиной, спор — как раньше) и
«Отправленные приглашения» (неиспользованные ссылки; отзыв без причины,
`status='revoked'`, без уведомления — получатель ещё не зарегистрирован).

**Не меняем:** срок 72 ч и одноразовость (REG-03/TIM), PDP-модель и аудит
(новое действие `connection.bind`, `registration.invite.revoke`), запрет
уведомлений администраторам о привязках (только аудит), поведение
`/objects` и `/add`.

## Альтернативы

- **Оставить объединённый шаг, добавить валидацию аргументов `/invite`.**
  Убирает тупик, но сохраняет фиксацию помещения/роли до отправки ссылки —
  главную претензию владельца.
- **Привязка с подтверждением жильцом (pending-связь).** Дублирует шаг
  согласия, который жилец уже дал при регистрации; собственник хочет
  управлять доступом без лишнего круга. Отзыв связи решает спорные случаи.
- **Ввод Telegram-username жильца для привязки.** Username не хранится в
  профиле и меняется пользователем; надёжная идентификация — через факт
  принятия собственной ссылки, кнопка уведомления устраняет ручной ввод.
- **Хранить список «моих приглашённых» отдельной таблицей.** Достаточно
  связи `invite.used_by_profile → profile.person_id` — новый агрегат не нужен.

## Проверки при реализации

- Миграция только ослабляет ограничения (`drop not null`) и гасит старые
  активные приглашения (`status='expired'` при непустом `premises_id`).
- Модульные (SQL-имитация): `/invite` одним нажатием и отказ не-собственнику;
  полный проход `/bind` (человек → помещение → роль) с аудитом
  `connection.bind`; секции `/accesses` и отзыв приглашения без причины;
  deep-link: новый пользователь → анкета без помещения, существующий →
  consume без мастера; уведомление инициатору с кнопкой `/bind <uuid>`.
- Таймер `invite_expiry` продолжает гасить просроченные приглашения;
  `revoked` таймером не перезаписывается.
- Golden-фикстуры шаблонов обновлены вместе с каталогом (help-full, notices);
  read-only аудит `audit-bot-button-templates.ts` перед выпуском.
- Требования/матрица/HLD обновлены: REG-03 (два шага), access-matrix
  («Привязать приглашённого жильца», «Отозвать отправленное приглашение»),
  модель Invite в HLD.
