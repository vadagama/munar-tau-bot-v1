# ADR-021: AI-ассистент кабинета на Cloudflare Worker и Durable Objects (Pi Durable)

Дата: 2026-10-25. Статус: черновик, на ревью. Направление AI-ассистента и все продуктовые решения согласованы 25.10.2026 в [`docs/ideas/ai-assistant.md`](../ideas/ai-assistant.md) (два раунда челенжа); настоящий ADR фиксирует только выбор рантайма агента и границы безопасности. План реализации — [`tasks/plan-ai-assistant.md`](../../tasks/plan-ai-assistant.md).

## Контекст и драйверы

Нужен AI-ассистент на главной странице кабинета: помнит пользователя и контекст диалога, отдаёт данные строго в рамках его роли, отвечает списками/карточками сущностей со ссылками, строит табличную и графическую аналитику, восстанавливается после сбоев, первый этап — только чтение. Драйверы:

- Память диалога должна переживать перезапуски и деплои, поток ответа — стримиться, сбои — восстанавливаться с чекпоинта. Это профиль «долгоживущего агента», а не обработчика запросов.
- Выбранная основа — Pi Durable (Earendil): запуск Pi-агента внутри Durable Object с SQLite (`pi_*`-таблицы), пробуждение по alarm, восстановление после краша/выселения/деплоя с последнего чекпоинта. Статус beta; проверено по документации 25.10.2026: Cloudflare Agents SDK (≥ 0.30.0, поддержка Pi 1.4) предоставляет `PiHarness`; ограничения приняты в расчёт — нет шага approvals для tool-вызовов, сессии не удаляются, поток событий всегда начинается со снапшота, один вызов модели дольше 15 минут обрезается лимитом alarm.
- Серверный код по ADR-003 — Supabase Edge Functions: изолятные вызовы без собственного хранилища изолята и alarm-цикла. Агентный цикл в них потребовал бы собственный harness с состоянием в PostgreSQL — второй «долгоживущий» механизм рядом с существующей очередью, вопреки замыслу ADR-003 сокращать число отдельных прикладных процессов.
- Доступ к данным — только через существующий API `/v1` с JWT самого пользователя (полный конвейер JWT → профиль → сеанс → Actor → PDP → аудит). Доступ ассистента к БД не предусмотрен принципиально.

## Решение

- Новый npm-воркспейс `source/assistant`: Cloudflare Worker с Durable Object `AssistantDO` — один DO на сотрудника; память диалога в SQLite DO, поверх — `PiHarness` в Lifecycle. Pi изолирован за интерфейсом `ChatRuntime` (фейк в тестах); версии пин (`agents` 0.30.x ↔ Pi 1.4), полноценный fallback заранее не строим.
- Деплой — отдельный `npx wrangler deploy`, вне Cloudflare Pages. Статическая админка по ADR-002 не меняется: Pages Functions не добавляются, бесплатная раздача статики не затрагивается; браузер открывает WebSocket напрямую к Worker (отдельный хост). JWT передаётся первым сообщением WS, не в URL; происхождение кабинета фиксируется секретом `CABINET_ORIGIN`.
- Инструменты агента — единственный путь к данным: read-only вызовы `/v1` с актуальным JWT пользователя, `replay: "safe"`; хук `beforeTool` блокирует всё вне read-only реестра. Нехватка разрезов закрывается новыми read-only агрегатными эндпоинтами API, не расширением полномочий агента. Доступ к БД ассистенту не выдаётся.
- Провайдер модели — DeepSeek (OpenAI-совместимый), единый токен ОСИ (BYOK отклонён). Ключ хранится зашифрованным в PostgreSQL: AES-256-GCM на уровне приложения (`v1:<iv_b64>:<ct_b64>`), ключ шифрования — 32 байта в секрете функций `ASSISTANT_API_KEY_SECRET` (base64). Supabase Vault не используется: рабочая среда — self-hosted (ADR-003), где Vault может отсутствовать, а AES-GCM на уровне приложения работает одинаково в облаке и на self-hosted. Ключ выдаётся по аудируемому `runtime-token` держателю валидного JWT и держится только в памяти изолята — не в SQLite DO и не в браузере (в кабинете — только маска). Секреты Worker: `SUPABASE_URL`, JWKS (публичный), `CABINET_ORIGIN`; секреты функций — `X_ASSISTANT_SECRET` (сервисный учёт расхода) и `ASSISTANT_API_KEY_SECRET` (шифрование токена провайдера).
- Память «05:00 → 05:00» Asia/Almaty: reset по alarm в DO; ручное «Очистить» — пересоздание DO по эпохе `assistant:<profile_id>:<epoch>`. Долгосрочной памяти нет.
- Пилот — только демо-стенд (Frankfurt, вымышленные данные), роли chairman/administrator, у всех сотрудников ассистент по умолчанию выключен (kill switch в «Настройках AI-ассистента»).

### Условия, без которых решение не действует

1. **Read-only на пилоте.** Контур записи допускается позже и только при каждом пишущем действии с явным подтверждением человека в UI — предмет отдельного ADR (срез S5 зарезервирован).
2. **Реальные данные — только после ИБ-анализа и отдельного ADR.** Провайдер DeepSeek находится в КНР (журналирование и обучение на данных — предмет анализа). До того: редакция персональных данных не определена, транскрипты диалогов лежат в Cloudflare DO, то есть вне Казахстана — размещение рантайма ассистента в рабочей среде (Cloudflare против self-hosted в Казахстане, включая вариант собственного vLLM) решается этим же анализом.
3. **Эмуляция исключена:** ассистент выключен в эмулированных сеансах.
4. **Модель не генерирует HTML:** ответ модели — недоверенный ввод (XSS); текст — санитизированный Markdown, таблицы и графики клиент рендерит из JSON инструментов. Числа — только из API.

## Рассмотренные варианты

| Вариант | Почему нет |
| --- | --- |
| Агентный цикл в Supabase Edge Functions, состояние в PostgreSQL | Pi Durable требует JS-runtime с хранилищем изолята и alarm; Edge Functions изолятны — пришлось бы писать свой harness, второй долгоживущий механизм вопреки ADR-003 |
| Ключи и вызовы модели напрямую из браузера | Секрет в браузере — прямое нарушение границ проекта (AGENTS.md «Границы и безопасность»); теряется серверный контроль лимитов |
| Агент ходит в БД / service-role напрямую | Дублирует PDP и аудит, ломает принцип «один серверный API» (HLD §9) |
| Модель рисует графики HTML/кодом | XSS (ответ модели — недоверенный ввод), галлюцинации чисел, чужие стили; виджеты из JSON детерминированы |
| BYOK — личный токен у каждого сотрудника | Сотрудники ОСИ не покупают ключи; per-user лимиты не защищали бы бюджет. Отклонено 25.10.2026 |

## Последствия и ограничения

- В стеке появляется второй рантайм и второй канал деплоя (wrangler) — частичная потеря свойства «весь серверный код в Supabase» из ADR-003; серверные бизнес-правила остаются в Edge Functions, Worker исполняет только агентный цикл.
- Зависимость beta: API Pi Durable меняется; пин версий и изоляция за `ChatRuntime` снижают стоимость замены, но fallback не строится заранее.
- История диалогов живёт в SQLite DO и в PostgreSQL не дублируется: отдельный бэкап диалогов не делается, retention и механика эпох — задача S6.1.
- Стоимость токенов — бюджет ОСИ: единый токен, per-user дневной/месячный лимит, kill switch, append-only ledger расхода с идемпотентностью по `operation_id`.
- Недоступность Cloudflare делает ассистент недоступным, кабинет не блокируется; компенсация организационная — как OPS-01.

## Проверки при реализации

- Версии пин (`agents` 0.30.x ↔ Pi 1.4); тесты идут на фейке `ChatRuntime`, Pi не протекает за интерфейс; транскрипты в `pi_*` переживают рестарт DO.
- `beforeTool` блокирует вызовы вне read-only реестра; тесты на инъекцию инструкций из данных; list-инструменты с жёстким `page_size` ≤ 20.
- Ключ провайдера не встречается в `pi_*`, браузере и сборке (secret-scan); runtime-token выдаётся только включённому профилю с `assistant.use` и журналируется.
- Все чтения — через `/v1` с JWT пользователя под PDP и аудитом; новых полномочий у агента нет; в эмуляции ассистент выключен.
- Учёт расхода идемпотентен по `operation_id`; гейт лимитов выполняется до submit.
- Обрыв WS восстанавливается со снапшота; повтор сообщения гасится `operationId`; alarm 05:00 Asia/Almaty сбрасывает контекст.
- Новый SQL покрыт `schema-drift`-тестом; интеграционные проверки — по действующему правилу (только по явному запросу).
