# ADR-015: Анкета-минимум и обращения без привязки помещения

Дата: 19.10.2026
Статус: принято (решение пользователя от 19.10.2026 в обсуждении сценария)

## Контекст

Регистрация жителя требовала на первом шаге выбрать дом из списка всех зданий, тип и номер помещения и роль. Это усложняло вход: жителю, который просто хочет пожаловаться на проблему во дворе или в чужом подъезде, приходилось привязывать помещение, которого у него может не быть. Обсуждение сценария с владельцем 19.10.2026 (задача «упростить этап регистрации») показало:

- барьер входа завышен: для доступа к обращениям не нужны сведения о помещении;
- список из ~45 домов в чате Telegram неудобен — лучше ввод номера текстом с автопроверкой (как уже сделано для номеров квартир);
- распределение адресных обращений по администраторам на этом этапе не делается (привязки сотрудников к домам нет, служебная область — вся ОСИ по ADR-014);
- анкета привязки помещения остаётся отдельным шагом — существующий `/add`.

## Решение

**Этап 1 — анкета-минимум (REG-01).** `/register` спрашивает только язык, имя, телефон и согласие (PRV-01). В схеме `registration.premises_id` и `role` стали nullable; анкета хранится без них. После подтверждения администратором создаются person+profile без связей — доступ к обращениям открыт, квартирные данные закрыты. Привязка помещения — в любой момент через `/add` (ввод дома текстом с автопроверкой, затем тип, номер, роль и проверка связи как раньше).

**Обращения по адресу (REQ-02/03).** У жителя без подтверждённых помещений шаг «Мои помещения / Общее имущество» пропускается: бот сразу просит адрес одной строкой («дом 107/2, кв 11»). Адрес сохраняется как написан (`location_text`), `premises_id`/`building_id` — NULL, без распознавания дома. Обращение попадает в общую очередь: видят администратор, заместитель и председатель с сохранением правила `chairmanOnly`; место уточняет администратор по REQ-06.

**Файловый диалог (REQ-03).** После описания бот спрашивает «Добавите файл/фото?» [да/нет]; «да» — ожидание медиа, после каждого принятого файла — синхронное «Хотите добавить ещё?»; сохранение файла остаётся асинхронным («Файл сохранён» — из джобы). «Нет» — карточка проверки и отправка.

**PDP.** Для обращений с `premises_id IS NULL` авторство (`active_author`) определяется действующим профилем автора, а не связью с помещением: житель после анкеты-минимум может создать и комментировать обращение. Видимость сотрудникам при `building_id IS NULL` — chairman/administrator/deputy с сохранением `chairmanOnly`.

**Дом текстом (REG-11).** Вместо списка всех домов — ввод «Напишите номер вашего дома (например, 107/2)» с сопоставлением по нормализованному коду: «/», «-», пробелы и ведущее слово «дом»/«үй» равнозначны; не найден — повтор с примером.

## Альтернативы

- **Оставить список всех домов, но с поиском.** Список из ~45 кнопок не помещается в Telegram-клавиатуру и не читается; текстовый ввод с автопроверкой короче и уже проверен на номерах помещений.
- **Распознавать дом из адресной строки и привязывать `building_id`.** Владелец явно отказался: распознавание хрупко («107-2»/«107/2»/опечатки), а автоматическая привязка к дому сужает видимость без пользы — администратор уточняет место по REQ-06. Пересмотр возможен, если адресные обращения станут массовыми.
- **Открывать обращения только после привязки помещения.** Противоречит цели среза: житель с проблемой на территории не обязан иметь помещение.
- **Кабинетная привязка помещения (старые B3/B4 из плана request-flow).** Не входит в срез; привязка через `/add` уже работает. Может быть добавлена позже отдельной задачей.

## Проверки при реализации

- Модульные: анкета без помещения создаётся и эскалируется по NULL (домен); approve без помещения даёт профиль без связей; диалог бота «язык → имя → телефон → согласие»; адресный путь и файловый цикл; автопроверка кода дома; PDP — авторство по профилю и видимость без дома с сохранением `chairmanOnly`.
- SQL: LEFT JOIN анкет в списках бота/джобах/кабинете; `listRequests` допускает `building_id IS NULL` для administrator/deputy.
- Интеграционные тесты сохранены в Git, не запускались по временному правилу от 17.10.2026.
- Миграция только ослабляет ограничения (`drop not null`) — безопасна на существующих данных.

## Последствия

- Адресные обращения скапливаются в общей очереди без маршрутизации по домам — осознанное решение; точка пересмотра при росте нагрузки.
- «Помещение не указано» в анкетах и адрес в обращениях — новая метка в боте и кабинете.
- Деплой: миграция предшествует функциям; новые шаблоны каталога ставятся до или вместе с функциями (ADR-010/011).
