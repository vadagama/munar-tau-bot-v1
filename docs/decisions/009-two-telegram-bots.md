# ADR-009: два Telegram-бота — жители и сотрудники ОСИ

Дата: 17.10.2026. Статус: принято в рамках задачи на разделение ботов.

## Контекст

Единый бот обслуживал и жителей, и сотрудников ОСИ: анкета регистрации (REG),
обращения (REQ), задания исполнителей (WRK), служебные уведомления (NTF, TIM,
дежурство и аварии). Смешение аудиторий мешает работе: исполнителю нужны задания
и служебные эскалации, жителю — статусы анкеты и обращения; меню команд
и справка не могут быть компактными для обеих аудиторий одновременно.
По задаче пользователя создан второй бот `@munar_tau_worker_bot` (токен уже
настроен в среде) — разделить каналы, не меняя бизнес-правил REQ/WRK/REG.

## Решение

Два бота с общим ядром: `resident` — бот жителей (`TELEGRAM_BOT_TOKEN`,
`@munar_tau_user_bot`), `worker` — бот сотрудников (`TELEGRAM_WORKER_BOT_TOKEN`,
`@munar_tau_worker_bot`). Бизнес-домены, PDP и аудит общие; разделяются только
канал доставки и сценарии бота.

> Примечание (22.10.2026): фактически созданный бот жителя имеет username
> `@munar_tau_user_bot` (имя отображения — «Munar Tau Bot»); ранее документ
> ошибочно называл `@munar_tau_bot`, такого аккаунта нет. Глубокие ссылки
> списков обращений берут username из `TELEGRAM_BOT_USERNAME` с фолбэком
> `munar_tau_user_bot` (см. `source/core/src/bot/request-text.ts`).

- **Маршрут webhook** — по суффиксу пути: `/functions/v1/bot-webhook/resident`
  и `/functions/v1/bot-webhook/worker`. Базовый путь без суффикса продолжает
  означать бота жителей (совместимость с уже зарегистрированным webhook),
  иной суффикс — 404. У каждого бота свой секрет
  (`TELEGRAM_WEBHOOK_SECRET` / `TELEGRAM_WORKER_WEBHOOK_SECRET`); регистрация —
  скриптом `tools/scripts/set-bot-webhooks.ts`.
- **Дедупликация** — `bot_inbound` получает колонку `bot`, первичный ключ
  `(bot, update_id)`: нумерации update_id у ботов независимы, прежний ключ
  `update_id` терял бы обновления при коллизиях между ботами.
- **Атрибуция уведомлений** — событийная, по целевому получателю (не по роли
  отправителя): `notification`, `notification_digest_item`, `request_upload_job`
  хранят колонку `bot` (`resident` по умолчанию). В worker-бот уходят задания
  исполнителей и служебные уведомления: назначения/снятия заданий, напоминания
  проверяющим (WRK), служебные напоминания по обращениям (`request.staff`),
  эскалации анкет (REG-14), сигналы и аварии, недоставки важных сообщений (NTF).
  В resident-бот — статусы анкеты, ответы по обращениям, публикации
  и дайджесты жителям. Председатель-собственник получает анкетные статусы
  в resident-бот, а задания — в worker-бот.
- **Файлы** — `request_upload_job.bot` фиксирует принимающего бота: file_id
  в Telegram привязан к боту-получателю, файл скачивается его токеном. Фоновый
  обработчик файлов в `jobs` требует оба токена: без worker-токена обработка
  файлов не выполняется вовсе (файлы заданий отправляются через worker-бот).
- **Дайджест** — worker-бот только если все элементы сводки worker; иначе
  сводка уходит в resident-бот.
- **Диалоги** — `bot_dialog` остаётся общим по `telegram_user_id`. Известное
  упрощение: сценарии одной персоны в двух ботах имеют общий контекст; редкие
  cross-bot сценарии самовосстанавливаются через `/cancel`. Перенос bot в ключ
  диалога — потенциальный последующий эпик, текущим срезом не требуется.
- **Сценарии worker-бота** — задания и файлы заданий (`/tasks`, `/task`,
  отчёты, визиты, проблемы, `/noaccess`), справка по умолчанию. Командные
  меню настраивает `tools/scripts/set-bot-commands.ts` для обоих ботов
  (resident: регистрация и обращения; worker: задания).

Сценарии и права не менялись: сотрудник, не подтвердивший связь с помещением,
по-прежнему не видит данные жителей, в каком боте ни работал (PDP общий).

## Альтернативы

- Один бот с ролями: сохраняет смешение меню/уведомлений и требует от каждого
  получателя фильтрации нерелевантных сообщений.
- Отдельные инстансы всей системы на два бота: дублирует домены и БД ради
  канала доставки.
- Разделение по типу файла/события вместо получателя: житель-председатель
  получал бы служебные сообщения вresident-бот или наоборот — атрибуция
  по получателю предсказуемее.

## Проверки

- Модульные: `botFromPath` (суффиксы, совместимость, 404), переменные среды
  ботов; webhook-тесты: worker-путь с чужим секретом — 401, неизвестный
  суффикс — 404; файлы — токен выбирается по `job.bot` с fallback `resident`.
- Миграция `20261017130000_two_bots.sql` идемпотентна: колонки `bot`
  с default `resident` (существующие записи — бот жителей), составной ключ
  `bot_inbound`.
- `npm run lint`, `npm run typecheck`, `npm test`, `deno task check/lint/test` —
  зелёные. Интеграционные тесты не запускались (правило проекта — только по
  явному запросу); SQL-приёмка миграции на Sydney — при следующем срезе.

## Источники

- ADR-003: общие модули бота и кабинета; ADR-008: аудитория уведомлений.
- Telegram Bot API: setWebhook с `secret_token`, независимые update_id и file_id
  у каждого бота.
- Требования: REG-14, REQ-05, WRK-04/05, NTF-01/02, TIM-05, EMG-05/06.
