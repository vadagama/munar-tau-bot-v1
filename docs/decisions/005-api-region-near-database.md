# ADR-005: регион API рядом с облачной БД

Дата: 2026-10-17. Статус: принято для dev, в рамках ADR-003.

## Контекст

Пользователь наблюдал около 9 секунд загрузки журнала (AUD-02). Dev-БД находится
в `ap-southeast-2`, автоматический выбор Edge Functions из текущей сети —
`eu-central-1`. Конвейер AUTH-06/PDP выполняет несколько последовательных SQL-вызовов.

## Решение

Кабинет принимает публичную необязательную переменную сборки
`VITE_SUPABASE_FUNCTION_REGION`. В dev значение `ap-southeast-2` передаётся
прикладным запросам через `forceFunctionRegion`. Auth URL, полномочия, проверка
сеансов и аудит сохраняются. Пустое значение оставляет стандартную маршрутизацию
и подходит для self-hosted в Казахстане. Не задавать облачный регион для self-hosted.

Выбран query-параметр, поддержанный Supabase для браузера: не требуется расширять
разрешённые CORS-заголовки. Значение региона задаётся для среды, а не зашивается в код.

## Альтернативы

- Кэшировать права: неприемлемо, отзыв роли должен блокировать следующий запрос.
- Переносить dev-БД: отдельная миграция среды, для устранения задержки не требуется.
- Переписывать SQL: пока нет измерений, доказывающих медленное исполнение SQL.

## Проверки и замеры

Три чередующиеся пары одинаковых POST `jobs` с пустой очередью; запросы с локальной
машины, полное время HTTP, включая соединение и чтение ответа. Все ответы HTTP 200,
`processed=0`, `sent=0`; фактический регион проверен по `x-sb-edge-region`.

| Маршрутизация | Замеры, мс | Медиана, мс |
| --- | --- | --- |
| Автоматически, Frankfurt | 6976 / 7051 / 6814 | 6976 |
| Регион БД, Sydney | 2101 / 1183 / 863 | 1183 |

Снижение медианы на 83%. Это контрольный серверный вызов с SQL, а не замер
пользовательской страницы журнала. Браузерный результат после публикации требует
повторного открытия журнала в авторизованном кабинете. Доступа к Chrome пользователя
у агента нет (Computer Use permissions are not granted).

Регрессионный тест проверяет регион, сохранение фильтров журнала и Bearer-заголовка,
а также отсутствие регионального параметра при пустой настройке.

## Эксплуатация

При фиксации региона Supabase не перенаправляет запрос автоматически при его отказе.
Для восстановления сменить регион или очистить переменную и пересобрать кабинет.
При CI-сборке передавать эту переменную в окружение шага Vite вместе с публичными
URL и publishable key. `.env.local` не коммитится.

## Перенос стенда во Frankfurt, 2026-10-17

Пользователь подтвердил ускорение журнала и запросил размещение ближе к Казахстану,
строго бесплатно. Пользователь создал Munar Tau Prod (`ohpjqsudibkcymjjuedy`)
в `eu-central-1`. Кабинет, API, webhook и jobs переключены на этот проект;
`VITE_SUPABASE_FUNCTION_REGION=eu-central-1`. Платные дополнения не включались.

Перед переключением выполнены backup и перенос данных. Содержимое и количество
строк всех 21 прикладных таблиц совпали; Auth users/identities перенесены с теми же
ID, существующие Auth-сеансы не переносились. Объектов Storage не было.
Проверены RLS всех прикладных таблиц, активная роль tech_admin, API/jobs HTTP 200
в новом регионе. Сборка кабинета: `index-CZkhHnpr.js`.

Старый проект сохранён исключительно для интеграционных тестов: CI действительно
очищал общую БД и удалил ручную привязку администратора; запуск был остановлен,
привязка восстановлена перед backup. После переноса TEST_DATABASE_URL остаётся
на старом проекте, его cron выключен. Новый стенд не использовать для тестов с truncate.

Пять health-запросов из текущей сети: медианы Frankfurt 421 мс, Mumbai 432 мс,
Sydney 633 мс. Это ориентир сетевой задержки, не гарантия для всех провайдеров Казахстана.
Облачного региона Казахстана у Supabase нет; рабочая среда с реальными данными
по-прежнему должна размещаться в Казахстане (ADR-003).
