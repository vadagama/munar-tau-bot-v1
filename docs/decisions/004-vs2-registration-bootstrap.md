# ADR-004: Начальная регистрация, временный импорт и идентичность VS-2

Статус: принято для реализации VS-2, 17.10.2026. Основание: REG-01–14, IMP-01–13, ADR-001/003.

## Контекст

Анкета и принятие приглашения начинаются до появления подтверждённой карточки человека и профиля. Значит, диалог и уведомление нельзя требовать привязать к уже существующему profile/person. Подтверждение по реестру не должно автоматически объединять людей по телефону. После восстановления Telegram новый профиль должен подключаться к проверенному входу OIDC, а прежняя привязка — терять прикладной доступ.

LLD задаёт полный будущий контур файлов и очередей. В VS-2 нужен ограниченный импорт первоначального реестра (~600 помещений), без преждевременного внедрения API вложений VS-3 и рассылок VS-7.

## Решение

- До подтверждения диалог хранится по проверенному `telegram_user_id` из private webhook. `profile_id` добавляется при наличии профиля. Выбор языка, ФИО, телефона, помещения, отношения и согласия сохраняется между вызовами. Анкета имеет собственный `is_test` даже при `person_id IS NULL`.
- Импорт принимает `.xlsx` до 5 МБ, четыре строгих листа, не более 5000 строк на лист. Формулы и гиперссылки не принимаются. Сервер хранит разобранный снимок листов в `import_batch.payload`; исходный файл не сохраняется. Отчёт с подсветкой восстанавливается из снимка. Бакеты и ссылки Storage этому пути не нужны.
- Проверка выполняется общей функцией из jobs либо при запросе отчёта. Commit повторяет проверку под блокировкой таблиц и записывает всё одной транзакцией. Вставки идут пакетами по 500 строк через `jsonb_to_recordset`, а не отдельными сетевыми запросами на каждую строку. Соответствия ключей и UUID сохраняются в `import_mapping`. Состояния реализации: uploaded → ready/invalid → committed.
- Сериализованные JSON-параметры в SQL используют явное `text → jsonb`, чтобы postgres.js не кодировал строку повторно. Новые данные хранятся как настоящие JSON-объекты/массивы. Исторические строки аудита нормализуются только при чтении; append-only история не переписывается.
- Четыре начальных операционных регламента: `invite_expiry` (72 календарных часа), `tenant_wait` (48 календарных часов), `registration_stage` (12 рабочих часов), `dispute_total` (36 рабочих часов). Параметры рабочего времени содержат IANA timezone, дни недели и часы открытия/закрытия. Таймер хранит версию; передача сохраняет её и начинает новый локальный интервал в момент фактической передачи. Общий срок спора не переносится.
- Уведомление до привязки адресуется Telegram; после привязки также содержит person. Канал `simulator` сохраняется при постановке и исключает внешнюю доставку. Работа с Telegram вынесена в jobs, с ограниченной порцией, повторами и сохранением ошибки.
- Эмуляция использует тот же сценарий анкеты. Person/profile/registration/premises разделены по `is_test`. Общую структуру зданий из эмуляции менять нельзя. Тестовые персоны со вторичными Telegram-аккаунтами также остаются в тестовом домене.
- При первом входе уже подтверждённого профиля `supabase_user_id` связывается только по закрытой серверной таблице `auth.identities`: `provider='custom:telegram'`, `provider_id=telegram_user_id`. Изменяемые пользователем metadata, телефон, username и email не участвуют. Вход с несколькими связанными identities не используется для автоматического сопоставления. Связывание журналируется; сам вход не создаёт карточку и не выдаёт роль.
- Восстановление выполняется через кабинет по новой серверной анкете и записанному основанию внешней проверки. Отзываются прикладные сеансы, архивируется прежний профиль; новые профиль и OIDC-привязка сохраняют person, назначения и связи. Перенос привилегированного председателя/техадминистратора доступен только другому техадминистратору. TOTP остаётся за пределами среза по принятой границе VS-1/пилота.

## Альтернативы

- Создавать person/profile до сбора анкеты: требует вымышленных телефонов либо ослабления уникальности, усложняет отказ от незавершённой регистрации.
- Сопоставлять по телефону/email/metadata: не обеспечивает проверку Telegram-идентичности и нарушает REG-09/IMP-07.
- Сразу внедрить общий сервис файлов и полный движок рассылок: расширяет VS-2 на последующие срезы без функциональной необходимости.

## Проверки

Unit: форматы, естественные ключи, рабочие интервалы, PDP, отказы по этапу и тестовому домену. Integration: транзакции, pending без доступа, постоянные ID, приглашения, споры, webhook-дедупликация, восстановление и проверенная auth.identity. RLS-заслон распространяется на все новые таблицы. Интерфейс проверяется в Chrome на вымышленных данных.

## Зависимости

ExcelJS закреплён на 4.4.0; используется document-only модуль без потоковых файловых обработчиков. Проверка XLSX проходит в Deno без доступа к filesystem/sys. `npm audit` отмечает транзитивный uuid <11.1.1 ([GHSA-w5hq-g745-h8pq](https://github.com/advisories/GHSA-w5hq-g745-h8pq)): проблема касается v3/v5/v6 с предоставленным буфером. ExcelJS в используемом пути вызывает только v4; код проекта не передаёт ему буферы для UUID. Не выполнялось принудительное обновление исходного React/Refine/AntD стека вне VS-2.
