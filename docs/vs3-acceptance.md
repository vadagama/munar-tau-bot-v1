# Приёмка VS-3 — обращения и переписка

Срез реализован в `feature/vs-3-requests-messaging`. Требования: REQ-01–09,
SHR-01–04, MSG-01–03, RAT-01–03, FIL-01–03, FLOW-01/04, CMP-01/02, AUD-01/02.
Уточнения и граница VS-4 — [ADR-006](decisions/006-vs3-request-files-and-boundaries.md).

## Среда и подготовка

Автоматические интеграционные тесты используют **только Sydney**. Они очищают
прикладные таблицы; старые параллельные CI-запуски без общей блокировки должны быть
завершены. Сам стенд Frankfurt до merge не изменяется. Деплой — после согласования PR.

Тестовым персонам нужны подтверждённые связи с тестовым помещением. Роли не
следуют из имени: персоне «Тест: администратор» отдельно назначаются полномочия и
область. Для проверки SHR используется отдельная персона без служебного назначения.

## Сквозной сценарий

1. Включить эмуляцию подтверждённого тестового жителя. Симулятор → «Обращения».
2. `/newrequest` → номер помещения из предложенного списка, либо
   `дом КОД описание места`, либо `территория описание места` → описание.
3. До `/sendrequest` это приватный черновик без номера. Прервать через
   `/requestcancel`: черновик остаётся. `/newrequest` возобновляет черновик, `/editrequest` меняет описание,
   `/deletedraft` удаляет его.
4. В реальном тестовом Telegram приложить фото/видео/документ. Бот сообщает
   «пока не сохранён»; после обработки `jobs` — «файл сохранён». Сбой файла не
   препятствует `/sendrequest` и выдаче номера `З-ГГ-NNNNN`.
5. Переключиться в кабинете на тестового администратора нужного дома: «Обращения» →
   карточка → классифицировать как «Вопрос» → принять на рассмотрение.
6. Запросить конкретное уточнение. Ответ автора/участника через «Жителю» возвращает
   обращение на рассмотрение; сообщение сохраняет авторство. Молчание ничего не закрывает.
7. Направить итоговый ответ. Автор видит версию результата и подтверждает её;
   участник подтверждать не может. Предлагается необязательная оценка 1–5.
8. В течение 7 дней изменить оценку, затем вернуть закрытое обращение на доработку:
   прежняя оценка остаётся в истории и исключается из текущей. После повторного
   результата требуется новое подтверждение и оценка.

## Команды бота

- `/requests` — мои и явно предоставленные обращения, включая сохранённый черновик.
- `/request НОМЕР` — статус, доступная переписка, версия результата; выбор карточки
  также задаёт обращение для последующих файлов.
- `/say НОМЕР текст` — сообщение «Жителю»; ответ в ожидании уточнения возвращает
  карточку администратору.
- `/confirm НОМЕР ВЕРСИЯ` — подтверждение указанного результата, без подстановки
  новой версии из старого сообщения.
- `/return НОМЕР причина`, `/reopen НОМЕР причина` — доработка.
- `/cancelrequest НОМЕР причина` — отмена до начала или запрос решения после начала.
- `/share НОМЕР ID`, `/unshare НОМЕР ID` — совместный доступ к своей квартире.
- `/rate НОМЕР 1–5 комментарий`, `/appeal НОМЕР причина`.
- `/registration` — выход из диалога обращений в регистрацию.

## Приватность и ошибки

- Собственник без приглашения не видит обращение арендатора.
- Участник видит «Жителю», пишет и добавляет файлы; не видит «Внутреннее», не
  отменяет обращение и не подтверждает результат.
- Внутреннее сообщение нельзя цитировать в жительском канале, его вложения не
  возвращаются в карточке жителя. Прямой запрос `/v1/files/ID/url` получает отказ.
- Отзыв участия/связи закрывает следующий доступ; действия сохраняются.
- Сотрудник другого дома и сотрудник, на которого жалуются, не получают
  внутреннюю карточку. Жалоба на администратора направляется председателю.
- Сохранённые текст/канал сообщения и исходное описание нельзя переписать.
  Исправление — новое сообщение с `corrects_message_id`; ограничение ошибочного
  раскрытия — отдельная операция с причиной и аудитом. Уже доставленные копии
  и выданные на 5 минут ссылки немедленно не отзываются.
- Повтор с тем же Idempotency-Key возвращает прежний результат; другое тело даёт
  409 IDEMPOTENCY_CONFLICT. Устаревшая версия карточки/результата даёт 409.
- До 10 файлов по 20 МиБ на сообщение; последующие сообщения могут содержать
  новые файлы. Повторная загрузка доступна у incomplete; успех — только после complete.

## Граница срезов

Заявки на работу создаются, уточняются, откладываются, отменяются по правилам и
проходят классификацию. Передача результата **работы** заблокирована до VS-4.
Смена вида после начала работ не снимает проверку. Задания, платёжные разрешения,
приёмка документов и полная диспетчеризация TIM не подменяются флагами клиента.

## Автоматические проверки

Из `source/`: `npm run lint`, `npm run typecheck`, `npm test`, `deno task check`,
`deno task lint`, `deno task test`, `npm run test:integration`,
`npm run build -w admin`, `sh tools/scripts/check-build-secrets.sh admin/dist`.

Браузерная проверка интерфейса проводится отдельно от интеграционных тестов БД:
локальные вымышленные фикстуры, desktop и ширина 390 px, каналы и явная аудитория.
Это не означает, что новая версия уже опубликована на демонстрационном стенде.

- Модульные: 209 core + 23 admin; Deno: 38 проверок.
- Полный интеграционный прогон: 26 тестов, 8 файлов. Дополнительно прошёл

  уточнение → результат → подтверждение → оценка; внутренний канал закрыт жителю.
  Воспроизведение: `deno run --allow-env --allow-read --allow-net --config deno.json tools/scripts/check-vs3-api.ts`
  из `source/` (очищает только защищённую проверкой dev-БД).
- Реальный Storage Sydney: загрузка вымышленного PDF, метаданные, подписанное
  скачивание, отказ публичного доступа и удаление тестового объекта.
- Браузер: desktop и 390 px, без переполнения страницы и ошибок JavaScript,
  локальные фикстуры; проверены каналы и настройки вложений.
- Проверки TypeScript, линт, сборка кабинета и сканирование на секреты пройдены.

Интеграционные запуски локально и в CI используют одну блокировку PostgreSQL;
ожидание выполняется короткими `pg_try_advisory_lock`, без длительного SQL-запроса.
