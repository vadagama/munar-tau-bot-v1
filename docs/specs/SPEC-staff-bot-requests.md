# SPEC: обращения сотрудников в Telegram-боте

Дата: 21.10.2026. Статус: проект для согласования; реализация не начата.

## 1. Цель и согласованные границы

Администратор, заместитель и председатель обрабатывают существующие обращения
через бот сотрудников: находят обращение, общаются с жителем, организуют задания,
проверяют результат и передают его на подтверждение. Успех — обычное обращение
проходит этот цикл без обязательного перехода в кабинет.

Решения пользователя:

- Сотрудник создаёт обращение только в кабинете. В worker-боте нет такого действия,
  включая обход через ручную команду или глубокую ссылку. Создание жителем
  обращения в resident-боте сохраняется.
- Во всех функциях обоих ботов управление доступно кнопками. Основной текст
  содержит контекст, вопрос, результат или ошибку; команды и варианты кнопок
  в нём не дублируются. Ручные команды сохраняются для совместимости.
- Исполнителей и другие небольшие наборы вариантов выбирают сразу кнопками,
  без обязательного поиска и пагинации.
- Большие перечни, прежде всего обращения, показываются строками с кликабельными
  номерами. Фильтры, поиск, переходы между страницами и возврат — кнопками.
- Содержательные данные (сообщение, причина, план, срок, поисковый запрос)
  вводятся пользователем по явному приглашению бота.

Предлагаемые параметры первой версии: по 10 обращений на странице; отдельные
разделы карточки вместо длинного сообщения; фильтры статуса, дома и периода.
Эти параметры и точные определения очередей ниже требуют согласования вместе
со спецификацией. Новые бизнес-права и состояния обращений не вводятся.

Сейчас `core/src/bot/inbound.ts` направляет worker-команды в сценарии заданий
и инцидентов; `req_<uuid>` открывается только в resident-боте, `wrk_<uuid>` —
в worker-боте. Домены обращений и заданий уже общие с кабинетом.
`domains/tasks/start-request-work.ts` атомарно создаёт обязательное задание
и переводит обращение в работу. `domains/tasks/assignees.ts` задаёт кандидатов.
Новые сценарии должны использовать эту основу.

Уточнения ADR-014 об области всего ОСИ и наследовании ролей применяются
вместо исторических ограничений ранних документов. Служебная роль сама
по себе не отменяет ограничения жалоб, финансовой аудитории и собственной приёмки.

## 3. Роли и доступ

| Пользователь | Поведение |
| --- | --- |
| Администратор / заместитель / председатель | Раздел обращений и действия по действующим полномочиям на конкретный объект |
| Исполнитель без управленческих полномочий | Свои задания; назначение не открывает исходное обращение и его переписку |
| Сотрудник с совмещением ролей | Совокупность разрешённых действий с сохранением запрета собственной приёмки |
| Техадминистратор | Системная роль не предоставляет обычное управление обращениями |
| Пользователь без действующих служебных полномочий | Нет доступа к служебным очередям и действиям |

Список, количество записей, поиск, карточка, материалы, уведомления и ссылки
соблюдают одну серверную область доступа. Чужой номер не раскрывает наличие,
описание, автора или статус недоступного обращения. После отзыва роли следующая
операция запрещена, даже если кнопка или ссылка осталась в истории Telegram.

## 4. Очереди и поиск

В меню worker-бота доступны «Обращения» и существующее «Мои задания».
Раздел обращений содержит подборки:

| Подборка | Точное определение первой версии |
| --- | --- |
| Новые | Доступные зарегистрированные обращения в состоянии `new` |
| Без заданий | Открытые зарегистрированные обращения без единого связанного задания, независимо от вида обращения |
| Требуют внимания | Открытые обращения с текущей просрочкой, непрочитанным входящим сообщением жителя, неразрешённым отказом исполнителя, отчётом на проверке или ожидающим решением об отмене |
| Сопровождаемые мной | Открытые обращения, где текущий сопровождающий — действующий сотрудник, открывший подборку |
| Все обращения | Все доступные зарегистрированные обращения, включая завершённые; личные черновики исключены |
| Найти по номеру | Приглашение ввести номер и переход к доступной карточке |

Открытые состояния исключают `draft`, `closed`, `canceled`, `rejected`.
Отменённое задание сохраняется связью, поэтому не превращает обращение
в «Без заданий». Оно также не считается выполненным обязательным объёмом.
Отсутствие заданий у вопроса или жалобы само по себе не является нарушением.

Причины внимания показываются явно; одно обращение с несколькими причинами
выводится один раз. Чтение переписки снимает только признак непрочитанного
для читающего сотрудника. Открытие карточки не устраняет просрочку, отказ,
непроверенный отчёт или запрос отмены. Требование о непрочитанном — новое
поведение интерфейса; наличие подходящего учёта чтения нужно проверить в плане.

Строка: кликабельный номер → краткое описание → адрес → статус → актуальная
причина внимания при наличии. Персональные данные заявителя в список не включаются.
Сортировка: текущая просрочка первой, затем наиболее старые обращения;
равные даты разрешаются стабильным порядком по идентификатору.

Фильтры: статус, дом, период регистрации; дополнительно поиск по доступному
тексту. Дом «Не указан» позволяет найти адресные обращения без `building_id`.
Фильтры пересекаются с выбранной подборкой. На первой/последней странице
не показывается недоступный переход; пустая выдача сохраняет кнопки фильтров
и возврата. Фильтрация и проверка прав выполняются до пагинации.

Номер является HTML-ссылкой на карточку в worker-боте, а не декоративным
текстом вида `/request НОМЕР`. Telegram поддерживает передачу `start`-payload
через глубокие ссылки; это не произвольная команда внутри HTML-ссылки.
Формат маршрута определяется в плане, ссылка только открывает карточку
и никогда не изменяет объект. См. [Telegram: Deep Linking](https://core.telegram.org/bots/features#deep-linking).

## 5. Карточка и навигация

Карточка показывает номер, статус, вид, категорию, адрес, описание,
сопровождающего, актуальные сроки и сводку заданий. Текущая просрочка выделена;
историческая просрочка исполненного обязательства не выдаётся за текущую.

Кнопки разделов: переписка, материалы, задания, история; действия процесса —
отдельными кнопками, только при наличии прав и подходящего состояния.
Большая переписка и история читаются страницами. Список заданий использует
кликабельные номера, карточка задания — кнопки действий.

Возврат из карточки сохраняет очередь, фильтры и позицию по возможности;
данные перечитываются с учётом изменений. При исчезновении последней страницы
бот возвращает ближайшую существующую. Прямой вход из уведомления или по номеру
даёт выход в раздел обращений, даже если сохранённого списка нет.

Во время ввода видны кнопки возврата и отмены. Отмена не записывает неполную
бизнес-операцию. Переход к другому объекту завершает текущий ввод без отправки
черновика; сохранённый в диалоге текст не становится сообщением автоматически.
Ввод в resident-боте не должен продолжать либо сбрасывать форму worker-бота
и наоборот. ADR-009 описывает нынешнее общее состояние диалога как упрощение;
способ устранения этого ограничения и необходимый ADR определяются при планировании.

## 6. Действия по обращению

Свободного переключателя статуса нет. Бот предлагает бизнес-действия,
допустимые по общему жизненному циклу и полномочиям.

| Действие | Что требуется и что меняется |
| --- | --- |
| Взять на рассмотрение | Конкретный сопровождающий; само действие не считается первым ответом жителю |
| Уточнить свойства | Вид, категория, срочность, место по существующим правилам; причина и история изменения; аварийность требует отдельных проверок |
| Ответить жителю | Текст/разрешённые файлы, явная аудитория и предпросмотр |
| Внутренняя заметка | Отдельное явно помеченное действие; материалы не уходят жителю |
| Запросить уточнение | Конкретный вопрос, адресат и причина; управление заданиями отдельно, сроки не обнуляются |
| Снять уточнение | Причина достаточности имеющихся сведений, без имитации ответа жителя |
| Начать работу | Исполнитель, план и срок; обязательное задание и переход атомарны |
| Добавить задание | Дополнительный объём к существующему обращению; обязательность определяется явно |
| Запланировать доработку | План исправления, задания и сроки по переходу `plan_rework` |
| Отложить / возобновить | Причина; для отсрочки также дата следующего действия и ответственный; влияние на задания явно фиксируется |
| Передать результат жителю | Проверены обязательные задания и документы; отдельная доступная жителю формулировка и снимок версии результата |
| Отозвать результат | Причина, уведомление жителю, прежний отчёт сохраняется |
| Рассмотреть отмену | Одобрить либо отклонить с причиной и проверкой возможности остановки работ |
| Отказать | Обоснование отсутствия ответственности ОСИ и дальнейший маршрут по действующим правилам |
| Закрыть администратором | Только при основаниях WRK-07/15, проверке и требуемых материалах; отдельная отметка способа закрытия |
| Рассмотреть оспаривание отказа | Доступное председателю решение по существующему переходу; не произвольное открытие отказанного обращения |

Вопрос/жалоба с подготовленным ответом может передаваться на подтверждение
без искусственного задания, если общие проверки разрешают это.
Сотрудник не подтверждает результат от имени жителя. Нереализованные зависимости
VS-6/VS-8 не обходятся ботом: показывается конкретное основание блокировки.

## 7. Работа с заданиями

«Начать работу»: выбор действующего сотрудника кнопкой → план/объём → срок →
предпросмотр → подтверждение. В предпросмотре видны обращение, исполнитель,
описание и срок; адрес и разрешённые материалы доступны исполнителю в задании,
переписка жителя автоматически не копируется.

При небольшом перечне все доступные исполнители показаны сразу кнопками.
Кандидаты берутся из общего `tasks/assignees.ts`; доступность повторно проверяется
при подтверждении. При пустом списке нельзя создать фиктивное назначение.

Сопровождающий обращения и исполнитель задания — разные назначения.
Исполнитель явно принимает или отклоняет задание в существующем сценарии.
Управляющий из связанной карточки может переназначить/отменить задание,
проверить отчёт, принять или вернуть на доработку по общим правилам WRK.
Причины, результаты и сроки сохраняются; собственный отчёт принимать нельзя,
в том числе после переназначения. Смена исполнителя не сбрасывает срок молча.

## 8. Общие требования к интерфейсу и доставке

- Проверка кнопочного пути касается новых и существующих функций обоих ботов:
  регистрация и связи, обращения жителя, задания, инциденты/публикации,
  настройки уведомлений и справка. Это требование доступности существующих
  операций, а не добавление новых доменных возможностей.
- Справка описывает назначение разделов и даёт кнопки входа; инструкции
  «введите /команду» и перечисление вариантов кнопок из тела сообщений убираются.
- Сообщения, ошибки и подписи — каталог шаблонов на ru/kk, язык профиля,
  HTML-экранирование и существующий каскад доставки. Даты — Алматы.
- Уведомления сотрудникам открывают карточку в worker-боте; ответы жителю
  доставляются в resident-бот. Тестовые операции и сообщения — только simulator.
- Старые ручные команды проходят те же PDP, валидацию, аудит и идемпотентность.
  Полномочия проверяются заново на каждом шаге и перед записью.
- При конфликте версии бот показывает актуальное состояние и предлагает
  пересмотреть действие; старая форма не отправляется автоматически.
- Повтор callback/webhook либо подтверждения не создаёт дубликат задания,
  сообщения или перехода. Новое осознанное действие имеет отдельный ключ.
- Ссылка из списка в симуляторе открывает ту же карточку внутри симулятора,
  не отправляет тестовую персону в реальный Telegram и не обходит PDP.
- Финансы, экспорт реестра, права сотрудников и регламенты — кабинет (AUTH-03).

## 9. Технические ориентиры для плана

Стек и границы ADR-003 сохраняются: TypeScript, общие домены, Edge Functions,
PostgreSQL, существующие `BotReply`/кнопки и каталог. Новые зависимости,
SQL-схема, конкретные команды и формат сохранения навигации этой спецификацией
не утверждаются. Архитектурные изменения потребуют ADR.

Затрагиваемые области: `source/core/src/bot/` (маршрутизация, сценарии,
кнопки, симулятор), `templates/catalog/`, общие `domains/requests/` и
`domains/tasks/`, `source/functions/bot-webhook/`, `source/tools/scripts/`
(меню команд). Серверные фильтры и причины внимания должны быть общими
для бота и кабинета; интерфейс бота не фильтрует уже ограниченную страницу.

Пример существующего стиля — `core/src/bot/tasks.ts`:

```ts
btn(messageButton(store, lang, key, "accept"), `/accepttask ${n}`)
```

Видимая подпись приходит из каталога, команда остаётся контрактом действия
кнопки. Техническая команда не добавляется в основной текст сообщения.

Всегда: общие домены/PDP, тестовые персоны, аудит без содержимого жалоб,
двуязычные шаблоны, проверки версии и повторов. Согласовать до реализации:
изменение бизнес-правил, границ первой версии и архитектуры. Запрещено:
обходить AUTH-03, назначать права кнопкой выбора исполнителя, публиковать
внутренние материалы жителю или использовать реальные данные для проверок.

## 10. Проверка и критерии приёмки

Модульные и сценарные тесты — Vitest рядом с модулями `core/src/**/*.test.ts`,
webhook — существующий Deno-набор. Проверяются результаты и права, а не только
совпадение строк. Порог покрытия в процентах не вводится.

| ID | Проверяемое условие |
| --- | --- |
| SBR-01 | Администратор, заместитель и председатель открывают свои очереди; исполнитель без этих полномочий не получает обращения |
| SBR-02 | Очереди, пересечение фильтров, адрес без дома и пустая выдача соответствуют разделу 4; закрытые записи и отменённые задания обработаны по определениям |
| SBR-03 | Большой список разбит по 10; номер открывает правильную карточку; возврат сохраняет подборку; недоступные объекты исключены до пагинации |
| SBR-04 | Недоступный номер/ссылка/старая кнопка и отзыв роли не раскрывают данные и не выполняют запись |
| SBR-05 | Полный цикл «новое → рассмотрение → задание → приёмка отчёта → передача жителю → подтверждение жителем» проходит кнопками, с вводом только содержательных полей |
| SBR-06 | Исполнители выбираются сразу кнопками; отзыв полномочий до подтверждения блокирует назначение; при пустом перечне запись не создаётся |
| SBR-07 | Повтор подтверждения и webhook создаёт одно задание/сообщение/переход; ошибка любой части старта откатывает всю операцию |
| SBR-08 | Конфликт версии не перезаписывает чужое изменение; отказ/отмена ввода не создаёт частичной операции |
| SBR-09 | Сообщение жителю и внутренняя заметка имеют явную аудиторию; внутренние тексты и файлы не раскрываются через ссылки, поиск, уведомления и отчёт |
| SBR-10 | Сотрудник не принимает свой отчёт, не обходит обязательный объём/документ и не закрывает обращение без основания; прямые команды также защищены |
| SBR-11 | Уточнение, отсрочка, доработка, отмена, отказ и оспаривание сохраняют причины и историю; историческая просрочка не подсвечивается как текущая |
| SBR-12 | Диалоги resident/worker независимы; возврат/отмена и переход по ссылке не отправляют незавершённый текст в другое обращение |
| SBR-13 | В worker-боте нельзя создать обращение; прежнее создание жителем в resident-боте работает |
| SBR-14 | Все существующие действия обоих ботов имеют кнопочный путь; тела шаблонов и переопределения проверены на дубли команд/вариантов; кликабельный номер списка — допустимое исключение |
| SBR-15 | Новые сообщения и кнопки работают на ru/kk; симулятор воспроизводит кнопки и ссылки, проверяет PDP и не отправляет уведомления наружу |
| SBR-16 | Уведомление открывает правильный объект в правильном боте; чтение снимает только персональный признак непрочитанного, остальные причины внимания сохраняются до решения |

Команды будущей проверки, из `source/`:

```sh
npm run lint
npm run typecheck
npm test
npm run build
deno task check
deno task lint
deno task test
```

Транзакции, SQL-фильтрация до пагинации и изоляция диалогов проверяются также
интеграционно на Sydney, только по явному запросу, согласно AGENTS.md:
`RUN_INTEGRATION_TESTS=1 npm run test:integration` из `source/`.
Ручная приёмка — тестовыми ролями в симуляторе; ссылки дополнительно проверяются
в Telegram на вымышленных данных. Эти проверки относятся к будущей реализации.

## 11. Исключения и дальнейшее согласование

Не входят: создание обращений сотрудником через бот, массовые операции,
новые финансовые/документные процессы VS-6/VS-8, управление ролями,
настройка нормативов, новый Mini App и замена кабинета.

До технического плана требуется согласование этой спецификации, включая
предлагаемые определения очередей и правило непрочитанного. Технические вопросы
плана: формат навигации/ссылок, состояние диалога отдельно по ботам, поддержка
ссылок симулятором, недостающие серверные фильтры/учёт чтения и перечень
существующих шаблонов/переопределений для приведения к кнопочному интерфейсу.
