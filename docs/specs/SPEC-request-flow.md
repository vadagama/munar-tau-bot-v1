# SPEC: request-flow — вид и адресат при создании обращения

Модуль `request-flow`; карта возможностей и контекст — `docs/ideas/registration-and-request-flow.md`. Статус: на ревью.

## Цель

При создании обращения в боте житель сначала выбирает вид — Заявка на работу / Вопрос / Жалоба (существующий `request_kind`: `request`/`question`/`complaint`), затем адресат — Мои помещения / Общее имущество, затем описание. Администратор получает классификацию сразу; жалобы с первого дня исключены из домовой рассылки уведомлений; общее имущество выбирается кнопками вместо текстового синтаксиса «дом КОД …».

Основание: REQ-09 (виды обращения, изменение вида не создаёт новый номер), REQ-02 (своё помещение, общее имущество своего/другого дома, территория). Правка REQ-03 (порядок создания: вид → место → описание) и раздела 6 `docs/resident-bot-ui-ux-review.md`.

## Что меняется

### Бот (`source/core/src/bot/requests.ts`)

- `/newrequest` (без черновика) → новый шаг `kind`: три кнопки (подписи из каталога, ru/kk) + текстовые эквиваленты; затем шаг `target`:
  - «Мои помещения» → текущий список `place_options` (кнопки 1..20, как сейчас);
  - «Общее имущество» → подменю: «В доме» → выбор дома (список с пагинацией, как `askBuilding` в регистрации; ввод кода дома остаётся текстовой альтернативой) → текст места (`location_text`); «На территории» → текст места (`building_id=null`).
- Далее существующие шаги `description` → `verify` → `/sendrequest` без изменений.
- `inputRow.kind` = выбранное значение (сейчас жёстко `"request"`); `premises_id`/`building_id`/`location_text` — по выбранному адресату.
- Черновик: `/newrequest` с черновиком показывает вид черновика; `/editrequest` дополнительно позволяет сменить вид до отправки (расширение `editRequest` полем `kind` — уточнить при реализации, см. границы). Возобновление старых черновиков (`kind='request'`) — без ошибок.
- `/objects` и остальные команды — без изменений.

### Домен

- Схема не меняется. `createRequest` уже валидирует `kind` (`choice(input.kind, ["request","question","complaint"], "request")`).
- `editRequest`: добавить поддержку смены `kind` для черновика (после отправки вид меняет только администратор по REQ-09).
- Маршрутизация CMP (`complaint_subject_person_id`, `complaint_route`) — по-прежнему заполняет администратор; житель ничего дополнительного не указывает.

### Шаблоны (ADR-010/011)

- Новые ключи в `source/core/src/templates/catalog/messages-requests.ts` + `templates/fixtures/requests.json`: выбор вида, подписи видов, выбор адресата, подменю общего имущества, выбор дома. Оба языка; существующие ключи не переименовывать.
- Подписи видов согласовать с метками `request_kind` в кабинете (ru: «Заявка на работу», «Вопрос», «Жалоба»; kk: «Жұмысқа өтінім/Өтініш», «Сұрақ», «Шағым» — финализировать при правке каталога).
- Страница `/templates` кабинета подхватывает ключи из каталога (обновить golden-фикстуры по процессу навыка `bot-message-templates`).

## Команды

Из `source/`:

- Проверки: `npm run lint && npm run typecheck && npm test`; `deno task check && deno task lint && deno task test`
- Интеграционные: `RUN_INTEGRATION_TESTS=1 npm run test:integration` — **только по явному запросу пользователя**

## Структура (что трогаем)

- `source/core/src/bot/requests.ts` (+ `requests-message.test.ts`, `request-text.test.ts`)

## Code Style (существенные ограничения)

- Реплики — только через каталог (ru+kk); пользовательский текст через `esc()`.
- `callback_data` = точная команда/значение; симулятор показывает кнопки из каталога и отправляет их `data` — новые шаги автоматически доступны в эмуляции.
- Никаких новых строк-реплик в сценариях.

## Testing Strategy

- Unit (Vitest): диалог «вид → адресат → описание» создаёт черновик с выбранным `kind` и адресатом (premises / building+location / территория); возобновление и правка черновика (включая смену вида); старый черновик без ошибок; недопустимое значение вида — повтор вопроса.
- Golden-фикстуры: новые ключи на ru и kk.
- Integration (в git, запуск ручной): идемпотентность отправки (REQ-05) не ломается; `kind` сохраняется; существующее правило «жалоба не бродкастится по дому» остаётся зелёным; смена вида не создаёт новый номер (REQ-09).
- Симулятор: шаги доступны кнопками (существующий паттерн `simulator-menu.test.ts`).

## Boundaries

- Always: новые реплики через каталог (ru+kk); `esc()`; серверная валидация `kind` (уже есть); тесты рядом с изменениями.
- Ask first: смена вида жителем после отправки (по умолчанию — только админ, REQ-09); подписи видов ru/kk; добавление `kind` в `editRequest`.
- Never: выбор жителем адресата конфликта/маршрута CMP; дифференциация сроков первого ответа по видам (TIM не трогаем); переименование существующих ключей шаблонов; автозапуск интеграционных тестов.

## Success Criteria

1. E2E: «Жалоба» → «Общее имущество» → «В доме» → дом 1 → «подъезд 2» → описание → черновик `kind='complaint'`, `building_id`, `location_text` → отправка: номер и срок как раньше; жалоба не попадает в домовую рассылку.
2. «Мои помещения» работает как прежний список; «Заявка на работу» остаётся значением по умолчанию для старых черновиков.
3. `npm run lint/typecheck/test` и deno-проверки зелёные; golden обновлены.
4. REQ-03 и раздел 6 UX-ревью синхронизированы с реализацией.
