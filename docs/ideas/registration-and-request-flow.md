# Идея: регистрация с уточнением помещения и новый сценарий обращения

Статус: направление утверждено пользователем 19.10.2026 (гибрид в регистрации, вид → адресат в обращении). Следующий шаг — спеки по модулям.

## Постановка проблемы

Как сделать так, чтобы житель всегда доходил до отправки анкеты и обращения, даже если не может точно назвать помещение, а выбранный им вид обращения помогал администратору классифицировать работу с первого шага?

Сегодня: (1) при регистрации несовпадение номера помещения — тупик «обратитесь к администратору»; (2) бот жёстко ставит виду обращения `kind='request'`, а общее имущество задаётся текстовым синтаксисом «дом КОД …».

## Рекомендуемое направление

**Регистрация — гибрид.** Быстрый путь (дом → тип → номер) сохраняется. «Помещение не найдено» больше не обрывает диалог: бот предлагает описать помещение своими словами и принимает анкету с этим текстом. Администратор в кабинете находит помещение в реестре и привязывает его до подтверждения анкеты. Для арендатора/проживающего подтверждение собственником (REG-04) стартует только после привязки.

**Обращение — вид и адресат.** Шаг 1: вид (Заявка на работу / Вопрос / Жалоба → существующий `request_kind`). Шаг 2: адресат (Мои помещения / Общее имущество). Затем — описание, как сейчас. Модель и API менять не нужно (`kind`, `building_id`, `location_text` уже есть).

## Карта возможностей

| Модуль | Ответственность | Зависимости |
| --- | --- | --- |
| `registration-binding` | Анкета без привязанного помещения: шаг бота, схема (`registration.premises_id` → nullable, текст в `draft`), привязка в кабинете, маршрут собственника после привязки | — |
| `request-flow` | Выбор вида и адресата при создании обращения: сценарий бота, каталог шаблонов, совместимость черновиков | — |

Порядок сборки: модули независимы; `request-flow` меньше — можно сделать первым. Спеки: `docs/specs/SPEC-registration-binding.md`, `docs/specs/SPEC-request-flow.md`.

## Ключевые допущения (проверить в PR)

- Гибрид утверждён (19.10.2026): «только свободный текст» не делаем.
- Непривязанную анкету привязывает администратор, который её рассматривает; действие привязки — privileged, с причиной, аудитом, Idempotency-Key.
- Удлинение пути арендатора (привязка админом → затем 48 ч собственнику) приемлемо.
- Непривязанная анкета живёт в состоянии `pending_review` с признаком неразрешённого помещения; уточнение — существующий `need_clarification`.

## MVP

- `registration-binding`: миграция; шаг «опишите помещение» в боте; отображение текста в `/status` и карточках до привязки; действие «привязать помещение» на странице «Регистрации»; правка REG-01/REG-02; ADR о новом порядке проверки анкеты.
- `request-flow`: шаг вида; шаг адресата (мои помещения / дом + место / территория); передача `kind` в `createRequest`; совместимость старых черновиков (`kind='request'`); новые реплики через каталог шаблонов (ADR-010/011); правка REQ-03 и раздела 6 `docs/resident-bot-ui-ux-review.md`.

## Не делаем (и почему)

- Парсинг и автоподсказки по свободному тексту («107/2 кв 5» → совпадения кнопками) — отдельная задача после пилота, парсинг ru/kk недёшев.
- Дифференциация сроков первого ответа по видам — единый норматив TIM не трогаем.
- Выбор жителем техкатегории, срочности, адресата конфликта — по REQ-03/REQ-09 это работа администратора.
- Несколько помещений в одной анкете — правило «одно помещение = одна анкета, второе через /add» сохраняется.
- Отдельный маршрут жалоб на председателя — запрещено добавлять молча (OQ-06).

## Открытые вопросы

- Подписи видов ru/kk — взять существующие метки `request_kind` из админки, не изобретать новые.
- Выбор дома для «Общего имущества» (~45 домов): список с пагинацией или ввод кода — решить в спеке `request-flow`.
- Точная формулировка приглашения к свободному вводу (ru/kk) — в спеке `registration-binding` через каталог шаблонов.
