21.10.2026. Ветка `codex/staff-bot-requests-spec`, PR #66.
Спецификация: [SPEC-staff-bot-requests](specs/SPEC-staff-bot-requests.md).
Решение: [ADR-017](decisions/017-staff-bot-request-interaction.md).

Реализация подготовлена и проверена локально. Полная приёмка стенда и публикация

## Реализованное поведение

Worker-бот предоставляет управленческим ролям очереди «Новые», «Без заданий»,
«Требуют внимания», «Сопровождаемые мной», «Все» и открытие по номеру. По 10
обращений на странице; номера-ссылки, фильтры и страницы. Фильтрация области,
жалоб и тестового контура выполняется до LIMIT. Исполнителю без управленческой
роли раздел недоступен. Создание обращения сотрудником остаётся в кабинете.

Карточка содержит страницы переписки, файлов, истории и связанных заданий.
Входящие сообщения отмечаются прочитанными отдельной кнопкой только для
показанных id. Текущая просрочка, отчёт на проверке, отказ от назначения и
ожидающая отмена сохраняют самостоятельные причины внимания.

Доступны разрешённые REQ-переходы, изменение свойств, начало работы с обязательным
заданием, отдельные задания, назначение/переназначение, пауза/возобновление,
замена обязательного объёма, просмотр результата и материалов отчёта,
приёмка/возврат. Доработка создаёт обязательное задание с выбранным сроком.
Все записи используют общие домены, актуального актора, версии и идемпотентность.

Ответ жителю и внутренняя заметка имеют явную аудиторию. Медиа служебной формы
сначала попадает в устойчивую очередь и становится сообщением после сохранения
и подтверждения. Ограниченные сообщения не раскрываются через страницы файлов.

Существующие сценарии получили кнопочные точки входа и формы содержательного
ввода. Текстовые команды остаются совместимыми. Тела стандартного каталога ru/kk
содержат контекст без командных дублей. Малые наборы исполнителей — кнопками.
Большие списки обращений — номером-ссылкой. Визиты и аварийные формы используют
общие доменные проверки и версию объекта. Старые формы не переживают смену
сценария/объекта. В текстовых формах жителя/визитов медиа отклоняется с возвратом
в карточку; отправка файла из самой карточки сохранена.

Симулятор исполняет собственные req/sreq/wrk/stsk-ссылки внутри диалога. Канал
resident/worker передаётся отдельно от сценария, в том числе для уведомлений.
Фокус нового ответа и сохранение фокуса при наборе проверены в браузере.

## Выполненные проверки

- Core: **726 тестов**, 84 файла, все прошли.
- Кабинет: **172 теста**, 27 файлов, все прошли, включая переход по номеру-ссылке.
- Deno: **57 тестов**; `deno task check` и `deno task lint` прошли.
- `npm run lint`, `npm run typecheck`, `npm run build`, `git diff --check` — прошли.
- Secret-scan `admin/dist` и `landing/dist` — секретов не найдено.
- Сборка сохраняет предупреждение Vite о крупном JS chunk; оптимизация загрузки
  кабинета не входила в этот срез.
- Независимое ревью исправлений: закрыты неверный объект старой формы/отчёта,
  callback >64 байт, зацикливание выбора помещения, публикация медиа в прежнюю
  карточку, сохранение аварийной формы после выхода, отличие NOT_FOUND/FORBIDDEN,
  потеря адреса без дома, сокрытие полного текста/материалов отчёта, потеря срока
  доработки, версия визита и неправильный дом аварийного preview.
- Mutation-проверки: допуск executor в служебный список и отключение проверки
  версии визита обнаруживаются регрессионными тестами; исходный код восстановлен.
- Браузер: реальный компонент RegistrationSimulator на localhost с изолированным
  stub API; номер-ссылка → карточка без перехода в Telegram, экранирование текста,
  кнопки, прокрутка/фокус и отсутствие console warn/error. Это проверка UI,
  она не заменяет запрос к настоящему серверу.
- Отдельная локальная SQL-проба на синтетической схеме: повтор миграций, RLS
  anon, независимость каналов, страницы 10+2, полный цикл, повтор, внутреннее
  медиа до подтверждения, точные отметки чтения при новом входящем сообщении.
  Это не прогон штатного интеграционного набора на Sydney.

Штатные интеграционные тесты не запускались согласно временному правилу
AGENTS.md. Сценарий сохранён в
`source/core/tests/integration/staff-request-bot.test.ts`. Живые webhook,
уведомления, данные и конфигурация Supabase/Telegram не изменялись.

## Контракты и выпуск

Добавлены таблицы `bot_dialog_channel` и `request_message_read`; RLS включён,
прямой доступ anon/authenticated отозван. Старый `bot_dialog` оставлен для отката.
Смена профиля, сеанса или сценария сбрасывает временную форму, а не бизнес-черновик.

Дополнительные API, с обычными AUTH/PDP/rate-limit и общими доменами:

- `POST /v1/requests/staff/search`: фильтр очереди, состояния, дома (включая
  `none`), периода, поиска, limit и связанного с фильтром cursor; items/next_cursor.
- `GET /v1/requests/:id/timeline/:section?page=0`: messages/history/files/tasks,
  по 10 элементов, has_more; требуется управление конкретным обращением.
- `POST /v1/requests/:id/read`: message_ids, максимум 10; только доступные
  показанные входящие сообщения, повтор не создаёт второй отметки.
- Эмуляция: необязательный `bot=worker` сохраняет канал общих сценариев.
  Передача канала не расширяет PDP и не даёт создание обращения в worker.
