# UI/UX бота жителя: сообщения, формы и кнопки

Дата: 18.10.2026. Статус: **предложение для анализа и корректировки**.

Результат задачи — проект текстов и взаимодействий. Код, настройки каталога в БД и Telegram не изменены. Предложения ниже ещё не являются принятой приёмкой или новым бизнес-правилом.

## 1. Что проверено

Проверен экспорт `TEMPLATE_CATALOG` из текущей рабочей копии: полный перечень ключей приведён в приложении. Проверены сборщики и маршрутизация в `bot/registration.ts`, `requests.ts`, `request-text.ts`, `request-files.ts`, `incidents.ts`, `notifications.ts`, `help.ts`, `inbound.ts`, `bot-errors.ts`, а также каталоги целых сообщений и уведомлений.

Источники: [требования](requirements-v1.md) — REG, REQ, MSG, SHR, WRK, EMG, PUB, NTF, PRV; [жизненный цикл](request-lifecycle.md); [матрица доступа](access-matrix.md); [ADR-009](decisions/009-two-telegram-bots.md); [ADR-010](decisions/010-bot-message-templates.md); [ADR-011](decisions/011-bot-message-scenarios.md).

Область: бот жителей, включая действия собственника и входящие уведомления жителю. Служебные задания, приём сигналов дежурным, сообщения администратору и worker-бот перечислены для контроля полноты, но не перепроектируются. Платежи, опросы и другие ещё не реализованные процессы не выдаются за существующие диалоги.

Это статический аудит исходников и дефолтов. Переопределения в БД, реальные переписки и фактическая доступность действий для конкретного профиля не проверялись. `deprecated` означает скрытый старый ключ, а не доказательство отсутствия вызовов: часть таких фрагментов используется сборщиками и историческими уведомлениями.

## 2. Контракт сообщения

Каждое сообщение начинается с одной понятной фразы: какой процесс, какой объект и что сейчас требуется. Контекст входит в тот же ответ, отдельная служебная реплика перед ним не нужна.

Примеры: «Ваши анкеты на регистрацию:», «Обращение З-26-00001 — требуется ваше подтверждение», «Визиты по обращению З-26-00001:», «Настройки уведомлений ОСИ:». Фраза «Файл сохранён» получает имя файла и обращение. На шаге ввода повторяется выбранное помещение или номер обращения.

Правила оформления:

- В видимом тексте и подписях нет инструкций с командами, UUID, техническими состояниями и форматов вроде «НОМЕР причина». Текст, номер телефона, описание и причина вводятся обычным сообщением после нажатия кнопки.
- `[Подпись]` ниже обозначает настоящую кнопку Telegram. Каждая строка в примере — отдельный ряд inline-клавиатуры. Постоянное меню используется для переходов между разделами.
- Кнопка относится к конкретной анкете, связи, обращению, визиту или публикации. Если под сообщением несколько объектов, подпись содержит номер/помещение: `[Исправить · кв. 4, дом 1]`. Под карточкой одного объекта достаточно `[Исправить анкету]`.
- У Telegram кнопки находятся после текста всего сообщения. Нельзя визуально вставить отдельную клавиатуру между строками списка: либо одна карточка на объект, либо список с однозначными подписями кнопок.
- Подтверждение и опасное действие разделены: сначала объект и последствия, затем явное подтверждение. Повторное нажатие не создаёт второй объект.
- На вводе: `[Назад]` и `[Отменить заполнение]`. Для обращения: `[Сохранить и выйти]`, если черновик действительно сохранён. «Назад» требует восстановления предыдущего шага, а не вызова существующей отмены под новой подписью.
- Пустое состояние объясняет отсутствие данных и предлагает доступный следующий шаг. Ошибка сохраняет введённое и предлагает восстановление. Успех называет объект и результат действия.
- Один язык по профилю, русский по умолчанию; первоначальный выбор языка — допустимое двуязычное сообщение. Все утверждённые изменения выпускаются одновременно на ru/kk. Ниже основной редакторский макет на русском; он не заменяет казахскую редактуру.
- Даты: ДД.ММ.ГГГГ ЧЧ:ММ, Алматы. Динамические данные экранируются по ADR-010/011. Большие списки разбиваются на страницы; кнопки относятся к видимой странице.

## 3. Ключевые несоответствия текущего интерфейса

| Наблюдение | Следствие для доработки |
| --- | --- |
| `message.registration.status` начинается с `{registrations}` и заканчивается `/fix`; кнопки «Исправить» одинаковые | Добавить вступление, подписи с помещением, устойчивую привязку к анкете |
| `/edit` перезапускает полную анкету, а `/fix` исправляет имя/телефон с сохранением помещения и роли | Различать полное редактирование и исправление контактов; не направлять разные кнопки молча в один сценарий |
| `/fix` выбирает `need_clarification`, `rejected` и `pending_review` при `total_due_at is null` | Не определять доступность только по видимому статусу; повторять фактическую серверную проверку |
| `/delete` вызывает запрос `delete_profile`, требует Actor и не принимает ID анкеты | Кнопка удаления отдельной анкеты — отдельное предложение; текущую команду нельзя подставить под неё |
| В активной карточке обращения нет кнопок переписки и визитов; у результата есть команда следующего отчёта | Добавить входы в шаги и навигацию отчётов |
| В `report_command`, подсказках и серверных блоках есть команды | Одной замены текста шаблона недостаточно: проверить и сборщики переменных |
| Настройки меняются командой с типом, режимом и языком | Нужен экран выбора параметра и варианты кнопками |
| Ошибки возвращаются строкой через `botErrorText` | Для кнопок восстановления нужно изменить сборку ответа и передачу клавиатуры |
| Списки хранят индексы в общем `bot_dialog`; старые кнопки могут ссылаться на новый список | Объектные действия должны проверять устойчивую ссылку и актуальность, а не доверять номеру старой строки |
| В каталоге есть `message.requests.places`, но `/objects` отсутствует в `REQUEST_COMMANDS` | Проверять реальный маршрут через `registrationStep`; наличие макета не доказывает доступность экрана |

## 4. Вход, меню и помощь

Требования: REG-02, REQ, NTF, PRV-01.

**Первый вход** (`help.welcome_text`):

```text
Добро пожаловать в ОСИ ЖК «Мунар Тау».
Здесь можно сообщить о проблеме, следить за обращениями и получать новости ОСИ.
Чтобы пользоваться личными сервисами, заполните анкету.
При непосредственной угрозе жизни звоните 112.

[Заполнить анкету]
[Аварийные контакты]
[Помощь]
```

**Повторный вход:** «Вы в боте ОСИ ЖК „Мунар Тау“. Выберите, что хотите сделать». Показать меню с учётом доступа; незавершённую анкету/черновик предложить продолжить отдельной кнопкой.

**Постоянное меню:** `[Новое обращение] [Мои обращения]`, `[Мои помещения] [Анкеты]`, `[Новости ОСИ] [Аварии]`, `[Настройки] [Помощь]`. Это предложение расширения текущего меню: сейчас есть шесть кнопок, включая «Добавить помещение». Добавление помещения остаётся в разделе помещений.

**Помощь** (`help.registration_help`): «Здесь собраны основные действия в боте. Выберите нужный раздел». Кнопки разделов и `[Аварийные контакты]`; для собственника — `[Анкеты жильцов]`, `[Выданные доступы]`. Вместо справочника команд — короткие объяснения разделов. `[Меню]` возвращает в начало; этот переход ещё требуется реализовать.

## 5. Анкеты, регистрация и помещения

Требования: REG-01–14, PRV-01–02. Общий шаг формы: контекст → один вопрос → варианты/поле → навигация.

### 5.1. Анкеты и привязанные помещения

Не называть анкету на проверке уже подтверждённой связью. Для списка анкет:

```text
Ваши анкеты на регистрацию:

1. Ожидает проверки: Алия Омарова
Дом 1, квартира 4 · Собственник

[Исправить анкету · кв. 4, дом 1]
[Добавить помещение]
[Мои помещения]
```

Для подтверждённых связей (`message.registration.objects`):

```text
К вашему профилю привязаны помещения:

1. Дом 1, квартира 4 · Собственник
Доступ подтверждён.

[Новое обращение · кв. 4, дом 1]
[Пригласить жильца · кв. 4, дом 1]
[Доступы · кв. 4, дом 1]
[Добавить помещение]
```

Кнопка приглашения — только для действующего собственника. Неактивная связь получает явную подпись; новые действия по прежней связи не показываются. История собственных обращений сохраняется по REG-08a.

**Запрошенный вариант удаления:** `[Удалить анкету]` под конкретной анкетой возможен только после определения отдельной операции отзыва этой анкеты, допустимых состояний и последствий. В текущей реализации используется запрос удаления данных всего профиля (PRV-02). До согласования отдельной операции макет показывает `[Запросить удаление данных]` в настройках, с явным описанием эффекта. Это не подмена требуемого действия: функциональный пробел вынесен на корректировку в разделе 13.

### 5.4. Удаление данных

`registration.podat_zapros_na_udalenie_ankety_i_dannyh`:

```text
Запрос на удаление данных профиля.
Вы направите запрос администратору ОСИ. Необязательные уведомления отключатся сразу.
История обращений и операций сохранится; администратор определит, какие данные можно удалить, и сообщит решение.
После отправки отменить запрос в боте нельзя — потребуется обратиться к администратору.

[Отправить запрос на удаление данных]
[Назад в настройки]
```

Успех: «Запрос на удаление данных профиля передан администратору ОСИ. Необязательные уведомления отключены. О решении вам сообщат»; `[Мои обращения]`, `[Настройки]`. Не обещать немедленного удаления, срока рассмотрения или удаления одной анкеты. Отдельно предусмотреть поведение до появления Actor: текущий `/delete` в этом состоянии недоступен.

## 7. Обращение, переписка и действия

Требования: REQ, MSG-01–03, SHR-01–02, WRK-07.

**Список** (`message.requests.list`): «Ваши обращения:» → номер, место, краткое описание, статус. Кнопки `[З-26-00001 · Протечка]`, `[Продолжить черновик]`, `[Следующая страница]`, `[Предыдущая страница]`, `[Новое обращение]`. Сейчас реализовано движение вперёд; обратная навигация — доработка.

**Карточка** (`message.requests.card.*`):

```text
Ваше обращение З-26-00001.
Статус: В работе
Место: дом 1, квартира 4
Создано: 18.10.2026 10:30

Проблема: Подтекает труба под раковиной.
Последние сообщения по обращению:
18.10.2026 11:00 · ОСИ: Предлагаем визит завтра.
```

| Состояние / вариант | Контекст и действия |
| --- | --- |
| `.active`: new / reviewing / need_clarification / in_work / on_hold | «Ваше обращение … принято / рассматривается / требует уточнений / в работе / приостановлено». `[Написать сообщение]`, `[Визиты]`, `[Файлы обращения]`, `[Мои обращения]`; при уточнении первым `[Ответить на вопрос]` |
| `.confirmation` | «По обращению … работы завершены. Проверьте результат». Сводка и число отчётов. `[Посмотреть результат]`, `[Принять результат]`, `[Вернуть на доработку]` |
| `.closed` | «Обращение … закрыто. Вы можете оценить результат». `[Оценить работу]`, `[Подать апелляцию]` при разрешении сервера; просмотр отчётов/истории |
| `.rejected`: canceled / rejected | «Обращение … отменено / отклонено. Причина: …». `[Подать апелляцию]`, `[Возобновить обращение]` только при допустимости перехода |
| `.other` | «Ваше обращение … Статус: …». Только доступные переходы и чтение, без универсального набора кнопок |

Не раскрывать внутренние сообщения, файлы и переписку чужих обращений. Предложенные `[Файлы обращения]` и `[История переписки]` требуют отдельного представления: сейчас карточка показывает последние три сообщения, а команды просмотра всех файлов жителя нет.

**Новые пошаговые формы вместо аргументов команды:**

| Действие | Диалог после нажатия | Завершение |
| --- | --- | --- |
| Написать сообщение | «Сообщение по обращению … Напишите, что хотите передать ОСИ» → текст; файлы привязываются к этому обращению | «Сообщение по обращению … сохранено»; `[Открыть обращение]` |
| Отменить обращение | Номер и текущий статус → причина → последствия | `[Подтвердить отмену]`; доступность только по FSM |
| Вернуть на доработку | «Возврат результата по обращению … Что осталось исправить?» → причина | Предпросмотр → `[Отправить на доработку]` |
| Принять результат | Сводка текущей версии результата → «Подтверждаете, что проблема решена?» | `[Подтвердить результат]`; версия подтверждения обязательна, устаревшая карточка перечитывается |
| Оценить работу | «Как вы оцениваете результат по обращению …?» → `[1] [2] [3] [4] [5]` → комментарий | `[Отправить оценку]`, `[Без комментария]`; сбор комментария и предпросмотр — доработка |
| Подать апелляцию | «Апелляция по обращению … Опишите, с чем вы не согласны» | Предпросмотр → `[Отправить апелляцию]` |
| Возобновить | «Возобновление обращения … Почему его нужно продолжить?» | Предпросмотр → `[Отправить запрос]`; текст успеха соответствует реальному переходу |
| Совместный доступ | «Доступ участников к обращению …» → разрешённый получатель → описание доступных данных | `[Предоставить доступ]` / `[Прекратить доступ]`, с проверкой SHR |

Формы отмены, апелляции, возобновления и совместного доступа — предложение интерфейса над существующими действиями; не все перечислены в нынешних карточках. Участник совместного обращения не получает прав автора на подтверждение, оценку или финансы автоматически.

## 8. Визиты и результат работ

**Визиты** (`message.requests.visits`): «Визиты по обращению {number}:» → дата, интервал, статус. Кнопки `[Согласовать · 19.10 10:00–12:00]`, `[Исполнитель не пришёл · 19.10]`, `[К обращению]`. Сервер определяет допустимость каждого действия; список не должен предлагать согласовать завершённый визит.

Неявка: «Исполнитель не пришёл на визит по обращению …, назначенный на …? Опишите ситуацию» → причина → `[Сообщить о неявке]`. Успех: «Сообщение о неявке по обращению … передано администратору для проверки». Это не автоматическое признание нарушения.

Успех согласования (`requests.vizit_soglasovan`): «Визит по обращению … согласован на …»; `[К обращению]`.

**Результат** (`message.requests.result`, `.result.more`): «Результат работ по обращению … Отчёт 1 из 2» → работа, результат, ограничения, доступные жителю материалы. Кнопки `[Предыдущий отчёт]`, `[Следующий отчёт]`, `[К обращению]`; переход к принятию/возврату относится ко всему актуальному результату обращения, не к одной странице отчёта. Внутренние файлы задания автоматически не раскрываются.

Если результата нет (`requests.rezultat_esche_ne_peredan`): «Результат по обращению … ещё не подготовлен для вашей проверки»; `[К обращению]`.

## 10. Аварии и публикации

Требования: EMG-01–07, PUB-01–03.

### 10.1. Контакты и сигнал

Вход (`incidents.opasnost_avariya_napishite_emergency_nomer_obrascheniya_chto`): «Аварийная помощь ОСИ. При непосредственной угрозе жизни звоните 112. Выберите, что нужно»; `[Аварийные контакты]`, `[Сообщить об аварии]`, `[Аварии моего дома]`.

Контакты: выбор дома → «Аварийная служба дома 1. Телефон: …». Если телефона нет: «Для дома 1 телефон аварийной службы пока не указан». Не писать безымянное «Телефон ещё не настроен».

Сигнал: выбор доступного обращения → «Сигнал по обращению … Что произошло?» → текст → проверка → `[Отправить сигнал]`. Текущий resident-маршрут отправляет сигнал по обращению; сценарий без обращения требует дополнительного решения и реализации. Кнопка выбора дома сама по себе не должна имитировать отправку сигнала.

Все восемь `messages.incidents.contact_*` / `sent_*` сохраняют условия:

- `contact_*`: показ контактов не означает, что сигнал отправлен. Текущая общая фраза про сигнал здесь может вводить в заблуждение; убрать её из просмотра контактов.
- `sent_on_*`: «Сигнал по обращению … передан дежурному ОСИ. Это ещё не подтверждение выезда».
- `sent_off_*`: «Сигнал по обращению … передан в ОСИ. Немедленная обработка сейчас не обеспечена». Не маскировать отсутствие дежурства.
- Суффикс `phone`: номер с подписью службы и дома; `no_phone`: явное отсутствие номера. `[К обращению]` при доступности, `[Аварийные контакты]`.

### 10.2. Список и карточка аварии

`messages.incidents.list`: «Аварии, доступные по вашим помещениям:»; `[А-26-00001 · Отключение воды]` для каждой записи.

Восемь `messages.incidents.card_*`: «Авария А-26-00001 · дом 1. Отключение воды» → статус/публичное описание → прогноз → следующее обновление. Для `checking`: «Сигнал проверяется. Авария ещё не подтверждена». Для отсутствующего прогноза: «Срок восстановления пока неизвестен»; следующее обновление показывать, только если оно назначено. Если его нет, отметить отсутствие, а не обещать время. Кнопки `[Список аварий]`, `[Аварийные контакты]`.

## 13. Что требует корректировки перед реализацией

1. **Удаление отдельной анкеты.** Нужна самостоятельная семантика: отзыв ещё не подтверждённой анкеты, допустимые состояния, причина, влияние на другие анкеты и уведомления. Нынешний запрос удаления профиля не решает этот сценарий. Вариант пользователя `[Удалить анкету]` сохранён как требование к обсуждению; он не помечен реализованным.
2. **Исправление.** Предложение: на карточке `[Исправить анкету]` открывает доступные поля; простой путь исправления контактов сохраняет помещение/роль, полная правка явно показывает их повторную проверку. Точные доступные состояния остаются по доменным проверкам.
3. **Карточки или списки анкет.** Предложение: компактный список с кнопками «Открыть · помещение», затем отдельная карточка с действиями. Для одной записи допускаются действия сразу под ней. Так удаление/исправление всегда относится к видимому объекту.
4. **Состав меню.** Предложенное расширенное меню и входы «Новости»/«Аварии» нужно оценить на телефоне; если слишком длинно, перенести их в один раздел «Информация ОСИ». Это редакторский выбор, не новый домен.
5. **Языки.** Русские формулировки после правок согласовать и перевести на казахский; проверять обе локали на одинаковые условия, кнопки и последствия. Пример: `[Исправить анкету]` → `[Сауалнаманы түзету]`, `[Мои обращения]` → `[Менің өтініштерім]`.
6. **Сигнал без обращения.** Не включать его в реализацию незаметно. Текущий обработчик resident ожидает обращение; сначала определить, создаёт ли форма новое обращение или предлагает существующее.

Эти пункты не блокируют подготовленный документ. При изменении бизнес-правил потребуется отдельное согласование требований; тексты не должны менять правила молча.

## 14. Граница будущей реализации и приёмка

**Редактура каталога:** вступления, удаление команд из видимого текста, подписи. **Код сценариев:** новые кнопки, формы причины/комментария, назад/меню, объектные ссылки, состояния ошибок. **Данные уведомлений:** номер и ID объекта, помещение, файл, целевой бот. Администратор каталога может менять подпись существующей кнопки, но не создать новый обработчик одной настройкой.

Существующие команды сохраняются внутренним контрактом `callback_data` и текстовым эквивалентом для симулятора. Новые переходы форм тоже получают точные команды, без переноса бизнес-логики в шаблоны. Ограничение 64 байта проверять на выбранном формате, включая кириллицу и версии. Не помещать произвольную причину в callback. Авторизация и версия повторно проверяются сервером; test-уведомления остаются в simulator.

Ключи и историю каталога не удалять. Проверить действующие переопределения: новый дефолт сам по себе их не заменит. Исторические подписи reply-меню продолжают маршрутизироваться по ADR-011. Разметка сохраняется в outbox; длинные ответы делятся с корректным HTML, клавиатура прикрепляется к последней части.

Приёмка будущего изменения:

- [ ] Весь путь жителя проходится без набора команды: вход → анкета → исправление → помещение → обращение → переписка/файл → визит → результат → оценка/апелляция; также доступы собственника, публикации, аварии, настройки.
- [ ] У каждого ответа есть понятный контекст; подтверждения и ошибки называют объект. Контекст не дублируется отдельным сообщением.
- [ ] Проверены ru/kk, длинные значения, несколько анкет и помещений с одинаковыми номерами в разных домах, пустые списки, ограниченные права и утраченные связи.
- [ ] Старая кнопка после открытия другого списка не меняет другой объект. Устаревшая версия результата не принимается. Повтор нажатия не создаёт дубликат.
- [ ] Кнопки с причиной открывают ввод текста и подтверждение. Отмена/назад не теряют сохранённый черновик и не отправляют данные.
- [ ] В видимом тексте нет команд, включая серверные переменные и наследованные шаблоны; пользовательский текст с символом «/» не искажается.
- [ ] Сохранение файла отличается от приёма в очередь. Переписка, вложения и финансовые данные не расширяют аудиторию.
- [ ] Выполнен проход реального Telegram на узком экране: читаемость подписей, связь кнопок с объектами, длинные клавиатуры, пагинация, сценарий возвращения к старому сообщению.
- [ ] Для реализации выполнены модульные/Deno-проверки и необходимые lint/typecheck/build. Интеграционные тесты — только по отдельному явному запросу пользователя согласно AGENTS.md.

Для этого документа проверены полнота инвентаризации ключей и ссылки на локальные файлы. Runtime-проверки и тесты приложения не запускались: поведение приложения в этой задаче не меняется.
