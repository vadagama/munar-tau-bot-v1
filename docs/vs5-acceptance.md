# VS-5 — регламенты и уведомления: состояние реализации

Дата: 17.10.2026. Ветка `feature/vs-5-regulations-notifications`, поверх завершённого VS-4 (PR #13).

## Реализовано

- TIM-02: закрытый каталог условий начала/паузы/погашения и разрешённых действий; новые версии сохраняют снимок, старые используют исходные условия v1. Подмена действия через API отклоняется; условия видны в кабинете.
- TIM-03/04/05: единый `work_schedule`, новые версии рабочих правил при смене графика, автор/причина и аудит. Уже запущенные сроки сохраняют версии и даты. Исторические версии защищены от UPDATE/DELETE.
- TIM-07: правовое основание, редакция, дата действия, область и границы хранятся явно. При создании версии основание копируется в `legal_basis`; обычный API не изменяет правовое основание. Незаданные или нарушенные границы дают `RULE_LEGAL_BOUNDARY`.
- TIM-05: первый ответ по рабочему графику; ближайшее открытие сохраняется при регистрации и показывается ботом. Содержательный ответ отменяет таймер. Просрочка не обнуляется.
- WRK-07: напоминание автору через 48 календарных часов и проверка администратором через 7 дней. Таймеры привязаны к версии результата. Подтверждение, отзыв и доработка погашают устаревшие таймеры; автоматического закрытия нет.
- NTF-01/03: предпочтения publication/work.report (сразу, сводка, выключено), request.status (сразу, выключено), ru/kk. Обязательные сообщения не отключаются. Сводка следует окончанию смены, повторно проверяет аудиторию и не отправляет пустое сообщение. Большая сводка продолжается порциями с сохранением отсечки состава.
- NTF-02: outbox с уникальным ключом, материализация notification, lease отправки и защита от устаревшего воркера, повтор по retry_after, пять попыток, немедленная окончательная ошибка при блокировке бота. Текст транспортного исключения не сохраняется. Окончательная ошибка важного уведомления создаёт единственную задачу контакта; результат сотрудник фиксирует явно. Для обращений уведомляются действующие обработчики.
- Перед отправкой повторно проверяются профиль, полномочия/доступ к обращению и связи с домами. Служебные и жительские аудитории разделены; simulator никогда не вызывает Telegram.
- Кабинет: версии регламентов, предпочтения и ошибки доставки в области сотрудника, запись результата связи. Причина окончательной ошибки и состояние контакта также показываются обработчику в карточке обращения. Бот/эмуляция: общий сценарий `notifications` и команда `/notifications`.

- WRK-01/02: таймеры принятия и последовательной эскалации администратору, заместителю, председателю; погашение при принятии/снятии. Отказ доставки назначения уведомляет резерв без автоматического назначения. Прежнему исполнителю доступен только минимальный личный факт снятия.
- JOB-05/06: расписание и история в кабинете, снимок версии методички/области для каждого запуска, устойчивый ключ даты, ограниченные повторы и явный retry после dead. Права автора проверяются при выполнении, нового автора — при повторе. Пропуск сохраняется при свипе и при завершении/отмене между тиками; автоматического завершения нет.
- Доступ к истории расписания проверяется по каждому заданию/снимку, включая перенос шаблона в другой дом. Карточка задания показывает срок принятия, просрочку, безопасный код ошибки доставки и состояние контакта.

## Проверка пользователем после развёртывания

1. Председателем изменить время закрытия смены. Создать новое обращение; сравнить его срок с обращением, созданным до изменения. Старый срок и версия не меняются.
2. Обычным администратором без права управления регламентами попытаться сохранить настройку: сервер возвращает 403. В эмуляции изменение регламентов запрещено.
3. Передать результат вопроса/жалобы, дождаться тестового срока напоминания. Обращение остаётся открытым. Вернуть результат на доработку; предыдущие напоминания больше не срабатывают.
4. В тестовой эмуляции открыть сценарий «Уведомления», отправить `/notifications`, затем `/notifications новости сводка ru`. Обязательные события недоступны для отключения.
5. Для окончательной ошибки важной доставки открыть «Уведомления → Ошибки доставки», записать фактический результат попытки связи. Это не меняет состояние обращения и не подтверждает согласие жителя.

6. Уполномоченным сотрудником заполнить `task_accept` и `task_escalation`: миграция не задаёт нормативов. Назначить тестовое задание, проверить срок и эскалацию; принятие отменяет ожидание, молчание не означает принятия.
7. В шаблоне открыть «Расписание и запуски», задать дату/период/срок явно. После создания запуска изменить методичку: прежнее задание сохраняет старую версию. Просроченный запуск виден в истории, включая отменённый после срока.
8. Отозвать полномочия настроившего расписание сотрудника: новая работа не создаётся. После исчерпания повторов уполномоченный сотрудник явно повторяет запуск из истории. Самостоятельно чужая область не становится доступной.

## Автоматические и интерфейсные проверки

- Модульные: 285 тестов ядра и 32 кабинета прошли после интеграции VS-4; включены TIM-03/04/07, календарь, NTF-01/02/03 и валидация расписания.
- Deno: check/lint/test — 41 тест прошёл. Сценарий проверяет 401 без JWT, ошибку даты без часового пояса и 403 для недоступного шаблона.
- Кабинет: typecheck, lint, unit, build и secret-scan прошли. Сборка сохраняет существующее предупреждение Vite о крупном JS-бандле.
- Браузер: локальный стенд с вымышленными данными и mock API — ошибки доставки, история версий, редактор графика, условия TIM-02 и отсутствие фиктивной истории у ненастроенного правила, форма расписания, сохранение периода и retry dead проверены; ошибок консоли нет. Это не сквозная проверка развёрнутого API/OIDC. Временные файлы стенда удалены.
- Независимое ревью: исправлены снятие назначения, проверка исторической области и пропуск при терминальном переходе до свипа; повторное ревью не выявило блокирующих дефектов.
- Интеграционные: 10 сценариев notifications прошли. Первый прогон task-timing выявил отсутствующее stop_checked в тесте поздней отмены и таймаут составного сценария; фикстура исправлена, таймер отделён от доставки. Дополнительно прошли три адресных сценария: TIM-04 (снимок контракта и графика), WRK-07 (напоминание без закрытия), REG-03/05 (спор регистрации). Повтор task-timing/task-notification-access остановлен во время ожидания блокировки по указанию пользователя. Эти сценарии пока не считаются пройденными; интеграции временно переведены в ручной режим, включая будущие тесты (AGENTS.md).

## Условия включения и последующие срезы

Значения `task_accept`/`task_escalation` должен явно задать уполномоченный сотрудник. До этого создание назначенного задания блокируется; ненастроенные сроки не подменяются вымышленными нормативами. Ранее созданные в VS-4 задания без таймера не получают задним числом выдуманного срока принятия: для них требуется явное новое назначение после настройки. VS-4 и VS-5 ещё не развёрнуты на демонстрационном стенде.

Публикации VS-7 и опубликованные отчёты последующих срезов должны вызывать общий enqueueNotice с разрешённой аудиторией; пока дайджест проверяется интеграционными событиями. Финансовая аудитория PAY-08 подключается с VS-6. Аварийное дежурство/резерв — VS-7.

Работа не развёрнута на демонстрационный Frankfurt. [Черновик PR №14](https://github.com/vadagama/munar-tau-bot-v1/pull/14) создан. Node и Deno CI прошли на коммите 2b5d660. Интеграционная джоба остановлена по указанию пользователя; после изменения запуска она пропускается на PR/push и доступна только вручную. PR остаётся на согласовании; merge выполняется только после одобрения пользователя.
