# Библиотека технических документов исполнителя

Дата: 25.10.2026. Статус: предложение на согласование, не реализованная функция.
Расширение существующего модуля documents: DOC-01–03 и WRK-17–18.
Базовые правила — SPEC-documents.md, SPEC-vs8-conventions.md, матрица доступа и AGENTS.md.

## Цель и согласованный объём

Исполнитель находит план ЖК, описание электрики, водоснабжения, канализации или отопления по содержанию документа. Документ доступен как текст, а не только файл. Пользователь выбрал оба способа наполнения сразу: ручной редактор и импорт PDF/фотографий с распознаванием.

Предлагается расширить существующий каталог документов, версии, проверку и PDP, а не создавать независимое хранилище. Первый выпуск — кабинет, включая мобильный экран. Новое меню Telegram и автоматические ответы AI по документам не входят в этот выпуск.

## Пользовательский сценарий

1. На главной исполнителя и в задании есть переход «Рабочая библиотека», если доступны документы. Отключение платного AI не скрывает библиотеку.
2. Поиск работает по названию и тексту. Фильтры: инженерная система, дом, помещение при наличии. Видны только разрешённые документы, включая счётчики и фрагменты поиска.
3. Карточка открывается отдельной страницей с постоянным URL: название, область, система, статус проверки, версия, дата, автор проверки. Вкладки: Читать, Исходник, Версии; Редактировать — при наличии прав.
4. Текст имеет оглавление, заголовки, списки, таблицы и ссылки на доступные объекты. Обозначения оборудования связываются с исходным листом. Текст можно выделить и скопировать; PDF/фото открывается рядом или отдельной вкладкой на узком экране.
5. Из задания ссылка может указывать конкретную проверенную версию. Новая редакция сохраняет старую и не переписывает уже использованный снимок.

## Наполнение и проверка

- Ручной ввод: название, система, область, текст, исходные материалы при наличии. Сохранение черновика не означает публикацию.
- Импорт: загрузка PDF/изображения в закрытое Storage → извлечение текстового слоя PDF → распознавание сканированных страниц → черновик с привязкой текста к странице → сверка человеком → существующий процесс проверки и публикации.
- Плохое качество, отсутствие текста, повреждённый файл и сбой распознавания имеют отдельные состояния с понятной возможностью исправления. Исходник не теряется. Повтор обработки не создаёт дубликаты версии и не повторяет оплату бесконтрольно.
- Непроверенные фрагменты отмечаются, но отсутствие отметки не считается гарантией правильности. Маркировки, размеры и привязки к схеме проверяются человеком. Пустой текст нельзя опубликовать как документ библиотеки.
- Геометрию схемы текст не заменяет. Оригинал сохраняется с версией; распознавание не должно придумывать отсутствующие обозначения или инструкции.
- Редактор и импорт доступны одновременно в первом выпуске; импорт не откладывается в отдельный будущий этап.

## Данные и совместимость

Расширить версию документа текстом, языком, происхождением (ручной ввод/извлечение/OCR), привязками к страницам и результатом сверки. Категория и область относятся к карточке. Поиск индексирует текст разрешённых опубликованных версий; черновики доступны только участникам процесса по действующей политике.

В текущем модуле файл версии обязателен. Предложение для текстовых библиотечных документов: разрешить текстовую версию без исходного файла при обязательном непустом тексте; у остальных видов документов прежнее требование файла сохраняется. Это отдельное изменение контракта, которое должно быть зафиксировано ADR до миграции.

Точное устройство очереди OCR, библиотеки извлечения и пределы размера/страниц определяются техническим планом после проверки возможностей среды. Фон остаётся в принятой модели PostgreSQL + jobs; постоянно работающий новый процесс не вводится молча.

## Доступ

Используется существующий PDP: роль, источник, назначение, аудитория, область и test-режим. Технический администратор не получает автоматически все документы. Новый индекс не раскрывает закрытые тексты через фрагменты, количество результатов или подсказки. Проверка применяется и к исходнику, и к конкретной версии. Поиск, открытие ссылки и скачивание повторяют авторизацию сервером.

Проверяющий отличается от подготовителя по действующему процессу. Изменения имеют expected_version, причину, ключ идемпотентности и аудит. Эмуляция не отправляет реальные документы внешнему OCR. AI-ассистент главной не получает библиотечные тексты автоматически.

## Стек, структура и стиль

Сохраняются TypeScript, React + Refine + AntD, Supabase/PostgreSQL/закрытое Storage и Edge Functions. Расширения: source/core/src/domains/documents, source/admin/src/pages/documents, source/functions/api и jobs, миграции source/db/migrations. Тесты рядом с кодом; интеграционные проверки — в существующем каталоге core/tests/integration.

Стиль существующих сервисов сохраняется: Actor поступает с сервера, проверка доступа до чтения текста, ApiError для ошибок, без клиентских флагов обхода. Пример контракта на TypeScript:

```ts
interface LibraryTextDraft {
  text: string;
  expected_version: number;
  reason: string;
}
```

Интеграционные тесты БД — только по отдельному разрешению AGENTS.md.

## Критерии приёмки

- Исполнитель находит документ по слову из содержания, отсутствующему в названии.
- PDF с текстом и скан/фото проходят соответствующий путь получения редактируемого текста.
- Ручной документ и импорт используют общую карточку, версии и проверку.
- Исполнитель видит только проверенную разрешённую версию; закрытая версия не появляется в поиске и по прямой ссылке.
- Текст не заменяет оригинал; доступен переход к странице источника.
- Сбой распознавания не публикует пустой документ и не теряет файл; повтор ограничен и идемпотентен.
- Изменение текста не меняет старую версию, связанную с заданием.
- Отключение AI не влияет на чтение, поиск и ручной редактор библиотеки.

## Границы и открытый вопрос

Всегда: общий PDP, неизменность проверенных версий, серверная валидация и аудит, тесты и проверка мобильного экрана. Согласовать отдельно: OCR-провайдер/место обработки, бюджет, новые зависимости и ADR изменения версии без файла. Никогда: автоматически публиковать OCR, отправлять реальные схемы внешнему провайдеру без согласованного назначения, открывать Storage публично или применять миграции к средам без отдельного решения.

Открытый вопрос: распознавание внутри инфраструктуры или внешний сервис? DeepSeek выбран пользователем для текстового ассистента; это не выбор OCR и не разрешение автоматически отправлять туда технические схемы. Предлагается выбрать обработчик на этапе технического плана по поддержке PDF/фото, ru/kk, стоимости и ограничениям среды.

Локальный концепт: http://127.0.0.1:8770/library-preview.html. Это пример сценария: данные искусственные, сохранение временное, фактического OCR и публикации нет.
