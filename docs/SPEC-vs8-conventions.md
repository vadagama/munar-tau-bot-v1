# VS-8: общие соглашения спецификаций

Дата: 23.10.2026. Статус: согласовано пользователем 23.10.2026 сообщением «Делай». Границы и порядок модулей
согласованы в [карте](VS8-CAPABILITY-MAP.md); спецификации и их предложения согласованы.

Этот документ — общая часть каждой из пяти спецификаций. В нём закреплены
стек, команды, структура, стиль, стратегия проверки и границы действий.
Это требования к будущей реализации, а не свидетельство готовности VS-8.

- [Требования](docs/requirements-v1.md), [жизненный цикл](docs/request-lifecycle.md),
  [матрица прав](docs/access-matrix.md), [HLD](docs/hld.md),

  исторические упоминания закреплённых домов не возвращают старые ограничения.

## Общий контракт API

Транспорт использует существующий `/v1`, Actor и формат `ApiError` с `trace_id`.
Новые пути в модульных спецификациях — предложения расширения LLD-03.
Списки имеют ограниченную страницу, устойчивую сортировку с UUID как вторым
ключом и серверную фильтрацию; размер и форма пагинации следуют существующему API.

Изменения проверяют актуальные права внутри бизнес-транзакции. Управленческие
изменения требуют причины, `expected_version` и `Idempotency-Key`; создание —
ключа намерения. Для личных ответов/поддержки ключ и версия предотвращают
повтор эффекта и запись из устаревшей формы. Повтор того же ключа возвращает
исходный результат; другое тело с тем же ключом — `IDEMPOTENCY_CONFLICT`.
Несовпадение версии — `CONCURRENT_MODIFICATION`/409.

Валидация тела — на границе API/бота, бизнес-инварианты — в домене.
Чужой UUID не раскрывает содержимое объекта. Изменение, аудит и outbox
фиксируются атомарно. В аудит не копируются индивидуальные ответы опросов,
содержимое жалоб, переписка и лишние персональные данные.
Фоновые процессы повторно проверяют получателя и область; очередь не означает
успешную доставку. Наличие кнопки не даёт полномочий.

## Стиль

Именование и форматирование следуют соседним доменам; пример существующего
правила из `source/core/src/domains/tasks/access.ts`:

```ts
/** ROL-02d: совмещение ролей не разрешает приёмку собственного результата. */
export function canAcceptTaskReport(actor:Actor,row:TaskRow,reportAuthorId:unknown):boolean {
 return row.state === "on_review" && typeof reportAuthorId === "string" &&
  reportAuthorId !== actor.person.id && row.assignee_person_id !== actor.person.id &&
  can(actor,"task.manage",taskResource(row)).allow;
}
```

Параметризованный SQL, без конкатенации пользовательского ввода; JSON-строки
передаются с `$n::text::jsonb` по конвенции проекта. Транспорт не дублирует PDP.
Пользовательский текст экранируется; прямой HTML в React не вставляется.

## Интерфейс и локализация

Кабинет использует существующие PageLayout, DetailSection, CardDrawer и ActionPanel.
Каждая страница предусматривает загрузку, пустой список, ошибку и потерю прав.
Конфликт версии предлагает обновить карточку без потери введённого текста.
Кнопки доступны с клавиатуры, формы имеют подписи и понятные ошибки.

В ботах все действия доступны кнопками, основной текст содержит контекст;
небольшие варианты показываются сразу. Ответы — на языке профиля,
уведомления через каталог ru/kk. Смена сценария закрывает временную форму;
nonce, версия и повторный PDP запрещают устаревшие отправки. Длинные ответы
используют существующее разбиение HTML и устойчивые ключи уведомлений.

## Команды и стратегия проверки

Все команды выполняются из `source/`:

```sh
npm run typecheck
npm run lint
npm test
npm run build
deno task check
deno task lint
deno task test
npm run dev -w admin
```

Vitest: модульные тесты рядом с доменом, интеграционные — отдельно;
React Testing Library проверяет формы и состояния интерфейса.
Проверки включают положительный путь, запрет чужому актору, отзыв полномочий,
повтор, конфликт версии, rollback и отсутствие внешней доставки test-данных.
Сценарии проходят через API и бот/симулятор, кабинет проверяется в браузере.

Очищающий интеграционный прогон отключён проектным решением 17.10.2026.
Команда только после явного разрешения, при безопасном `TEST_DATABASE_URL`
Sydney и отсутствии параллельного прогона:

```sh
RUN_INTEGRATION_TESTS=1 npm run test:integration
```

Пропущенный прогон не считается проверкой PostgreSQL. Его отсутствие
фиксируется в приёмке как ограничение. Frankfurt не используется для очистки.
Процент покрытия не придумывается: обязательны перечисленные инварианты
каждого модуля и регрессионные проверки существующих сценариев VS-3/4/5/7.

## Границы действий

- Всегда: общие домены, серверный PDP на чтение и запись, защита финансовой
  аудитории, версии/идемпотентность, приватные файлы, RLS-заслон, проверка тестовых
  данных, уведомления в той же транзакции, явные доказательства приёмки.
- Согласовать: предложения спецификаций; противоречия требованиям;
  новые архитектурные решения и зависимости; очищающий интеграционный прогон;
  применение к облачной среде, выпуск и merge.
- Запрещено: выдавать неподтверждённые документы за проверенные,
  принимать собственную работу в обход ROL-02d, раскрывать индивидуальные
  ответы опросов, отключать провалившиеся проверки, публиковать секреты,
  смешивать реальные и тестовые данные, заменять финансовые/юридические решения.

## Готовность к следующей фазе

Нужны согласованные модульные спецификации, разрешённые открытые вопросы
и затем технический план. На этой фазе миграции и код не пишутся,
облачные среды не изменяются.
